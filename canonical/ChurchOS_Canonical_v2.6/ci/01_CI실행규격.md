# Church OS CI 실행 규격

현재 포함한 workflow는 정적 설계·회귀 검사만 실행한다. 별도 database-ci.yml에 DB·복구 job을 추가했으나 GitHub 실행은 NOT_RUN이다.

## 목표

PR마다 정적 계약과 PostgreSQL 16 실행을 재현하고, 실패한 실행을 PASS 근거로 기록하지 않는다. 실제 workflow 작성 시 이 문서를 기준으로 하되 저장소의 승인된 브랜치 정책과 runner 환경을 다시 확인한다.

## Job 순서

1. `static-integrity`
2. `openapi-and-schema`
3. `postgres-clean-apply`
4. `postgres-security`
5. `backup-restore`
6. `service-tests` - 구현 이후 활성화
7. `evidence` - 앞 단계 상태를 그대로 집계

## PostgreSQL 실행 역할

- container bootstrap만 기본 postgres 관리 역할을 사용한다.
- 별도의 non-superuser migration owner가 DB와 object를 소유한다.
- PostgreSQL 16에서는 역할 생성자에게 `SET ROLE` 권한이 자동 부여되지 않으므로 bootstrap 관리자가 `GRANT church_os_app TO <migration_owner> WITH SET TRUE`를 실행한다.
- 백업은 object owner가 아니라 별도 `church_os_backup` 로그인 역할로 수행하며, DBA가 `BYPASSRLS`, 데이터베이스 CONNECT, `GRANT pg_read_all_data TO church_os_backup`을 명시적으로 부여한다.
- 보안 테스트는 superuser 또는 `BYPASSRLS` 역할이면 즉시 실패한다.
- 실제 애플리케이션 로그인은 `church_os_app` group role을 상속하되 object owner가 아니다.

shell에서 migration 파일을 실행할 때 실행권한에 의존하지 않고 `psql -f`로 명시적으로 읽는다. 파이프 출력의 일부 `PASS|` 문자열만으로 job 성공을 판정하지 않고 각 명령의 종료코드를 사용한다.

## Evidence 형식

```json
{
  "gate_id": "G06",
  "status": "PASS|FAIL|INCOMPLETE",
  "commit_sha": "...",
  "postgres_version": "16.x",
  "started_at": "...",
  "finished_at": "...",
  "commands": [{"name": "01_tenant_fk_rls", "exit_code": 0}],
  "test_count": 1,
  "failure_count": 0,
  "artifact_hashes": ["..."]
}
```

Evidence collector는 모든 blocking gate가 PASS이고 누락이 없을 때만 전체 PASS를 만든다. `if: always()`는 증거 수집을 보장하기 위한 것이지 실패를 성공으로 바꾸는 장치가 아니다.

## Secret와 로그

- DB password, OIDC token, webhook secret, provider token은 secret store에서 주입한다.
- command echo와 SQL notice에 secret가 나타나지 않게 한다.
- 실패 payload는 key 목록과 schema error만 남기고 원문 body를 남기지 않는다.
- artifact에는 테스트 로그, 버전, 해시만 저장한다.

## 병렬화

정적 검사와 JSON Schema 검증은 병렬 실행할 수 있다. DB clean apply, security, restore는 동일 migration set의 순서 증거가 필요하므로 하나의 의존 체인으로 실행한다.
