# PostgreSQL 16 실행 절차

## 상태

이 절차와 SQL은 실행 후보이며 현재 패키지에서는 실제 PostgreSQL에 적용하지 않았다. 정적 검증 PASS와 runtime PASS를 혼동하지 않는다.

## 필수 전제

- PostgreSQL 16 이상
- 빈 전용 데이터베이스
- migration owner는 `CREATEROLE`이 있지만 superuser와 `BYPASSRLS`가 아닌 역할
- test runner는 migration object owner이며 bootstrap 관리자가 PostgreSQL 16 문법으로 `GRANT church_os_app TO <test_runner> WITH SET TRUE`를 실행했음
- `pg_dump`는 DBA가 별도로 만든 `church_os_backup LOGIN BYPASSRLS` 역할의 연결 문자열을 사용함. `GRANT pg_read_all_data TO church_os_backup`도 필수다.
- 운영 로그인 역할과 `church_os_app` group role은 분리
- 운영 비밀은 DB SQL이나 Git에 저장하지 않음

## 적용 순서

1. 빈 데이터베이스와 비로그인 runtime role을 준비한다.
2. `V001`부터 `V015`까지 이름 순서대로 한 번씩 적용한다.
3. 적용 파일의 SHA-256과 적용 시각을 migration history에 기록한다.
4. `00_posture_assertions.sql`을 먼저 실행한다.
5. `00`부터 `05` 보안 테스트를 순서대로 실행한다.
6. 각 테스트의 `PASS|...` 행과 psql 종료코드를 함께 저장한다.
7. object owner가 아닌 백업 전용 `BYPASSRLS` 역할로 전체 dump를 만든 뒤 별도 빈 DB에 restore한다.
8. restore DB에서 posture와 보안 테스트를 다시 실행한다.

## 실패 처리

- 적용된 migration 파일을 수정하지 않는다.
- 실패 원인을 수정한 새 forward migration을 추가한다.
- 아직 공유되지 않은 일회성 로컬 DB만 삭제·재생성할 수 있다.
- 운영·공유 DB에는 down migration을 기본 전략으로 사용하지 않는다.
- 테스트 로그에 민감 원문이나 접속 비밀번호를 기록하지 않는다.

## 합격 기준

- V001~V015 clean apply 성공
- 모든 migration transaction 종료 상태 정상
- 보호 테이블 23개 모두 ENABLE/FORCE RLS
- 보안 테스트 `00`부터 `05`까지 모두 PASS 결과행과 exit 0 확인
- app role의 타 tenant 조회 0행 또는 거부
- composite FK 교차 tenant 쓰기 거부
- 중첩 outbox 금지 키 거부
- audit update/delete 거부
- 시스템 역할 재시드 후 중복 0
- mutable row의 `row_version` 정확히 1 증가
- dump/drop/restore 후 동일 테스트 재통과

## 아직 남은 설계

- 실제 배포 도구(Flyway/Liquibase/직접 runner) 선택
- 운영 로그인 역할과 connection pool의 transaction-local context 설정
- 백업 보존기간·암호화·복구 목표
- 최소 10명·상보 억제를 적용한 pastor aggregate materialization
- 개인정보 삭제·보존 job
