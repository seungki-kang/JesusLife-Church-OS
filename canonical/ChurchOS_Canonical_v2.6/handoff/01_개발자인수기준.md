# Church OS 3.0 개발자 인수 기준

## 착수 전 제공물

- 제품·시스템 경계
- OpenAPI 3.1 계약
- JSON Schema 이벤트 계약
- PostgreSQL V001~V015 후보와 해시
- RLS·privacy 음성 테스트
- 권한 매트릭스와 reason code 정책
- Today·목회자 Overview 정책
- 화이트라벨 schema와 예시 3개
- 화면 명세 27개
- CI 품질 게이트

## 개발자가 임의 변경할 수 없는 사항

1. ChurchOS와 여섯 독립 전문 제품의 정본 경계
2. Pastor Aggregate Only와 Life Diary 코치 기능의 Church OS 완전 분리
3. 개인 원문 비복제
4. 참여·수료와 성장·성숙의 분리
5. `Missing != 0`과 소표본 suppression
6. tenant 복합 FK와 FORCE RLS
7. 교회별 code fork 금지
8. migration immutable과 API major 정책

## 첫 PR 합격 기준

- 목표 폴더 구조만 만들고 비어 있는 placeholder의 책임을 README로 설명
- Node·npm·Flutter·PostgreSQL 버전 pin 파일 포함
- root에서 lint·typecheck·unit test 명령이 실패 없이 실행
- OpenAPI·JSON Schema·migration hash validator 실행
- secret와 local build artifact가 Git에 포함되지 않음
- 구현되지 않은 기능을 PASS 또는 ACTIVE로 표시하지 않음

## Backend skeleton 합격 기준

- health와 readiness endpoint 분리
- correlation ID 생성·전파
- OIDC adapter interface와 test double
- transaction-local tenant·actor context wrapper
- default-deny authorization port
- domain module 간 직접 table 접근 금지
- outbox worker가 idempotent handler interface 사용
- raw request/response body logging 기본 비활성

## 화면 skeleton 합격 기준

- 역할별 route guard
- 교인과 목회자 첫 화면 분리
- loading·empty·missing·suppressed·error 상태 구분
- 전문 앱 미연결·장애·동의철회 상태 표시
- 키보드·screen reader·text scaling 기본 검사
- tenant brand 설정 실패 시 안전한 platform theme 사용

## 중단 조건

다음 중 하나라도 발생하면 병합하지 않는다.

- 개인 원문이 Church OS DB·로그·event에 저장됨
- 타 tenant 데이터가 조회되거나 참조됨
- 목회자 화면에서 개인 성장정보로 drill-down 가능
- admin role이 consent 없이 전문 앱 데이터에 접근
- migration 수정 후 기존 hash가 바뀜
- CI가 실패 또는 skip된 blocking gate를 전체 PASS로 기록
- 교회별 source fork가 생김
