# Church OS 배포와 운영 규격

## 목표

한 코드베이스를 환경별로 승격하고, 테넌트 설정만 분리한다. 교회별 소스 브랜치나 수동 패치를 운영하지 않는다.

## 환경

| 환경 | 목적 | 실데이터 | 외부 전송 |
|---|---|---|---|
| local | 개발자 단위 테스트 | 금지 | mock 기본 |
| test | 자동 통합·보안 테스트 | 합성 데이터만 | sandbox만 |
| staging | 출시 후보 검증 | 익명 합성/승인 fixture | sandbox 또는 제한된 시험 연동 |
| production | 실제 서비스 | 허용 | 승인된 production endpoint |

환경 간 DB 복사는 기본 금지한다. 필요한 경우 승인된 비식별 fixture 생성 절차를 사용한다.

## 배포 흐름

1. 변경 객체와 ADR/계약 영향 확인
2. format, lint, unit, contract, schema, migration 검사
3. 임시 PostgreSQL에서 처음부터 migration 적용 및 재적용 안전성 검사
4. 테넌트 격리·권한·민감정보 로그 부정 테스트
5. 컨테이너 이미지 SBOM 생성, 취약점 검사, digest 고정
6. staging 배포와 smoke test
7. 승인 후 production canary 5%, 25%, 100% 승격
8. 오류율·지연·DB 상태·DLQ·감사 이벤트 관찰

## 배포 중단 기준

- 교차 테넌트 접근 가능성
- 인증·권한 우회
- 원문 또는 민감정보의 로그·이벤트 노출
- 마이그레이션 비가역 손실 가능성
- 오류율 또는 지연이 SLO 예산을 초과
- Today·Pastor Overview의 잘못된 개인화 또는 집계 억제 실패

## 롤백

애플리케이션은 직전 digest로 되돌린다. DB는 적용된 migration을 삭제하지 않고 forward-fix를 원칙으로 한다. destructive migration은 expand-migrate-contract의 세 릴리스 절차와 복구 리허설 없이는 금지한다.

## 초기 SLO 후보

| 대상 | 목표 |
|---|---|
| 인증 제외 핵심 읽기 API | 월 99.9% |
| Today 읽기 p95 | 500 ms 이하 |
| 쓰기 API p95 | 800 ms 이하 |
| webhook 수락 | 2초 이하, 비동기 처리 |
| 복구 목표 | RPO 15분, RTO 4시간 후보 |

SLO는 파일럿 측정 후 확정한다. AI·CHGO·JLPrayer·JLBible 장애가 Church Core 사용 불가로 전파되지 않도록 degraded mode를 제공한다.
