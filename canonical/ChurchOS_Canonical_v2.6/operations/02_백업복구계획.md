# Church OS 백업과 복구 계획

## 범위 분리

Church OS 백업에는 교회 운영 데이터, 설정, 감사 메타데이터만 포함한다. 생명일기·기도수첩·너랑나랑 원문과 Personal Vault 객체는 각 전문 서비스의 별도 정책을 따른다.

## 후보 정책

- PostgreSQL: 지속 WAL 보관과 일일 전체 백업
- 객체 저장소: versioning, server-side encryption, lifecycle policy
- 설정: 서명된 release artifact와 Infrastructure as Code
- 암호화 키: 데이터 백업과 분리된 키 관리 및 복구 권한
- 감사 데이터: append-oriented 보관, 원문 미포함
- 백업 접근: 별도 역할, MFA, 승인 및 감사

## PostgreSQL 역할 경계

- FORCE RLS가 적용된 테이블은 일반 object owner의 `pg_dump`가 실패할 수 있다.
- DBA가 `church_os_backup LOGIN BYPASSRLS NOSUPERUSER NOCREATEDB NOCREATEROLE` 역할을 별도로 만들고 `GRANT pg_read_all_data TO church_os_backup`을 부여한 뒤 비밀 저장소에서 자격증명을 주입한다. BYPASSRLS만으로는 스키마·테이블 읽기 권한이 생기지 않는다.
- 백업 역할은 애플리케이션 요청에 사용하지 않으며, 네트워크·시간·명령을 백업 작업으로 제한하고 모든 사용을 감사한다.
- 복원 검증은 격리된 임시 DB에서 일반 앱 역할과 RLS를 다시 적용한 상태로 수행한다.

## 복구 단위

1. 단일 논리 레코드 복원은 감사·충돌 검토 후 보상 트랜잭션으로 처리한다.
2. 테넌트 복원은 다른 테넌트와 분리된 임시 환경에서 먼저 검증한다.
3. 전체 재해 복구는 새 환경에 인프라·DB·객체·비밀을 순서대로 복원한다.
4. 삭제된 개인 데이터는 법적 보관 의무와 삭제 전파 정책을 우선하며 일반 복구로 되살리지 않는다.

## 검증 주기

| 검증 | 주기 후보 | 합격 기준 |
|---|---|---|
| 자동 백업 무결성 | 매일 | 백업 완료·암호화·카탈로그 일치 |
| 표본 테넌트 복원 | 매월 | 격리 환경에서 읽기·권한 검사 통과 |
| 전체 DR 리허설 | 분기 | RPO/RTO 달성, 증거 기록 |
| 키 복구 훈련 | 반기 | 이중 통제하 성공, 평문 키 노출 없음 |

복구 성공은 명령 종료코드만으로 판정하지 않는다. 행 수, FK, tenant binding, RLS, checksum, 핵심 API smoke test를 함께 확인한다.
