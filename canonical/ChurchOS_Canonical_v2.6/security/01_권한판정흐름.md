# Church OS 권한 판정 흐름

## 기본 원칙

모든 요청은 DENY로 시작한다. 역할 하나만으로 허용하지 않고 다음 조건을 순서대로 검증한다.

1. token issuer, audience, signature, expiry, nonce 검증
2. external subject와 Church OS membership 연결 확인
3. token client와 요청 tenant의 서버측 binding 확인
4. membership 상태와 역할 유효기간 확인
5. API scope와 활성 module 확인
6. 요청 목적 `purpose_code` 허용 여부 확인
7. 필요한 경우 사용자 consent와 공유 범위 확인
8. resource가 같은 tenant에 속하는지 확인
9. 본인·담당 그룹·배정 업무 등 resource relation 확인
10. 응답 field redaction 또는 aggregate suppression 적용
11. ALLOW·DENY·REDACT·SUPPRESS·HANDOFF 결정을 감사 기록

## 권한 입력

```yaml
actor:
  subject_ref: opaque
  membership_id: uuid
  roles: [MEMBER]
client:
  client_id: opaque
  scopes: [church.today.read]
request:
  tenant_id: uuid
  action: today.read
  resource_type: today_feed
  purpose_code: MEMBER_SELF_SERVICE
policy:
  module_enabled: true
  consent_required: false
  current_time: RFC3339
```

## 결정 결과

```yaml
decision: ALLOW | DENY | REDACT | SUPPRESS | HANDOFF
reason_code: stable_machine_code
allowed_fields: []
denied_fields: []
obligations:
  - AUDIT
  - MASK_SMALL_GROUP
  - ISSUE_ONE_TIME_HANDOFF
policy_version: string
```

## 특별 규칙

- `X-Church-Tenant`는 요청 힌트일 뿐 권한 근거가 아니다.
- service token은 사용자를 자동 가장할 수 없다.
- TENANT_ADMIN은 생명일기·기도·상담 원문을 볼 수 없다.
- PASTOR도 기본적으로 개인 원문을 볼 수 없다.
- Church OS는 COACH 역할과 개인 원문 접근을 제공하지 않는다. 코치 공유는 생명일기 내부 종단 간 암호화 경계에서만 처리한다.
- 안전 신고는 일반 성장 flow보다 우선하지만 최소한의 담당자에게만 전달한다.
- feature flag는 기능 노출 조건이며 authorization을 대신하지 않는다.
