# ChurchOS 코드 개발 전 통합 기준

2026-11-11. 기술 정리 상태: 설계 지침. 실행 검증: **NOT_RUN**. 이 문서는 기존 COS·REC 합의를 대체하거나 미결 정책을 승인하지 않는다. 새 코드 개발·파일럿·에뮬레이터 실행은 이번 변경 범위가 아니다.

## 1. 무엇을 기준으로 개발하는가

제품·권한 정책은 [결정 원장](../decisions/DESIGN_DECISIONS.md), 특별 철회 정책은 [REC 결정 원장](../../recovery-design/RECOVERY_DECISIONS.md)을 따른다. 현재 요구사항은 [상세 설계](../operations/ecosystem-v1/DETAILED_DESIGN_V1.5.md)와 [통합 안내](../../START_RECOVERY_CURRENT.md)에서 찾는다. 이 문서는 그 요구사항을 구현할 위치·모듈 소유권·의존 순서·검증 방법을 연결한다. 과거 리비전의 '다음 작업'을 현재 개발 지시로 실행하지 않는다.

서로 다른 버전의 문장이 충돌하면 최신 날짜만으로 채택하지 않는다. 결정 ID·적용 대상·승인 범위를 확인하고 충돌을 기록한다. 사용자 정책 변경은 별도 결정으로 처리한다. 역사 문서와 스냅샷을 삭제하여 충돌을 숨기지 않는다.

| 근거 | 이번 대조 결과 | 개발 지침 |
|---|---|---|
| v2.6 구현과 루트 예약 서비스 경로 | 실제 서버는 canonical 내부, 루트의 예약 디렉터리는 실행 서버가 아님 | 후속 활성 소스를 한 곳으로 이행한 뒤 개발 |
| 공통 인증과 교회 승인 정책 | JWT 검증은 있지만 실제 공통 인증·최초 관리자·신규 심사 흐름은 미완료 | 데모 역할을 운영 권한으로 연결하지 않음 |
| 교회 정보·브랜드·소개 요구 | 같은 교회를 표현하지만 변경 이유와 게시 권한이 다름 | 소유 모듈과 레코드를 분리 |
| v2.6 멱등 영수증과 후속 결과 조회 | 키 재사용·결과 열람·감사 보유 목적이 다름 | 저장 기반 일부 공유, 업무 수명·열람 규칙 분리 |
| 기존 공지/일정 쓰기와 후속 초안/게시 | 기존 변경 API가 새 게시 워크플로를 보장하지 않음 | 호환 영향과 계약을 정한 후 새 행위 구현 |
| 독립 제품과 앱 내 연결 화면 | 화면 통합이 데이터 소유권 통합을 뜻하지 않음 | 제공자 어댑터를 통하며 원본 기능 복제 금지 |

## 2. 품질 우선순위와 변경 책임

우선순위는 교회 격리·개인정보와 권한 정확성, 업무 정합성과 복구 가능성, 앱 사용 용이성, 변경 용이성, 운영 비용 순으로 둔다. 정량 성능·가용성·비용 목표는 실제 부하와 운영 계약을 확인하기 전까지 미확정이다. 기능 편의를 위해 앞선 권한 원칙을 약화하지 않는다.

기능 변경 PR은 요구사항/결정 → 소유 모듈 → API/이벤트 → 데이터 변경 → 화면 상태 → 검증 증거를 연결한다. 모듈 소유자는 기술 책임 범위이며 실제 담당자 이름은 배정 전까지 미정이다. 담임목사의 도입 결정권과 서버의 게시·위임 권한은 별개다.

## 3. 소스 위치를 먼저 정리한다

| 대상 | 현재 위치/상태 | 후속 기준 |
|---|---|---|
| 백엔드 기준선 | canonical/ChurchOS_Canonical_v2.6/services/church-core | 바이트 보존, 후속 기능을 직접 추가하지 않음 |
| 후속 활성 백엔드 | 아직 생성하지 않음 | 루트 services/church-core를 단일 활성 위치로 사용하는 이행안 |
| 앱 | apps/church-os | 같은 앱에서 교인·운영자 업무; 현재 데모와 실제 연결 구분 |
| 루트 예약 서비스 | services 아래 과거 경계 자료 | 별도 ChurchOS 서버를 동시에 새로 구현하지 않음 |
| 기존 루트 DB | 과거 별도 계보 | 신규 전용 DB에 혼합 적용하지 않음 |
| 관리자 웹 | apps/admin-console의 역사 자료 | 기본 교회 업무의 필수 실행 경로로 부활시키지 않음 |

활성 소스 이행(S00)은 다음 순서를 따른다. 이번 문서 변경은 이행을 실행한 것이 아니다.

1. 기준 커밋·소스 해시·80개 서버 회귀 테스트 목록과 기존 설정/실행 명령을 기록한다.
2. 스냅샷에서 활성 소스를 한 번 파생한다. 출처를 기록하고, 복사 후 두 소스를 동시 유지하지 않는다. 기존 스냅샷 검사는 보존 검사로 남긴다.
3. 활성 OpenAPI·마이그레이션·테스트·실행 도구의 경로를 함께 이행한다. v2.6 V001~V015 해시와 순서를 보존하고 후속 변경은 새 버전으로 추가한다. 기존 운영 DB 계보와의 이관은 별도 검증한다.
4. CI·문서·런처를 활성 경로로 전환한다. 같은 버그를 스냅샷과 활성 소스 양쪽에 수정하도록 만드는 의존을 제거한다.
5. 기존 API 호환과 회귀를 검증한 뒤 신규 기능 개발을 시작한다. 스냅샷을 고쳐 과거 증거를 재사용하지 않는다.

## 4. ChurchOS 안의 모듈 경계

ChurchOS 백엔드는 기능별 모듈을 둔 단일 서비스로 시작한다. 소유권표의 각 행은 논리적 책임이며 행마다 별도 패키지·서버·DB를 생성하라는 뜻이 아니다. 여섯 사용자 제품의 독립 배포 원칙을 ChurchOS 내부 기능마다 별도 서버를 만드는 근거로 사용하지 않는다. 현재 NestJS/TypeScript 기반과 기존 IdentityPort·StorePort·AuditPort를 검토하여 필요한 경계만 확장한다. 프레임워크를 교체하는 작업은 포함하지 않는다.

[데이터 소유권표](DOMAIN_OWNERSHIP.csv)가 레코드별 쓰기 소유자를 지정한다. 각 모듈의 사용 사례가 상태 전이를 결정하고, 다른 모듈은 공개된 인터페이스로 요청한다. 다른 모듈 테이블에 임의로 쓰지 않는다. 조회용 투영은 정본이 아니며 필드·대상·삭제 전파·재생성 기준을 가진다.

권장 활성 서비스 내부 구조는 modules/<도메인>/{domain,application,adapters}다. domain은 HTTP·DB SDK·외부 제품 SDK를 가져오지 않는다. application은 권한 판정과 트랜잭션 사용 사례를 조합하고, adapters가 HTTP·PostgreSQL·제공자 API를 연결한다. 파일 수를 맞추려고 빈 계층을 만들지 않는다. 기존 app.ts/postgres.ts의 여러 책임은 기능을 옮길 때 실제 호출자와 함께 나눈다.

| 경계 | 소유하는 것 | 공유/참조하는 것 | 합치면 생기는 문제 |
|---|---|---|---|
| church | 교회 식별·개설 심사·운영 사실 | 다른 기능이 church_id 참조 | 브랜드 변경이 교회 승인 사실까지 변경 |
| experience | 로고 참조·색상·홈 배치·표시 설정 | 소개/공지/일정 ID와 허용 투영 | 설정 JSON에 본문과 게시 규칙 중복 |
| church_intro | 목회철학·사명·비전 등 기관 소개 | 선택된 홈 카드가 게시본 참조 | 미선택 콘텐츠 강제, 초안의 공개 유출 |
| membership/access | 유효 소속 / 위임·역할 | 모든 사용 사례가 현재 권한 검증 | 공동체·교육·봉사 상태가 교인 권한으로 승격 |
| community/community_intro | 공동체 소속 / 개인 소개 동의·철회 | 명시적으로 허용된 최소 명단 | 기관 소개 게시 로직으로 개인 철회 보장 대체 |
| notice/event | 공지 게시 / 일정과 취소 | 홈·알림은 정본을 참조 | 화면 카드마다 본문·시간의 별도 사본 생성 |
| attendance/ministry/care | 업무별 대상·출석·배정·후속 처리 | 허용된 교인·공동체 참조 | 하나의 범용 참여 상태가 정정·권한을 혼합 |

한 화면은 여러 모듈의 허용 결과를 조합할 수 있다. 화면을 한 번에 그린다는 이유로 해당 레코드의 쓰기 권한이나 정본을 합치지 않는다.

## 5. 공통으로 만들 것과 업무별로 남길 것

| 공통 기반 | 업무별로 유지할 규칙 |
|---|---|
| 현재 교회 문맥·인증 검증 인터페이스·추적 ID | 승인·게시·철회·역할 부여의 자격과 상태 전이 |
| 트랜잭션·멱등 키 파싱·영수증 저장 기반 | 키 범위·충돌·만료 후 행위·조회 기간·오류 공개 수준 |
| 구조화 에러 형식·민감값 제거 | 화면별 안내·재시도 허용 여부·정정 책임 |
| 디자인 토큰·버튼·목록·로딩·빈 화면 | 공지·일정·소개·공동체의 입력 필드와 확인 절차 |
| 파일 업로드/참조 어댑터 | 자원별 업로드 자격·사용 동의·열람·철회·보유 기간 |
| 알림 전송 어댑터·실패 재시도 기반 | 알림 대상·최소 내용·동의·확정 결과 전달 시점 |

범용 /commands API 하나에 모든 업무를 밀어 넣거나, 공통 CRUD가 업무 권한을 대신 판정하게 하지 않는다. 컴포넌트 재사용과 상태 머신 재사용은 별개다. 반복 횟수만으로 공통화를 강제하지 않고 동일한 변경 이유와 보안 규칙인지 확인한다.

멱등 키 재요청 영수증, 사용자 결과 조회 투영, 감사 기록은 목적과 접근권한이 다르다. v2.6의 24시간 영수증 만료를 후속 168시간 결과 조회의 근거로 재사용하지 않는다. 특별 철회의 조회·증거·불확정 처리 조건도 일반 게시 기능에 일괄 적용하지 않는다. 기록별 수명표와 계약이 확정되기 전 통합 TTL 상수를 만들지 않는다.

V012의 공지/일정 첨부 권한을 로고·설교 파일에 자동 적용하지 않는다. 새 자원 유형과 참조 관계·삭제 전파를 명시한 후 마이그레이션한다. 별도 범용 파일 플랫폼을 먼저 구축하는 것은 필수 조건이 아니다.

## 6. 쓰기 사용 사례의 공통 실행 틀

입력 검증 → 토큰 대상/현재 소속·행위 권한 확인 → 멱등 문맥/현재 버전 확인 → 트랜잭션 내 상태 변경·업무 감사·필요한 outbox 기록 → 커밋 → 결과 반환 순서를 기준으로 한다. 실제 권한 판정은 변경과 경합하지 않도록 트랜잭션 안에서 필요한 상태를 재확인한다. 권한 해제와 제출의 경쟁 조건을 업무별 검증한다.

업무 감사 기록은 변경 사실의 증거이며 HTTP 요청 로그·성능 로그와 구분한다. 기존 AuditPort가 어느 목적을 수행하는지 확인한 뒤 역할을 정한다. 동일 사건을 서로 다른 '정본 감사'로 중복 저장하지 않는다. 원문·토큰·증빙 파일은 요청 로그에 남기지 않는다.

알림과 외부 호출은 커밋 이후 전달한다. 알림 실패가 이미 확정된 승인을 되돌리지 않는다. outbox·재시도·처리 중복 방지는 필요한 쓰기부터 도입하며, 외부 제품에 변경을 보내는 경우 양측의 멱등/철회/보상 계약을 먼저 정한다. 전체 제품을 하나의 DB 트랜잭션으로 묶지 않는다.

읽기·숨김 메뉴·기능 플래그는 권한을 부여하지 않는다. 교회 전환 시 이전 교회 캐시·진행 중 요청을 분리하고 서버에서 현재 권한을 검증한다. 초안 미리보기 API와 공개 게시본 API를 분리하고 인증 내부 읽기를 방문자 공개 읽기로 전용하지 않는다.

## 7. 외부 제품과 화이트라벨의 변경 격리

공통 계정은 하나의 사람 식별을 연결하며 제품 이용·교회 권한·개인 공유 동의는 별개다. ChurchOS는 JLPrayer의 기도 원본, JLBible의 본문/권리·통독, JLAcademy의 교육/수료, 너랑나랑의 관계 실천, 생명일기의 개인 기록을 다시 구현하지 않는다. 어댑터는 제공자별 토큰 대상·필드 허용 목록·시간 제한·실패 격리를 가진다. 생명일기의 원문뿐 아니라 작성 여부·횟수·날짜·코칭 상태도 수집하지 않는다.

기도·성경/찬송은 교회 앱 내부에서 편하게 사용하도록 화면을 구성하되 실제 제공자 계약과 콘텐츠 권리를 충족해야 한다. 제공자가 중단되면 공지·일정 등 ChurchOS의 독립 업무는 계속 사용할 수 있어야 한다. 제공자 계약이 미확정인 기능은 연결된 것으로 표시하지 않는다.

화이트라벨은 공통 디자인 토큰·검증된 테마·공통 컴포넌트 위의 교회별 설정으로 구현한다. 교회마다 Flutter 소스·패키지를 복제하지 않는다. 선택하지 않은 소개 항목은 빈 카드/필수 입력으로 노출하지 않는다. 간단 설정을 기본으로 하고 복잡한 선택에 설명·미리보기·복원 수단을 제공한다. 접근성 기준을 벗어나는 색/대비 조합은 안내하고 안전한 대안을 제시한다.

교회 메뉴 선택, 운영 릴리스 플래그, 서버 권한은 서로 다른 값이다. 메뉴를 켠다고 계약·동의·권한이 생성되지 않는다. 공유 앱의 원격 설정 갱신과 네이티브 앱의 스토어 업데이트를 구분한다. 교회 전용 앱·직접 영상 호스팅은 별도 운영/비용 범위이며 기존 기본형에서 자동 제공한다고 약속하지 않는다.

## 8. 개발 순서와 진입 기준

[개발 의존 순서표](DEVELOPMENT_SLICES.csv)는 선행 조건을 명시한 S00~S11이다. 상세 설계의 D0~D4는 제공 단계의 분류로 보존하며, D 번호만 보고 모든 기능을 일렬로 개발하지 않는다. 외부 계약은 S00부터 병행 준비할 수 있다. S09 대기가 내부 읽기 S03 개발까지 막지는 않는다.

| 묶음 | 목적 | 종료 조건 |
|---|---|---|
| S00~S01 | 단일 활성 위치와 소유권·공통 계약 | 경로 이행·호환·데이터 책임·계약이 검증 가능한 상태 |
| S02~S04 | 인증/읽기 수직 흐름과 개설·가입·위임 | 실제/합성 인증 구분, 서버 현재 권한과 초기 권한 부여 경로 검증 |
| S05~S08 | 게시·브랜드·소개·공동체·교회 업무 | 기능별 쓰기·경합·정정·특별 철회 조건 충족 |
| S09~S10 | 기본 외부 연결과 선택 교육/CHGO | 제공자별 권리·토큰·최소 데이터·사람 승인 검증 |
| S11 | 승인된 출시 범위의 전체 확인 | 포함 기능과 운영 준비 증거가 모두 충족 |

기본형은 공동체·출석·봉사·후속 업무·기도·성경/찬송·설교 등 기존 출시 목표를 유지한다. 내부 수직 증분 하나가 통과했다고 기본형 범위를 축소하거나 출시 완료로 쓰지 않는다. 선택 교육 S10은 교회의 선택과 해당 기능 제공 시 조건을 따른다. 파일럿/출시 검증의 계획은 남기되 현재 사용자가 미룬 실행을 시작하지 않는다.

각 단계는 설계 정리, 계약 확정, 코드 구현, 실제 검증을 따로 표시한다. CSV의 NOT_RUN은 실행하지 않았다는 뜻이다. 기존 [블로커 원장](../../recovery-design/IMPLEMENTATION_BLOCKER_REGISTER.md)의 B 번호를 종료 조건으로 추적하고, 단순 문서 검사 통과로 닫지 않는다. 특정 기능의 차단 조건은 그 기능에 적용하며 모든 기능에 불필요하게 확장하지 않는다.

## 9. 개발하면서 자동으로 지킬 규칙

| 검증 | 잡으려는 실패 | 적용 시점 |
|---|---|---|
| 소유권/의존 순서 정적 검사 | 중복 ID·중복 레코드 소유·없는 선행 단계·의존 순환 | 지금 문서 CI |
| 모듈 import 검사 | domain의 DB/HTTP 의존·순환 참조·외부 DB 접근 | S01에서 실제 경로에 맞춰 도입 |
| 도메인 행동 테스트 | 승인·게시·정정·철회의 허용/차단과 경쟁 결과 | 해당 쓰기 구현 시 |
| PostgreSQL 통합 테스트 | RLS·FK·롤백·트랜잭션 내 권한·직접 변경 우회 | DB 변경 시 |
| 제공자 계약 테스트 | 토큰 대상·필드/오류 변경·동의와 철회 전파 | 실제/검증용 제공자 연결 시 |
| 앱 핵심 흐름 테스트 | 교회 전환·빈/실패 상태·응답 유실·이전 데이터 노출 | 실제 앱/API 연결 시 |
| 구버전/복원/운영 검증 | 마이그레이션·삭제 상태 재적용·설정 호환 | S11 전 |

불안정한 테스트는 원인을 고치고 격리 사유/복구 조건을 기록한다. 핵심 회귀를 통과시키려고 삭제하지 않는다. 테스트 수·커버리지 비율만으로 완료를 판정하지 않는다. 비밀 탐지·의존성 보안 갱신·정적 타입/린트는 활성 코드 경로와 함께 CI에 연결하고, 정의된 워크플로와 실제 성공 실행을 구분한다.

## 10. 업데이트·운영을 위한 인계

API/이벤트는 계약 버전을 두고 기존 소비자 영향을 기록한다. 필드 삭제·이름 변경·필수화는 호환 기간과 소비자 전환을 먼저 정한다. DB는 확장 → 데이터 이전/검증 → 읽기 전환 → 구필드 제거 순서가 필요한지 변경별로 판단한다. 롤백 불가능한 데이터 변경은 코드 롤백과 분리하여 복구 절차를 정한다.

기능마다 성공/거절/일시 실패를 구분할 최소 지표·trace_id·지원 절차를 지정한다. 토큰·개인 기도/일기/증빙은 지표와 로그에 넣지 않는다. 가용성·대기열·복구 시간·지원 담당의 수치는 운영 책임자와 실제 환경이 정해지기 전 미정으로 둔다. 배포 빈도·변경 실패·복구 시간은 운영 시작 후 증거로 측정한다.

첫 구현 전에 아직 필요한 것은 실제 공통 인증 제공자와 식별/철회 계약, 권한 초기 부여와 심사 운영의 미결 결정, 새 게시/자산/보유 기간의 세부 계약, 외부 콘텐츠 권리와 API 확인이다. 이 문서가 그 결정을 대신 승인하지 않는다. 다음 실행 작업은 S00의 경로·계약·마이그레이션 이행표 작성이며, 그 이후 선택된 수직 기능의 계약과 실패 검증을 먼저 확정한다.

## 11. 이번 변경의 검증과 한계

문서 구조 검사와 검사기 회귀 20개가 PASS다. v2.6 정본 매니페스트 검사도 PASS이며 스냅샷·앱·서버 구현은 변경하지 않았다. 이 검사는 데이터 소유권 문장의 정책적 완전성이나 실제 DB 권한을 증명하지 않는다. 실행 원장에는 실제/합성·미실행을 구분한다.

기존 합의와 연결하여 기술적 중복 위험을 줄인 상태이며, 모든 미결이 해소되거나 모든 기능이 바로 구현 가능한 상태라는 뜻은 아니다. 실제 SSO·외부 제품·모바일·DB 이행/복원은 이번 작업에서 NOT_RUN이다. GitHub main 반영도 별도 확인 전까지 완료로 기록하지 않는다.
