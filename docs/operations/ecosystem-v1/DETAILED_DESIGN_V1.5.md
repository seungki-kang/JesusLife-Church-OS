# ChurchOS 상세 개발 설계 v1.5

2026-10-24. ID COS-DETAIL-001. 운영 합의 v1.4를 실제 개발 단위로 구체화한 설계 문서다. 에뮬레이터 실행과 신규 기능 코딩은 이번 단계에서 하지 않는다.

## 1. 기준과 상태

기준 저장소 브랜치: feature/churchos-app-0.1, 커밋 b37c6c8. 사용자가 GitHub에 올린 최신 파일에서 작업을 시작했다. v2.6은 실제 백엔드 구현·검증 기준점이고 운영 v1.4/상세 v1.5는 후속 요구사항이다. 문서가 추가되었다고 v2.6 OpenAPI·DB·외부 제품에 신규 기능이 생기지 않는다.

확인된 검증은 v2.6 서버 테스트 80개, 사용자 제공 PostgreSQL/API 검사 63개 PASS, 사용자가 보낸 Flutter 위젯 테스트 3개 PASS 출력이다. Flutter 세 테스트는 기도 화면의 데모 표시, 시연 역할별 관리자 진입, 교회 전환의 데모 상태 초기화다. 실제 모바일 실행·인증·기도/성경/찬송/설교 연결·신규 기능 검증은 미완료다. 사용자의 테스트 출력은 대화 근거이며 실행 원본 로그가 저장소에 제출된 것은 아니다.

## 2. 출시 범위와 단계

첫 출시는 '교회 기본형'을 목표로 한다. ChurchOS 앱 하나로 교인과 운영자가 기본 업무를 처리한다. 관리자 웹·PWA·교회 홈페이지는 필수 경로가 아니다. 아래 준비 단계는 개발 순서를 뜻하며, 미완성 전문 기능을 숨기고도 '전체 기본형 완성'이라고 부르는 기준은 아니다.

| 단계 | 제공 가치 | 단계 종료 조건 |
|---|---|---|
| D0 설계 확정 | 범위·화면·권한·정본·외부 계약 정리 | 미결 사항·가정·현재 구현과의 차이 기록 |
| D1 운영 흐름 개발 | 인증→교회 가입→공지/일정→관리자 게시 | 실제 API·역할·교회 경계와 앱 오류 처리 검증 |
| D2 기본형 파일럿 준비 | 화이트라벨·기도·성경/찬송·설교/수동 나눔지·공동체·출석·봉사·후속 업무 | 파일럿에 포함할 모든 기능 실제 검증, 콘텐츠 권리/제공 범위 고지 |
| D3 선택형 확장 | Academy·너랑나랑·생명일기 교육 경로, CHGO 설교 초안 | 제공자별 계약과 별도 검증. Academy 미선택 교회에 교육 의무 없음 |
| D4 별도 구축 | 직접 영상 호스팅·교회 전용 앱 | 비용·계정·지원·인계·공통 업데이트 계약과 실행 검증 |

회계·헌금 결제·시설 예약·온라인 쇼핑·독자적 영상 서버·개인 영성 순위는 첫 기본형에 넣지 않는 제안이다. 목사님의 기본 기능 요구를 축소 확정하는 뜻이 아니라 파일럿 범위를 검토하기 위한 구분이다. 각 교회 도입 시 필수 요구를 확인하고 범위를 바꿀 때 데이터·비용·출시 영향을 함께 기록한다.

## 3. 한 앱의 역할·화면 구조

하단 메뉴는 홈·말씀·기도·교회생활·내정보를 기준안으로 한다. 교회 관리자 도구는 내정보의 '교회 관리'와 콘텐츠별 '관리'로 접근한다. 모든 변경 동작은 서버 권한 검사를 거친다. 운영 앱에는 데모 역할 선택을 넣지 않는다. 현재 시연 앱의 역할/교회/Academy 스위치는 테스트 빌드 전용으로 분리해야 한다.

| 화면군 | 필수 화면 | 핵심 동작 | 데이터 책임 |
|---|---|---|---|
| 시작 | 로그인·교회 선택·가입 대기·접근 철회 | 인증·가입·활성 교회 선택 | 인증 제공자 + ChurchOS 소속 |
| 홈 | 교회 브랜드·공지·일정·이번 주 설교·선택 연결 | 목록→상세→원래 위치 복귀 | 교회 정본과 허용된 제공자 결과 |
| 말씀 | 성경·찬송·설교 목록/상세·요약·나눔지 | 앱 내 열람·영상/음성·통독 이동 | JLBible 콘텐츠 / ChurchOS 설교 |
| 기도 | 나의 수첩·교회 공동기도·기도 요청·기도방 | 조회·작성·공유 선택·응답 | JLPrayer |
| 교회생활 | 내 공동체·행사·출석·봉사·선택 교육 | 소속·참여·신청/취소·실천 이동 | ChurchOS / 각 전문 제품 |
| 내정보 | 기본 계정·소속·알림·연결·철회 | 계정/제품/교회 행동 구분 | 각 정본 소유자 |
| 교회 관리 | 브랜드·가입·교인/역할·공지/일정·설교·기도 검토·연결·사용량 | 단계별 편집·미리보기·승인/게시 | ChurchOS + 제공자 권한 |

모든 API 화면에는 LOADING / EMPTY / READY / FAILED / UNAUTHORIZED / FORBIDDEN / STALE 상태를 명시한다. 미설정·권리 미확보·제공자 장애는 빈 목록과 구분한다. 실패를 0건/미활동/미성숙으로 바꾸지 않는다. 온라인 연결이 필요한 쓰기는 성공 응답 전에 완료 표시하지 않는다.

## 5. 대표 업무의 데이터·상태·계약

### 5.1 가입과 교회 전환

인증 계정의 issuer/subject와 교회 membership ID를 구분한다. 가입 요청은 PENDING→APPROVED/REJECTED/CANCELLED로 모델링하는 제안이며 기존 membership 상태를 그대로 대체하지 않는다. 승인 시 소속을 멱등 생성한다. 탈퇴/정지 시 새 요청의 권한을 차단하고 제품별 연결 근거를 철회한다. 여러 교회 가입 여부와 승인 정책은 설정으로 명시한다. 교회 전환 시 이전 교회 요청 취소·캐시 제거·역할 재조회·딥링크 재검증을 수행한다. 이름·전화번호만으로 계정을 병합하지 않는다.

### 5.2 공지와 일정

원본: ChurchOS. 현재 서버가 지원하는 공지/행사 생성·상세·수정·게시·취소를 재사용한다. 초안 목록과 관리자 조회 범위는 아직 보완이 필요하다. 현재 일반 목록은 게시 콘텐츠 중심이므로 현재 API만으로 '관리자 초안함' 완성을 선언하지 않는다. 수정은 ETag/If-Match, 쓰기는 멱등 키를 사용한다. 412 충돌 시 최신 버전을 다시 읽고 사용자 편집 내용을 보존해 재적용 여부를 선택한다. 충돌 시 자동 덮어쓰지 않는다.

게시·취소 상태와 물리 삭제를 구분한다. 현재 취소는 종결 상태로 다루므로 '숨김→다시 게시' 요구가 있으면 새 전이 정책을 설계한다. 앱에서 임의로 취소를 삭제·보관과 같은 버튼으로 표시하지 않는다. 구체적인 종결·복제·재등록 동작을 사용자에게 설명한다.

### 5.3 기도

원본: JLPrayer. ChurchOS가 별도 개인 기도 테이블을 만들지 않는다. 개인 화면은 자기 수첩만, 공동기도는 제공자가 확인한 범위만 읽는다. 개인 수첩을 교회에 공유하려면 '공동기도 요청 제출'을 별도 동작으로 분리한다. 공개 요청 상태 SUBMITTED→APPROVED/REJECTED/WITHDRAWN은 제안이며 JLPrayer 실제 상태 모델과 대조해야 한다. 사용자 개인 기록을 교회에서 삭제하거나 관리자 승인만으로 공개할 수 없게 한다. 화면 원문·키보드 입력·실패 요청 본문·알림 미리보기를 운영 로그에 남기지 않는다.

대상 API capability는 personal.read/write, church.read/submit, moderation.review, room.join/leave다. provider audience 토큰과 본인/교회 참조·공유 정책을 JLPrayer가 검사한다. ChurchOS 토큰을 그대로 모든 제공자에 재사용하지 않는다. 화면이 직접 제공자 API에 접근할지 얇은 gateway를 사용할지는 인증 구조에서 확정하되, 어느 경우도 업무/원문 저장을 ChurchOS에 복제하지 않는다.

### 5.4 성경·찬송·통독

원본: JLBible. ChurchOS 뷰어가 판본/본문/찬송/허용 자산을 API로 받는다. 허용된 표시·검색·악보·음원·오프라인 권한을 나눈다. 판본·콘텐츠 버전·회수/만료 정책을 캐시에 적용한다. 단순 성경 열람·마지막 위치를 통독 완료로 만들지 않는다. 통독 진도 갱신은 JLBible 업무 흐름에서만 확정한다. 라이선스 미확보는 서비스 오류나 0건과 구분한다.

### 5.5 설교·요약·나눔지

원본: 교회별 ChurchOS 콘텐츠. YouTube 연결이 기본이고 음성·원고·승인 요약/나눔지를 별도 제공한다. 직접 영상 호스팅은 기본형 밖이다. 설교 metadata와 asset ref, 소스 버전, 처리 권한, 생성 작업, 요약/나눔지 버전, 승인 기록을 분리한다. 실제 DDL은 생성 전이다.

링크만으로는 초안 생성하지 않는다. CHGO는 개념/근거를 연결하고, 전사·자연어 생성 어댑터는 별도다. 교회가 허용한 원고·검토 전사만 입력한다. 생성 초안은 리뷰 전 비공개이며 원고가 바뀌면 STALE을 표시한다. 검토자가 수정·승인하고 게시자가 게시한다. 한 사람이 두 권한을 가질 수 있으나 생성 완료가 자동 승인을 만들지 않는다. 작업 재시도·취소·소스 버전·교회 경계를 검증한다. CHGO 실패 시 수동 요약·기존 승인본을 계속 제공한다.

### 5.6 Academy와 실천

교회 선택/제품 이용권, 개인 수강, ChurchOS 행사 참가, 생명일기/너랑나랑 개인 계정을 각각 구분한다. 연결 참조 후보는 tenantRef, courseRef, cohortRef, lessonRef, churchEventRef, activityRef다. 제공자 소유 ID를 ChurchOS DB 외래키로 강제하거나 이름으로 매칭하지 않는다.

Academy의 교육 안내→너랑나랑 활동→생명일기 실천/나눔으로 이동한다. ChurchOS는 생명일기 작성 여부·회차·원문을 받지 않는다. 코치 권한·공유는 생명일기에서 따로 확인한다. 수강 종료/교회 탈퇴/제품 이용권 해지는 개인 기록 삭제를 뜻하지 않는다.

## 6. 기존 API와 신규 요구의 차이

| 영역 | 확인한 실제 구현 | 다음 설계/개발 |
|---|---|---|
| 인증 | 설정된 OIDC JWT 검증 어댑터 | 실제 제공자·앱 로그인·복구·세션·제품별 토큰 |
| 교회 | 승인 소속의 tenant 조회 | 개설·브랜드·가입 요청·승인·전환 목록 |
| 교인 | 목록·생성 | 역할/소속 정정·승인·정지·범위별 조회 |
| 공지/행사 | 생성·목록·상세·수정·게시·취소 | 관리자 초안함·위임 권한·앱 저장/충돌 UI |
| 출석/공동체/봉사/돌봄 | 설계/DB 기반, 주요 앱 API 미구현 | 상태 전이·행사/담당자 범위·정정·조회 |
| 기도/성경/찬송 | 시연 화면과 소비자 요구 | 제공자 계약·권한·콘텐츠/공유 범위·앱 API 연결 |
| 설교/CHGO 나눔지 | 운영 설계·시연 설명 | 새 API·DDL·비동기 작업·승인·파일/콘텐츠 정책 |
| 관리자 | 시연 화면·TENANT_ADMIN 서버 쓰기 | 실제 역할 조회·세부 위임·모바일 전체 흐름 |

신규 API는 다음 버전에서 OpenAPI·권한·DB·테스트를 함께 추가한다. v2.6의 spec에 경로가 있어도 실제 라우트·업무 구현이 없으면 완료가 아니다. 후속 마이그레이션은 별도 추가하며 기존 V001~V015를 수정하지 않는다. 다른 Git DB 계보에는 적용하지 않는다.

## 7. 비기능 요구와 실패 처리

| ID | 요구 | 검증 |
|---|---|---|
| N01 | 교회·사용자·제품 권한 격리 | 잘못된 tenant/대상/토큰·철회 후 요청 거부 |
| N02 | 웹 없는 기본 운영 | Android/iOS 앱에서 관리자 기본 업무 전체 수행 |
| N03 | 장애 격리 | 외부 기도/성경/CHGO 실패 중 공지·일정 저장 유지 |
| N04 | 저장 정확성 | 중복 요청·오프라인 복귀·412·부분 업로드·재시도 처리 |
| N05 | 원문 보호 | 기도/일기/관계/답안이 로그·이벤트·관리자 통계에 없음 |
| N06 | 승인과 출처 | 설교·나눔지 소스/승인/버전, 소스 변경과 철회 반영 |
| N07 | 접근성 | 글자 확대·스크린리더·긴 제목·작은 화면에서 필수 동작 |
| N08 | 자료 권리 | 판본/표시/검색/재생/오프라인 허용 범위 검사 |
| N09 | 복구 | 백업 복구 후 소속/공유 철회가 부활하지 않음 |
| N10 | 관측 | 원문 없는 trace·오류·지연·재시도·작업 상태, 알림 중복 키 |

성능 목표 수치·보유기간·지원 시간·저장 한도·요금은 임의 확정하지 않는다. 파일럿 대상 교회 규모와 공급자 선택 후 예산/측정 기준을 정한다. 단말 분실·앱 로그아웃·계정 교체 시 민감한 화면/캐시/진행 중 요청을 정리한다. 외부 인증창은 허용하되 별도 ChurchOS 웹 관리자를 필수로 만들지 않는다.

## 8. 정밀화 단계의 산출물과 다음 순서

현재 산출물: 이 문서, FEATURE_MATRIX_V1.5.csv, CONTRACT_BACKLOG_V1.5.md. 기능표는 화면·정본·권한·현재 구현·다음 단계·검증 기준을 연결한다. 계약 백로그는 제공자별 입력/출력·불허 데이터·장애/철회 조건을 정리한다. 모두 문서 검토 전인 설계이며 실제 API 계약 체결을 뜻하지 않는다.

다음 순서는 (1) 교회 기본형 범위 검토 (2) 실제 제공자 정본/소스 대조 (3) 역할/상태/입출력 확정 (4) 화면별 상세 동선·오류 화면 (5) OpenAPI·신규 DDL 검토 (6) 구현 재개다. 에뮬레이터 실행은 구현 검증을 재개할 때 수행한다. 이번 Git 커밋은 설계 브랜치에만 보존하고 자동 main 병합을 하지 않는다.

## 9. 함께 검토할 의사결정

| 항목 | 제안 | 현재 상태 |
|---|---|---|
| 교회 공동기도 공개 | 기본은 제출→검토→게시, 교회별 변경 | JLPrayer 정책 대조 필요 |
| 설교 승인자 | 목회자 검토 권한을 명시적으로 부여, 동일인 편집/승인 허용 가능 | 교회 역할 모델 확정 필요 |
| 초안 보관/취소 | 취소·숨김·보관·재게시를 분리 | v2.6 취소 종결과 차이 검토 |
| 회원가입 정보 | 필요한 소속/연락 정보부터, 민감 상세정보 일괄 수집 제외 | 초기 필드 목록 확정 필요 |
| 기도/말씀 공개 | 교회별 공개 콘텐츠와 개인 영역을 구분 | 비회원 공개 범위 확정 필요 |
| 직접 영상 구축 | 상담 후 전용 서비스/앱 선택 | 한도·비용·지원은 미정 |

검토가 필요한 항목은 미결로 유지하며 사용자 의사결정으로 자동 간주하지 않는다. 기능을 추가할 때 정본 소유·권한·상태·화면·실행 증거를 함께 갱신한다.
