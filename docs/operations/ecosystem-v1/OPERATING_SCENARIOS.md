# ChurchOS 중심 생태계 운영 시나리오 v1.2

작성일: 2026-10-24 (한국 시간). 문서 ID: COS-ECO-OPS-001.

## 적용 상태와 권위

사용자의 전체 운영 기획·경계 정리 요청에 따라 작성한 개발 기준 제안이다. ChurchOS, 너랑나랑, 생명일기, JLPrayer, JLBible, JLAcademy, CHGO를 대상으로 한다. JLAcademy의 사용자 표시명은 JesusLife Academy로 대응한다. ChurchOS 최종 브랜드명은 미정이다. 지저스라이프 원은 내부 생태계 명칭으로만 사용한다.

2026-10-24 추가 지시를 반영했다. ChurchOS는 화이트라벨과 교회 기본 기능 및 제품 연결을 담당한다. Academy는 교회별 선택 서비스이며, 참여 교회의 교육 흐름에서 너랑나랑과 생명일기를 직접 연결한다. 특히 생명일기는 교육 이후 실천·나눔·코칭과 연결한다. CHGO는 모든 제품과 관계되는 독립 엔진으로 정의한다. 이 운영 방향은 사용자 지시이며, 아래 구체적인 연동 필드·권한·화면은 아직 구현 전이다.

이미 확정된 독립 개발·API 연결·ChurchOS 중심 앱 원칙은 유지한다. 이 문서에서 새로 제시하는 공유 범위·진도 제한·출시 순서·상품 운영은 운영 기획 제안이며 제공자 승인이나 구현 완료를 뜻하지 않는다. 다른 여섯 제품의 최신 코드와 정책은 아직 대조하지 않았다. 제품 간 계약 상태는 소비자 요구사항이며 실제 연동 검증은 미실행이다.

v2.6 패키지는 검증된 구현 스냅샷으로 그대로 보존한다. 이 문서는 그 후속 운영 설계다. 내용이 다른 항목은 아래 처분표를 통해 후속 계약·화면·스키마에 반영한다. 과거 마이그레이션을 수정하거나 기존 DB에 신규 계보를 섞지 않는다. 원본·감사·Git 이력·과거 검증 증거는 삭제하지 않는다.

확인 근거: v2.6 제품 정의, 통합 경계 계약, integrations.yaml, 화면 27개, OpenAPI, V001~V015, 서버 컨트롤러와 외부 상태 이벤트 스키마. 사용자 제공 실제 PostgreSQL 16.15/API 검사 63개 PASS 및 GitHub Actions 초록색 성공 화면은 v2.6에 대한 근거다. 이번 문서의 신규 운영 시나리오는 실제 실행 검증되지 않았다.

성경·찬송·설교·말씀 나눔지의 최신 경계는 [말씀 운영 설계 v1.2](WORD_AND_SERMONS.md)를 따른다. ChurchOS 내 성경·찬송 열람과 교회 설교 콘텐츠의 CHGO 처리를 추가한다. 개인 기록 금지 규칙은 유지한다.

## 1. 운영 목적

교회는 화이트라벨 ChurchOS에서 공지·일정·교인·소그룹·출석·후속 업무를 운영한다. 교회 기본 운영만 도입할 수 있으며 Academy 이용을 필수 조건으로 삼지 않는다. Academy를 선택한 교회에는 과정·개설반·모임과 너랑나랑·생명일기 활동이 연결되는 교육 운영 경로를 제공한다. 개인은 필요에 따라 전문 제품을 사용한다. ChurchOS 도입이 전문 제품 전체 가입이나 정보 공유 의무를 만들지 않는다. 전문 제품은 ChurchOS 없이도 자체 계정과 핵심 기능을 운영한다. 사용자 화면은 한국어를 기본으로 하며 국가·언어 확장은 제품별로 관리한다.

ChurchOS는 Flutter 앱 하나 안에서 역할별 화면을 제공한다. 관리자 웹을 초기 범위에 추가하지 않는다. 다른 제품으로의 앱 이동·설치 필요·복귀는 명확하게 안내한다. 모바일 환경별 안전한 앱 열기 방식은 실기기 검증 후 확정한다. 전문 제품의 핵심 기능을 ChurchOS에 복제하는 방식을 편의상 선택하지 않는다.

성공 기준은 교회 개설, 가입, 첫 공지 확인, 행사 참여, 담당자 업무 완료가 실제로 쉬워지는 것이다. 일기·기도·통독 횟수나 수료율을 개인의 영적 가치·성숙·사역 적합성 점수로 홍보하지 않는다.

## 5. 운영 시나리오

각 시나리오의 합격 조건은 앞으로 수행할 검증 기준이며 현재 PASS 기록이 아니다.

### S01. 교회 개설과 도입

주체: 교회 도입 담당자. 시작: ChurchOS 도입을 선택한다. 책임: ChurchOS.

1. 계정 인증 후 교회 개설을 요청한다. 교회 식별 정보와 관리 책임자를 등록한다.
2. 동일 이름의 기존 교회가 있으면 자동 병합하지 않고 소유·운영 권한 확인 절차로 보낸다. 확인 기준과 담당자는 도입 정책으로 정한다.
3. 교회명·로고·색·표시명을 설정하고 기본 홈을 미리 본다. 공용 앱/개별 교회 앱은 서로 다른 배포 방식으로 안내한다.
4. 관리자 역할을 부여하고 공지·일정·교인 가입 기능부터 활성화한다.
5. 전문 제품은 미연결이 기본이다. Academy는 교회가 별도로 선택한다. 미선택 교회의 기본 홈에는 수강·과제·일기 미작성 표시를 만들지 않는다. 교회 연결 설정과 개인의 제품 사용·공유 선택을 별도로 받는다.

실패/대안: 교회 확인 대기 중에는 임시 설정만 허용하고 정식 교회 명의의 공개 초대 발송을 제한한다. 로고 실패는 기본 이미지로 대체한다. 외부 제품 장애는 개설을 막지 않는다.

합격 조건: 전문 제품을 모두 끈 상태로 교회 개설→첫 공지 게시가 가능하다. 스플래시·로그인·메뉴에 내부 생태계 명칭이 나오지 않는다. 개별 교회 앱 배포를 즉시 완료로 표시하지 않는다.

### S02. 교회 가입과 첫 화면

주체: 새 교인. 시작: 교회 초대 링크 또는 교회 검색. 책임: ChurchOS.

1. ChurchOS를 열고 계정을 인증한다. 교회 가입 요청과 전문 앱 동의를 한 화면의 필수 동의로 묶지 않는다.
2. 초대의 교회·만료·재사용 정책을 확인하고 가입 요청을 만든다.
3. 교회 정책에 따라 승인 또는 승인 대기로 처리한다. 승인 대기자는 교인 전용 명단·자료를 보지 못한다.
4. 승인되면 해당 교회 홈에서 공지·일정·가입 가능한 공동체를 확인한다.
5. 선택한 전문 제품만 본인에게 연결 안내한다. 기존 개인 계정은 인증된 연결 절차로 확인한다. 이름·전화번호 일치만으로 계정을 합치지 않는다.

합격 조건: 가입 링크 재전송·중복 제출로 소속이 중복 생성되지 않는다. 거절·만료 상태에서 비공개 자료가 노출되지 않는다. 전문 제품 가입을 거절해도 기본 교회 생활을 사용할 수 있다.

### S03. 일상 공지·일정·출석

주체: 관리자와 교인. 책임: ChurchOS.

1. 관리자가 공지·행사를 초안으로 작성하고 검토 후 게시한다.

합격 조건: 동시 수정 충돌과 중복 제출을 처리한다. 타 교회 명단·출석은 보이지 않는다. 출석 이벤트를 성장 판정으로 변환하지 않는다. 출석·신청·정정 UI는 구현 후 실제 검증한다.

### S04. 새가족 연락·돌봄·봉사

주체: 담당 목회자/리더. 책임: ChurchOS.

합격 조건: 일기 작성량·기도 횟수·CHGO 개인 결과를 조회하거나 봉사 배치의 근거로 사용하지 않는다. 담당자 해제 후 업무 접근이 종료된다.

### S05. 너랑나랑 혼자하기·함께하기

주체: 개인 사용자. 시작: ChurchOS 연결 카드 또는 너랑나랑 직접 실행. 정본: 너랑나랑.

1. ChurchOS에서 선택한 경우 본인 요청으로 단회 앱 열기를 수행한다. 직접 실행이면 ChurchOS 소속을 요구하지 않는다.
2. 혼자하기/함께하기, 상대 이름과 실제 참여 계정의 구분, 상대 초대와 수락은 너랑나랑이 처리한다.
3. 문답·은혜 기록·서명·임시저장·복원·이력 관리를 너랑나랑에서 수행한다.
4. 사용자 요청이 있으면 ChurchOS로 복귀한다. 본인용 이어하기 참조만 제한적으로 갱신한다.
5. 교회 모임으로 운영해도 모임 참석과 관계 세션 완료를 분리한다.

실패/대안: 상대 초대 거절·만료·탈퇴는 너랑나랑이 처리한다. 교회 밖 상대도 별도 참여 정책을 따른다. 제품 미설치 시 설치/나중에 선택을 제공하고 ChurchOS로 돌아갈 수 있게 한다.

합격 조건: 목장 가입으로 세션이 자동 생성되지 않는다. 교회 리더가 개인 답변·서명·은혜 기록·진도표를 볼 수 없다. 교회 탈퇴가 개인 세션·기록 소유권을 변경하지 않는다.

### S06. 생명일기 작성·공유·코칭

3. 공유·코칭을 선택하면 생명일기에서 대상·범위·기간·철회 방식을 확인한다. 실제 제품 지원 범위를 대조하기 전 자동 공유를 만들지 않는다.
4. 교회가 모임을 운영하면 ChurchOS에는 일정과 참석만 기록한다.
5. 복귀 시 작성 성공 여부·회차·내용을 ChurchOS에 전송하지 않는다. 앱 이동 결과와 콘텐츠 활동 결과를 구분한다.

합격 조건: ChurchOS 상태 캐시·알림·통계·이벤트에 작성 여부가 남지 않는다. 보안 목적 앱 연결 로그도 활동 진도 추론에 사용하지 않으며 필요 최소 보유기간을 따로 정한다. 목회자 역할만으로 공유 대상이 되지 않는다.

### S07. 교회 기도회와 JLPrayer 캠페인

주체: 교회 행사 담당자·JLPrayer 캠페인 운영자·개인. 정본: 행사=ChurchOS, 기도 활동=JLPrayer.

5. 기도회에 출석해도 캠페인 참여·기도 완료가 자동 생성되지 않는다.

합격 조건: 교회 중보팀 역할이 기도방 접근권을 자동 부여하지 않는다. 비공개 기도제목·간증은 ChurchOS 공지나 감사 로그로 복사되지 않는다. 기도방 탈퇴와 교회 팀 탈퇴를 구분한다.

### S08. 공동체 성경통독

1. JLBible에서 계획·본문 범위·진도 정책을 설정한다.

3. 개인은 JLBible에서 읽기와 완료 처리를 수행한다. ChurchOS 본인 카드에는 허용된 오늘 읽기 참조·이어하기만 표시한다.
4. 본문이 다른 화면에 필요하면 라이선스가 허용한 제공 방식을 사용한다. 전문 제품 토큰을 URL에 실어 전달하지 않는다.
5. 공동체 진행률은 별도 집계·열람 계약이 없으면 관리자에게 제공하지 않는다.

합격 조건: ChurchOS에 별도 진도 원장이 생기지 않는다. 오프라인 읽기는 JLBible이 동기화 충돌을 처리한다. ChurchOS 행사 출석이 읽기 완료로 바뀌지 않는다.

### S09. JesusLife Academy 교육 운영

주체: Academy를 선택한 교회의 교육 담당자·강사·수강자. 정본: 교육 운영·학습=JLAcademy, 교회 현장 운영=ChurchOS.

선행조건: 교회가 Academy 도입을 선택하고 교육 운영자를 정한다. ChurchOS만 도입한 교회에는 이 경로를 요구하지 않는다. 개인의 수강·전문 제품 연결은 별도로 확인한다.

1. Academy에서 과정·차시·강사·수강 조건을 정한다. ChurchOS에서 교회의 교육 행사와 담당자를 정한다.
2. 행사 ID와 강좌/개설반/차시 참조를 API로 연결한다. 단순 제목 일치로 연결하지 않는다.
3. 행사 신청과 수강 등록은 각각 확정한다. Academy 등록 실패 시 '행사 신청 완료 / 수강 등록 미완료'로 구분해 재시도 안내한다.
4. 교실·현장 출석은 ChurchOS, 과제·평가·진도는 Academy에서 관리한다.
5. 출석을 수료 요건으로 사용할 경우 Academy가 허용된 운영 사실을 받고 자체 정책으로 수료를 판정한다. 수정된 출석의 정정 이벤트도 처리한다.
6. 강사는 Academy 권한으로 배정된 강좌만 조회한다. ChurchOS 관리자 역할을 자동 강사 권한으로 쓰지 않는다.

합격 조건: 같은 요청 재시도로 중복 수강·결제가 생기지 않는다. ChurchOS가 수료증을 독자 발급하지 않는다. 관리자용 수강 명단·수료 조회는 별도 목적·권한 계약 전까지 제공하지 않는다. 개인에게는 본인 상태를 제공할 수 있다.

### S10. 지저스라이프 16회 통합 프로그램

주체: Academy 참여 교회의 교육 책임자와 참여자. 교회 일정·출석 운영: ChurchOS. 교육 프로그램 총괄·과정·학습 정본: Academy. 너랑나랑과 생명일기 활동 정본: 각 제품.

1. Academy 과정과 ChurchOS의 16회 모임 일정을 연결한다. 차시와 현장 모임은 변경 가능한 참조로 매핑한다.
2. Academy는 차시별 너랑나랑 연결과 생명일기 실천·나눔 경로를 교육 계획에 직접 배치한다. 기도·성경 활동도 필요한 경우 연결한다. 각 활동의 이용·공유 범위를 별도로 안내하며 Academy 안에 문답·일기 편집기를 복제하지 않는다.
3. ChurchOS는 모임과 담당자 업무를 관리하고, 각 전문 제품은 자기 활동을 관리한다.
4. 프로그램 참가 신청만으로 개인 기록이 리더에게 공유되지 않는다. 필수 교육 요건이 있다면 등록 전에 Academy가 명시하고, 원문 제출 의무와 혼동하지 않는다.
5. 종료 시 ChurchOS는 모임 운영 결과, Academy는 수료 결과를 각각 확정한다. CHGO는 별도 허용 근거와 계약이 있을 때만 해석한다.

합격 조건: '출석 완료 / 학습 완료 / 개인 기록 / 성장 해석'이 서로 다른 상태로 유지된다. 전문 제품 하나가 미준비이면 해당 선택 활동을 비활성화해도 교회 모임 운영은 계속된다.

### S11. 공동체 운영 현황과 CHGO 엔진

주체: 권한 있는 목회자. 운영 통계 정본: ChurchOS. 성장 해석 정본: CHGO.

1. ChurchOS는 출석·행사·후속 업무 현황을 운영 지표로 집계한다.
2. CHGO는 ChurchOS만의 통계 부가 기능이 아니라 모든 제품과 연결되는 독립 엔진이다. 제품마다 개념 매핑·규칙·해석·집계 중 필요한 기능을 계약한다. ChurchOS의 공동체 집계 화면은 이 엔진 활용 중 하나다. ChurchOS가 전문 제품 원문을 모아 CHGO에 중계하지 않는다.
3. CHGO는 제공자별 적법한 권한·제품 정책·목적별 허용 범위에 따라 받은 근거만 해석한다. 입력 제공 범위는 별도 계약 전까지 없음으로 취급한다.
4. ChurchOS에는 허용된 공동체 집계만 전달한다. 집단·기간·표본·coverage·갱신 시각·억제 여부를 함께 표시한다.
5. 10명 미만 또는 차분·반복 질의로 개인 추정 가능성이 있는 결과는 억제한다. 이 기준은 최소 설계 조건이며 익명성 보장이 아니다.

합격 조건: 개인별 드릴다운·순위·성숙 점수·사역 자동 추천이 없다. 미연결·자료 부족·갱신 지연을 0점으로 표현하지 않는다. CHGO 장애 시 ChurchOS 운영 지표는 계속 작동한다.

### S12. 알림과 연결 실패

주체: 각 제품 운영자·사용자. 책임: 원래 사건의 소유 제품.

1. 교회 공지·행사 변경·담당 업무는 ChurchOS, 세션 초대는 너랑나랑, 일기 알림은 생명일기, 기도 알림은 JLPrayer, 읽기 알림은 JLBible, 학습·과제 알림은 Academy가 소유한다.
2. 전달 시스템을 공용화하더라도 알림 정본·수신 설정·발송 권한은 제품별로 분리한다.
3. 발송 중복 키는 source product + event ID + recipient + channel로 정하고 재시도를 중복 발송으로 만들지 않는다. 개인정보 원문은 잠금화면 알림에 넣지 않는다.
4. 교회가 강좌 일정을 바꾸면 일정 알림은 ChurchOS가 맡고, Academy는 강의 자료·과제 변경이 있을 때 자기 알림을 보낸다.
5. 외부 호출 실패는 timeout·재시도·명시적 지연 상태로 처리한다. 본인 카드에 갱신 시각을 표시하고 만료된 상태를 최신 완료처럼 표시하지 않는다.

합격 조건: 한 사건에 두 제품이 같은 알림을 보내지 않는다. 제품 연결 실패가 교인 등록·공지 저장 트랜잭션을 롤백하지 않는다. 계약과 발송 구현 전까지 '설계'로 표시한다.

### S13. 공유 철회·연결 해제

주체: 개인 사용자. 동의 정본: 각 전문 제품.

1. ChurchOS는 연결 현황과 제품별 동의 관리 진입점을 제공한다. 제품의 동의 원장을 복제하지 않는다.
2. 사용자가 상태 공유를 철회하면 해당 제공자가 정책을 갱신하고 ChurchOS는 후속 조회·상태 갱신을 중단한다.
3. 캐시·미사용 handoff를 무효화하고 이미 발급된 권한의 잔여 유효시간·차단 방식을 계약에 명시한다.
4. 공유 철회·제품 연결 해제·교회 탈퇴·제품 계정 삭제를 서로 다른 행동으로 설명한다.
5. 제품의 개인 원문 삭제는 해당 제품에서 처리한다. ChurchOS 연결 해제가 타 제품 원문 삭제를 명령하지 않는다.

합격 조건: 철회 후 새 handoff가 거부되고 앱 재시작·캐시 복원으로 상태가 다시 보이지 않는다. 이전에 전달된 기록과 백업·감사 보유 처리의 한계를 제품별로 설명한다.

### S14. 여러 교회 소속·교회 이동·역할 해제

주체: 개인·교회 관리자. 책임: ChurchOS 소속, 전문 제품의 개인 계정은 각 제품.

1. 사용자가 교회를 전환하면 활성 tenant를 바꾸고 교회별 역할·캐시·연결을 다시 검증한다.
2. 교회 탈퇴 또는 역할 해제 시 해당 교회의 권한을 중단하고 진행 중 요청도 재검증한다.
3. 전문 제품에서 교회 역할을 근거로 부여한 권한은 별도 연결 이벤트로 철회한다. 제품의 개인 사용 권한과 구분한다.
4. 새 교회에 과거 개인 기록·공유·통독·수강 정보를 자동 이관하지 않는다. 교회가 지불한 이용권 만료도 개인 기록의 교회 귀속을 뜻하지 않는다.
5. 교회 운영 기록의 보유·정정과 전문 제품 개인 기록의 보유·삭제는 각각 처리한다.

합격 조건: 이전 교회의 토큰·요청·캐시로 새 교회 데이터를 볼 수 없다. 동일인이 여러 교회에 있다는 이유로 개인정보가 교차 노출되지 않는다.

### S15. 교회 계약·이용권·해지

주체: 교회 계약 담당자·개인·상품 운영자. 상태: 운영 설계 제안, 가격·판매 방식 미확정.

1. ChurchOS 계약과 전문 제품 이용권을 구분해 안내한다. 묶음 상품을 판매해도 각 제품의 이용권 정본·지원 책임을 명시한다.
2. 교회가 구매한 좌석 배정과 개인 계정·기록을 분리한다. 교회 관리자는 이용권 배정에 필요한 정보만 본다.
3. 결제·환불·해지는 하나의 거래 책임 주체를 정한다. 여러 제품이 같은 주문을 각각 청구하지 않는다.
4. 이용권 만료 시 사용 제한·내보내기·보유·삭제 선택을 각 제품 정책으로 설명한다. 자동 원문 삭제를 기본으로 가정하지 않는다.

합격 조건: 계약 해지가 개인 원문을 교회에 넘기지 않는다. 중복 청구·중복 환불을 막는다. 상용화 전 국가별 판매·보유·동의 요구를 별도 확인한다.

### S16. 문의·장애·백업·종료

주체: 사용자·교회 운영자·제품별 지원자.

1. ChurchOS는 교회 운영과 앱 연결 문의를 접수하고, 전문 활동 문의는 담당 제품으로 안내한다.
2. 공유하는 진단 정보는 제품·오류 코드·시간·연결 추적 ID 등 최소 정보다. 원문·토큰을 붙여 보내지 않는다.
3. 각 제품은 자신의 DB·암호화·백업·복구·장애 공지를 책임진다. 공통 장애라도 데이터 정본을 하나로 합치지 않는다.
4. 복구 후 연결 권한·삭제/철회 상태·이벤트 중복을 재검증한다. 복원으로 철회된 권한이 되살아나면 안 된다.
5. 제품 종료 시 사용자 고지·내보내기·보유 종료·연결 해제는 담당 제품이 실행하고 ChurchOS는 연결을 제거한다.

합격 조건: 지원자가 개인 원문을 요구하지 않고도 기본 진단이 가능하다. 백업 복구와 제품 간 철회 재동기화를 실제 실행한 증거가 있어야 운영 완료로 판단한다.

### S17. Academy 참여 교회의 생명일기 실천·나눔 지속

주체: Academy 참여 교회의 교육 책임자·코치·작성자. 교육 계획: Academy. 개인 기록·공유·코칭: 생명일기. 교회 일정: ChurchOS.

1. 교회가 Academy를 선택하면 담당자가 과정·개설반·강사·참여자를 Academy에서 구성한다. ChurchOS 교인 명단 전체를 자동 수강 등록하지 않는다.
2. 교육 과정에서 너랑나랑 활동을 연결하고 생명일기 실천 시작 시점·안내·나눔 모임을 계획한다. 기존 16회 교육 후 주 1회 생명일기 실천·코칭 및 100회 1단계 운영 취지를 참고하되, 회차·진행 계산 정본은 생명일기에 둔다. 세부 프로그램 규칙은 교재와 기존 제품 정본 대조 후 확정한다.
3. Academy는 활동 목적·사용 안내·제품 연결을 제공한다. 생명일기 작성 화면·문항·회차 계산·원문 보관을 소유하지 않는다. 참여자는 생명일기에서 본인 계정으로 작성한다.
4. 공유·코칭을 원하면 생명일기에서 코치/나눔 상대·범위·기간을 정한다. Academy의 강사 배정이 생명일기 공유 권한을 자동 생성하지 않는다.
5. 나눔 모임 일정·장소·참석은 ChurchOS에서 관리하고 Academy에서는 교육 운영에 필요한 모임 참조만 사용한다. 생명일기 작성 여부·원문·회차는 ChurchOS에 보내지 않는다.
6. Academy에도 개별 작성 상태를 기본 전송하지 않는다. 수료 요건과 연동하려면 작성자가 선택한 확인 방식·최소 확인값·열람자·철회·보유기간을 별도 계약한다. 원문 제출이나 개인 영적 평가는 기본 요건으로 만들지 않는다.
7. 교육 수료 후에도 개인은 생명일기를 계속 사용하고 교회는 나눔 모임을 계속 운영할 수 있다. Academy 수강 종료와 생명일기 계정·기록·공유 기간을 각각 처리한다. 코치 권한도 본래 부여 근거와 기간을 재검증한다.

합격 조건: Academy 참여 교회에서 교육→실천 안내→생명일기→나눔 모임이 이어진다. 같은 계정 연결 요청을 반복해도 기록·수강이 중복되지 않는다. 교육 종료·이용권 해지로 일기가 자동 삭제되지 않는다. 직접적 교육 관계를 근거로 개인 원문이 중앙 수집되지 않는다.

### S18. 모든 제품의 CHGO 엔진 활용

주체: 각 제품 서비스와 CHGO 엔진 운영자. 개념·해석 정본: CHGO. 제품 업무 정본: 각 제품.

1. ChurchOS·너랑나랑·생명일기·JLPrayer·JLBible·Academy가 자신의 기능과 CHGO 개념·관계 ID의 대응을 명시한다. Academy를 사용하지 않는 교회·개인 제품에도 개념 관계가 성립한다.
2. 각 제품은 개념 조회, 허용된 근거 교환, 규칙/해석 결과, 공동체 집계 중 실제 필요한 capability만 선택한다. 개념 참조만 사용하는 제품에 개인 활동 전송을 요구하지 않는다.
3. 입력 필드·목적·권한·결과 열람자·보유·철회·버전을 제품별 계약으로 정한다. 모든 제품이 관련된다는 이유로 모든 데이터를 보내지 않는다. 원문·개인 식별 근거의 허용 여부는 별도 정본 정책과 계약 없이는 없음으로 취급한다.
4. 요청은 해당 제품에서 CHGO API로 직접 전달한다. ChurchOS가 여섯 제품의 필수 중계 서버나 원문 통합 저장소가 되지 않는다. CHGO의 접근 키와 업무 DB 권한도 분리한다.
5. 결과는 요청 제품과 승인된 대상에게만 반환한다. 너랑나랑/생명일기 관련 결과를 ChurchOS나 Academy에 자동 전달하지 않는다. 기존 승인된 정적 교환 계약이 있으면 그 범위를 우선 대조하고 확장하지 않는다.
6. 엔진 규칙·개념 버전·근거 범위·불확실성을 기록한다. 활동 횟수·수료를 성숙으로 자동 등치하지 않는다. 장애 시 해당 제품의 저장·읽기·교회 업무를 계속하고 해석 기능만 지연/불가로 표시한다.

합격 조건: 여섯 제품 모두 개념 매핑표를 갖는다. 실제 실행 연결은 제품별 증거로 판단한다. 허용되지 않은 필드를 거부하고, 결과의 제품 간 누출을 막는다. 엔진 장애·철회·규칙 버전 변경을 시험한다.

### S19. 교회 앱에서 성경과 찬송 사용

ChurchOS 말씀 메뉴에서 성경과 찬송을 열람한다. JLBible이 판본·콘텐츠·권리와 제공 범위를 관리하고, ChurchOS는 API 기반 뷰어를 제공한다. 통독계획·진도는 JLBible에서 처리한다. 열람을 통독 완료로 기록하지 않는다. 상세 절차와 실패·권리·캐시 검증은 [말씀 설계 S19](WORD_AND_SERMONS.md)를 따른다.

### S20. 담임목사 설교 등록과 제공

교회별 권한 있는 편집자·승인자가 설교 링크·원고·음성을 준비된 형식으로 등록하고 검토·게시한다. 링크만으로 내용을 추측해 요약하지 않는다. 음성 전사는 별도 작업으로 검토한다. 설교 정본과 공개범위는 ChurchOS가 소유한다. 상세 절차와 검증은 [말씀 설계 S20](WORD_AND_SERMONS.md)를 따른다.

### S21. CHGO 연계 설교 요약·말씀 나눔지

허용된 설교 원고/검토 전사 버전에 CHGO의 개념·근거 연결을 적용한다. 전사와 생성 어댑터를 별도로 두고 근거 있는 초안을 만든 후 목회자가 수정·승인해 게시한다. 개인 일기·기도·나눔 답변은 입력하지 않는다. 소스 변경·엔진 장애·재시도·승인 전 비노출 검증은 [말씀 설계 S21](WORD_AND_SERMONS.md)를 따른다.

## 6. 공통 연결 계약

| 항목 | 필수 규칙 |
|---|---|
| 계정 | issuer+subject 기반 연결, 이름·연락처로 자동 병합 금지, 제품별 audience |
| 소속 | ChurchOS tenant/membership과 제품별 계정/그룹 참조를 구분 |
| 참조 | product+resource kind+opaque ID+version으로 의미 지정, 타 DB 외래키·직접 SQL 금지 |
| Handoff | 단회·최대 10분·사용자/교회/제공자/기능 결속·등록된 복귀 주소·원토큰 로그 금지 |
| 상태 | 제공자×기능별 enum·본인 조회·만료·마지막 갱신·철회 처리. 범용 자유 문자열로 원문 우회 금지 |
| 운영 사실 | 출석 정정·행사 취소 등 원천 정본의 이벤트와 버전 전달, 수신 제품이 자신의 상태를 판정 |
| 이벤트 | schema version·event ID·시간·source·목적·중복 처리·서명·재전송 검증 |
| 장애 | timeout·재시도·격리·마지막 갱신 표시, 핵심 업무와 외부 호출 분리 |
| 로그 | 최소 행위 메타데이터, 개인 원문·비밀·원토큰·답안 금지 |
| 보유 | 상태 캐시·연결 보안 로그·이벤트·감사·백업의 기간과 삭제 책임을 구분해 계약 확정 |

수신이 허용된다는 것은 영구 보관이나 관리자 열람까지 허용한다는 뜻이 아니다. 초기 연동은 너랑나랑/JLPrayer/JLBible/Academy의 본인용 기능만 대상으로 하고, 생명일기/CHGO의 개인 상태는 받지 않는다. 관리자용 전문 활동 집계는 별도 계약 없이는 제공하지 않는다.

## 7. 지식·교육·성장 경계

성경 본문·번역본·인물/장소/연대는 JLBible, 교육과정·차시·학습목표는 Academy, 성장 개념·관계·해석은 CHGO가 소유하는 기준을 제안한다. 같은 '하나님 나라' 용어를 사용해도 본문 참조·교육 설명·성장 개념은 다른 레이어다. 제품별 ID를 유지하고 검토된 대응 관계와 버전을 연결한다. 기존 신학 정본 ID와 저작권 기준을 이 문서로 변경하지 않는다. Theology 등 외부 정본의 정의 권위는 별도 원본 규칙을 따른다.

| P2 | 준비된 전문 제품 하나만 연결 | 해당 제품의 계약·sandbox·동의·철회·복귀·장애 시험 |
| P3 | Academy 참여 교회 파일럿: 과정·교회 모임·너랑나랑·생명일기 실천 경로 연결 | 신청/수강·개인 공유·과정 종료 후 지속·권한 분리 시험 |
| P4 | 전 제품 CHGO 엔진 API를 준비된 범위부터 실행 연결, ChurchOS 공동체 집계는 별도 화면 | 제품별 입력/출력 계약·불허 데이터·장애·철회·집계 억제 시험 |
| P5 | 교회 파일럿·운영 전환 | 지원·복구·보유·스토어·교회 도입 지표 검증 |

P2 제공자는 실제 준비 상태를 보고 결정한다. 너랑나랑이나 생명일기부터 시작할 수 있으나, 현재 자료만으로 연동 준비 완료를 선언하지 않는다. CHGO의 전 제품 개념 매핑과 계약은 P0부터 설계한다. 실행 연결은 제품별 준비 상태에 맞춰 진행하며, CHGO 미완성은 ChurchOS 단독 파일럿의 차단 조건이 아니다. Academy 미선택은 CHGO 엔진 관계를 배제하는 조건이 아니다.

## 9. 추가 확정이 필요한 항목

1. 다른 여섯 제품 최신 코드·정본의 역할·공유·탈퇴 처리와 이번 제안의 차이.
2. 제품별 허용 capability/state enum, 본인 카드 표시 항목, TTL와 보유기간.
3. 교회 소유 확인·가입 승인·여러 교회 소속의 실제 정책과 담당자.
4. 교회 공동체와 전문 그룹, 교육 행사와 Academy 개설반/차시의 연결 계약.
5. 실제 OIDC 제공자·앱 설치/미설치·계정 복구·모바일 복귀 방식.
6. 통합 프로그램의 필수 학습 요건과 선택적 개인 기록 활동의 구분.
7. 알림 채널·제품별 발송 책임·수신 설정·지원 라우팅.
8. 판매·이용권·환불·종료 정책. 금액과 출시일은 이번에 임의 확정하지 않음.
9. CHGO 입력 근거별 제공 범위와 집계 억제 구현. 원문 중계를 전제로 삼지 않음.

## 10. 변경 기록

v1.2: ChurchOS 내 성경·찬송 열람, JLBible 통독 분리, 설교 링크/원고/음성·요약·나눔지 및 CHGO 개념/근거 처리 설계를 추가했다. S19~S21과 B17~B19를 추가해 총 21개 시나리오와 19개 경계 결정이다. 기능 구현·권리 확보·실행 검증은 미완료다.

### v1.1

- ChurchOS 화이트라벨·교회 기본 운영과 선택형 Academy를 명확히 구분했다.
- 교육 총괄을 Academy, 교회 일정·출석을 ChurchOS로 구분했다.
- Academy 참여 교회의 너랑나랑·생명일기, 특히 교육 이후 생명일기 실천 흐름을 직접 연결했다.
- CHGO를 전 제품과 관계되는 엔진으로 보완하고 설계는 초기부터, 실행은 제품별로 검증하도록 했다.
- S17/S18을 추가했다. 기존 16개를 포함해 총 18개다.

## 11. 이번에 실제 변경한 범위

새 운영 문서와 제품 경계 처분표를 추가하고 저장소 README에서 연결한다. v2.6 코드·DB·매니페스트·검증 증거·다른 제품 저장소는 변경하지 않는다. 위 처분표의 정책 삭제와 실제 데이터 삭제를 구분했다. 신규 문서의 시나리오 검증은 아직 실행하지 않았다. 원격 main 반영은 별도 Git 인증과 업로드가 필요하다.
