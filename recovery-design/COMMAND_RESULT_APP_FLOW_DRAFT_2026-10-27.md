# 일반 업무 처리 상태와 앱 안내 흐름

> 현재성 안내: 부분 합의·과거 제안·기술 초안을 구분합니다. [결정 색인](RECOVERY_DECISIONS.md)과 [현재 상태](../START_RECOVERY_CURRENT.md)을 함께 읽으세요. 상단 AGREED가 모든 기술 항목의 승인을 뜻하지 않습니다.

2026-10-27 / 결과 확인 우선·자동 재실행 금지 AGREED / 나머지 SCREEN_FLOW_DRAFT / 구현·실행 NOT_RUN

확정 근거: 사용자가 앱 기본 동작 확정 질문에 “네”로 동의했다. 결과 불명 시 결과 확인을 기본 동작으로 하고 앱 재시작 후에도 미확정 업무를 자동 재실행하지 않는다. 나머지 화면 문구·저장 기술·보유 기간·자동 조회 주기는 별도 검토 대상이다.

## 1. 범위와 기존 합의

누적 r11을 이어 작성한다. 기존 요청 동일성·서버 확정 순서·현재 권한 재검증·본인 최소 상태 조회 합의를 유지한다. 이번 문서는 앱 화면·문구·버튼의 신규 제안이다. 서버 API 상태명·코드와 지역 저장 기술·보유 기간은 아직 확정하지 않는다. 소실된 r7 전체 원문을 복구한 문서가 아니다. 기도·일기·문답·교육 원문의 오프라인 저장 정책을 변경하지 않는다.

|---|---|---|---|
| 입력 중·연결됨 | 내용을 확인한 뒤 저장해주세요. | 유효한 현재 권한 확인 후 저장 | 이전 화면 권한만으로 허용 |

존재·만료·다른 계정·다른 교회 등 비공개 원인을 구분하는 문구를 제공하지 않는다. 세부 원인을 보여줄 수 있는 경우와 문구는 계약 검토 후 확정한다.

## 3. 제출과 결과 확인

1. 저장은 한 업무 의도에 대해 요청 식별자를 하나만 만든다. 버튼을 비활성화하는 UX와 서버 중복 방지를 함께 설계한다.
2. 서버의 업무 확정 성공을 확인하기 전까지 ‘완료’로 표시하지 않는다. 접수·대기·알림 수신·화면 닫기는 성공 근거가 아니다.
3. 응답 단절 후 기본 버튼은 ‘결과 확인’이다. 연결을 회복해 같은 계정·교회에서 같은 요청 상태를 확인한다.
4. 서버가 요청을 찾지 못했다는 응답만으로 미실행을 단정하지 않는다. 인증 문제·상태 조회 만료·복구 중·기록 보유 한계가 원인일 수 있다. 안전하게 미실행이 판별되기 전에는 새 요청으로 자동 저장하지 않는다.
5. 거절이 최종 확정됐을 때만 수정 가능한 화면으로 돌아간다. 사용자 수정·최신 버전 확인 후 새 업무 의도로 제출한다. 같은 식별자에 변경 내용을 보내지 않는다.
6. ‘화면 닫기’는 UI 이동이다. 이미 서버로 보낸 업무를 취소하거나 권한을 해제하지 않는다. 별도 취소 가능한 업무라면 현재 권한으로 별도 계약을 따른다.

## 4. 앱 종료·재시작

권장안: 제출된 요청의 결과 확인을 이어가기 위해 계정·교회에 묶인 최소 확인용 참조만 보호된 기기 저장소에 남긴다. 참조 후보는 요청 식별자·소유 계정 참조·교회 참조·API 계약 버전이다. 이름·기도·일기·변경 값·전체 요청 본문·인증 토큰을 확인 기록에 넣지 않는다.

이 기록은 오프라인 실행 대기열이나 관리자 원문 캐시가 아니다. 앱 재시작 때 쓰기를 자동 재전송하지 않고, 연결·재인증·현재 소속 검증 후 최소 상태 조회만 수행한다. 자동 조회 간격·배터리·망 사용·재시도 횟수는 후속 명세다.

저장 기술·암호화·백업 제외·보유 상한은 OPEN이다. 로그아웃/다른 계정 전환 제거는 REC-028을 따른다. 이 계약을 정하기 전 기기 영구 저장 구현을 시작하지 않는다. 기기 기록이 사라졌다고 서버 업무가 미실행인 것은 아니다. 기록 손실에 대한 앱은 자동 재실행 대신 현재 권한으로 자료 확인·수동 확인 경로를 제공해야 한다.

## 5. 교회 전환·로그아웃·소속 변경

| 사건 | 화면과 요청 처리 |
|---|---|
| 교회 전환 | 이전 교회의 상세 화면·결과 문구를 새 교회에 노출하지 않는다. 전환 자체로 이미 제출한 서버 요청을 취소하지 않는다. 이전 교회로 돌아오면 그 교회 현재 권한으로 확인한다. |
| 로그아웃·계정 변경 | 개인·교회 보호 화면과 확인 기록 접근을 차단한다. 다른 계정으로 동일 요청을 조회하지 않는다. 명시적 로그아웃/다른 계정 전환의 기기 참조 제거는 REC-028로 합의됐다. 보유 상한·저장 기술·정리 실패는 미결이다. |
| 일반 업무 권한만 종료 | 계정·교회 소속이 유효하면 본인 요청의 허용된 최소 상태만 조회한다. 원문이나 대상 명단을 열어주지 않는다. |
| 계정·교회 소속 상실 또는 확인 불가 | 요청 존재·상태를 표시하지 않는다. 이전 캐시의 완료 여부도 자동 재표시하지 않는다. |
| 최종 상태 확인 168시간 만료 | 최소 상태 화면 재공개를 차단한다. 업무 데이터·감사·중복 방지 기록 삭제와 별개다. |

## 6. 접근성과 운영 안내

색상이나 회전 표시만으로 상태를 설명하지 않는다. 처리 중·확인 필요·완료를 텍스트와 보조기기 읽기 순서로 구분한다. 반복 조회 때 동일 상태 안내를 과도하게 반복하지 않는 방안을 설계한다.

수동 확인 이관은 기존 합의대로 최초 서버 실패·결과 불명·비정상 정체부터 해결되지 않으면 24시간 이내이며 복구 보장 시간이 아니다. 단순히 앱을 닫았다는 이유로 장애를 생성하지 않는다. 실제 담당자·연락 경로·정체 판정 임계값은 미결이다. 문의·알림에는 원문·변경 값·토큰을 넣지 않는다. 보안 이상은 즉시 조사한다.

## 7. 화면 수용 조건 — 실행한 테스트 아님

- 저장 연타와 화면 재진입으로 요청 식별자가 바뀌거나 중복 업무가 생성되지 않는다.
- 서버 성공 응답 유실 후 ‘결과 확인’으로 같은 요청을 조회한다.
- 앱 종료·재시작 후 미확정 요청을 자동으로 새 쓰기로 제출하지 않는다.
- 교회 전환 후 이전 교회 요청의 존재·자료가 새 교회 화면에 나타나지 않는다.
- 권한 종료 후 본인 최소 상태와 업무 상세 접근을 구분한다.
- 계정·소속 상실 시 이전 확인 결과를 재공개하지 않는다.
- 조회 만료·미존재 안내로 미실행을 단정하지 않는다.
- 화면 닫기를 서버 취소로 안내하지 않는다.

## 8. 확정 질문과 답변

앱에서 결과가 불명확할 때 ‘다시 저장’ 대신 ‘결과 확인’을 기본 동작으로 하고, 앱을 재시작해도 미확정 업무를 자동 재실행하지 않는 안내 방식으로 정할까요?

답변: 네. 2026-10-27 앱 기본 동작 설계 합의.

이 질문은 앱의 기본 동작에 한정한다. 기기 저장소·보유 기간·자동 조회 주기·문의 운영자·API 세부 규격 전체를 승인하는 것은 아니다.

## r28 연결 계약 참고

[송신 전 기기 참조와 서버 확인 ID](SUBMISSION_RECEIPT_BINDING_DRAFT.md)를 함께 적용한다. 서버 확인 ID가 없는 응답 유실은 새 쓰기나 새 키 발급으로 해결하지 않는다. 연결 ID·정확한 경로 범위·영속 접수·읽기 연결의 구체 방식은 DRAFT다. 다섯 공개 항목 합의에 기기 내부 필드를 추가 공개하지 않는다.
