# 변경 명령의 입력→판정→반영→감사→실패 계약

2026-10-30 / r94 / TECHNICAL_CONTRACT_DRAFT / PARTIAL_RECOVERY / 실행 NOT_RUN

## 범위와 읽는 법

[r93 권한/이행표](LEADER_INTRO_LEAST_PRIVILEGE_TRANSITION_DRAFT.md)의 PM01~08을 [현재권한/경합 후보](LEADER_INTRO_STORAGE_VERSION_RACE_DRAFT.md), [모델/실패표](LEADER_INTRO_MODEL_COMMIT_FAILURE_DRAFT.md), [결과조회 초안](LEADER_INTRO_RESULT_QUERY_APP_DRAFT.md)에 연결한다. PM09~12는 기존API/멱등/감사/미디어 지원경계로 함께 표시한다. 정책 근거는 [기존 COS/REC 결정](RECOVERY_DECISIONS.md)이며 새권한/기간/개인자료수집을 승인하지 않는다.

명령 CMND 식별자는 문서추적용이며 실행함수명/URL/역할코드/DB상태 enum이 아니다. 아래 입력은 의미단위 후보다. 정확한 스키마/오류코드/트랜잭션·LP-A/B/H 선정은 미결이며 코드를 만들지 않았다.

## 모든 변경 명령의 공통 입출력 경계

클라이언트는 대상참조·해당행위의 기대버전/확인참조·허용변경값·기존멱등키를 전달하는 후보로 설계한다. 서버는 검증된 principal/현재계정·선택교회/목적·정본본인소속·현재권한을 수립한다. 본문 actor/tenant/role/approved=true 같은 값을 권한증거로 믿지 않는다. 개인연락처/동의원문/토큰/사진바이트를 업무감사나 요청결과에 복제하지 않는다.

참조 존재→같은교회/공동체/본인관계→해당행위 권한→현재자격/기간/상태→기대버전/확인묶음→멱등성/일관성 경계를 대조하되 비인가 대상 존재를 누출하지 않는 순서/응답을 따로 설계한다. 이 개념순서는 실제락 획득순서가 아니다. 잠금대기 후 현재조건을 다시 확인하고 성공확정 직전까지 구작업/철회와 일관성을 확보해야 한다.

## 구현 전 대조/검증 조건

CMND01~12의 권한은 PM01~12·LP/MP 이행표 및 기존 COS/REC와 대조한다. 함수내 현재검사만 넣고 원본직접DML/다른배치/복원 쓰기를 방치하지 않으며 공통보호후보S의 전경로/실효권한 검증이 필요하다. 기존notice/event API·Idempotency-Key/If-Match/24h재생·만료409는 보존한다. 신규소개/조회/후속을 실제구현으로 표시하지 않는다.

CA141: 본인소개 편집/게시/철회/사진제어와 원본관리/역할/인증연결의 입력·권한·반영을 섞지 않고 관리자제안이 직접변경/공개로 이어지지 않는지 확인할 조건.

CA142: 상태변경/업무감사/결과 확정의 일관성, 거절관측/롤백된감사/커밋불명의 구분과 민감원문 비복제를 확인할 조건. 실제테스트·트리거/함수·앱/API/DB/연동 실행은 모두 NOT_RUN이다.

## 미결과 다음 작업

새권한/새동의기간/보유를 정하지 않았다. 관리행위별담당·철회접근자격·표시이름정본/정정·LD03 재시도/후속조회·실제시각/기한·거절관측/보유·LP/C-A 최종선정은 미결이다. 다음은 이 명령표의 미결을 기본MVP 필수/후속설계/출시전 검증으로 분류해, 개발진입을 막는 조건과 독립적으로 진행할 설계작업을 정리하는 단계다. 분류만으로 구현/운영 완료로 승격하지 않는다.
