# 동의·게시 확정 방식의 기술 권장안 후보

2026-10-30 / r89 / RECOMMENDATION_DRAFT / PARTIAL_RECOVERY / 실행 NOT_RUN

## 결론의 범위

[최소모델/실패표](LEADER_INTRO_MODEL_COMMIT_FAILURE_DRAFT.md)의 C-A/C-B를 [재시도 동일성](LEADER_INTRO_RETRY_IDENTITY_DRAFT.md) 및 [조회/앱 계약](LEADER_INTRO_RESULT_QUERY_APP_DRAFT.md)과 대조했다. 새 동의와 ‘동의하고 공개 반영’의 결합 실행에는 C-A(동의·게시 함께 확정)를 조건부 우선 기술검토 대상으로 권장한다. 동의 원본과 게시 데이터가 같은 일관성 경계에 있고, 현재 자격/철회/사진차단을 최종쓰기까지 보호하며, 감사/영수증/결과를 함께 확정할 수 있다는 전제다. 이 전제는 아직 실행 검증되지 않았다.

기술 권장과 사용자 정책 합의/최종 아키텍처 선정/구현을 구분한다. 새 REC를 추가하지 않는다. ChurchOS 소개 동의를 공통 인증 Core나 다른 제품 동의로 이전하는 제안이 아니다. 기존 동의·확정실패 재시도 합의는 그대로 유지한다.

## 먼저 세 경로를 구분

| 경로 | 동의의 출처 | 게시 실패 시 해석 | 재시도 경계 |
|---|---|---|---|
| P1 철회 후 새동의+명시게시 | 이번 본인확인/새동의 | C-A 명확롤백이면 이번 새동의/게시 모두 미반영 | 과거철회 동의가 유효하게 남았다고 안내 금지; 새확인/동의 UX 세부 OPEN |
| P2 현재 유효동의 아래 내용 게시 | 실제 남아있는 유효동의와 이번 확인버전/대상 | 이번 게시롤백이 기존 유효동의를 자동철회하는 것은 아님 | REC-073 전제가 실제로 확인되고 동일조건 유효할 때만 본인 명시 재시도 |
| P3 C-B 새동의 먼저 저장 후 게시 | 별도확정된 새동의 | 동의저장 성공/게시미반영이 증명되면 분리안내 | 현재동의/조건 재검증·본인 재시도; 후보B 의도/키 계약 미해결 |

P2가 항상 존재한다고 가정하지 않는다. 기존 동의가 해당 내용/대상을 포괄하는지, 바뀐 내용에 다시 동의가 필요한지의 적용 규칙은 OPEN이다. P1의 롤백된 새동의를 P2의 유효동의로 분류해 체크박스를 생략하지 않는다. 같은 조건에서 본인재시도 허용이라는 합의가 C-B 분리 저장을 강제하지 않는 이유다.

## C-A를 우선 검토할 조건

현재 요청접수 후보 TxA와 동의/게시확정 C-A는 다른 축이다. TxA 내구접수를 도입하더라도 그 자체를 동의/게시 성공으로 표시하지 않는다. C-A의 업무확정 후보 안에서는 이번 새동의 증거·공개버전/사진조건·최소감사·영수증/최종결과를 일관되게 반영해야 한다. 하나라도 실패했는데 업무 성공만 남기는 우회를 두지 않는다.

같은 DB에 저장된다는 사실만으로 자격변경/철회/자연만료와의 원자성이 증명되지는 않는다. 현재 소속/지정/동의/대상 버전·사진차단세대 검사와 갱신이 충돌할 때 허용 확정순서를 명시하고 실패주입으로 확인해야 한다. 외부 계정정지 최신성·커밋시각 증명도 별도 게이트다.

정확한 트랜잭션/락 순서·시계·조건부쓰기·복구 및 outbox 필요여부는 미선정이다. 성공 뒤 알림/캐시전파 실패는 게시 롤백이라고 재분류하지 않는다. 외부전파 장애가 실제 공개 노출과 차단보장에 미치는 영향은 분리 표시한다.

## C-B를 다시 검토해야 하는 조건

동의를 게시와 독립적으로 미리 저장해야 하는 실제 제품 요구가 별도 합의되거나, 동의 원본이 별도 저장소/서비스에 있어 같은 확정단위에 묶을 수 없다는 근거가 있다면 C-B를 검토한다. 현재 자료만으로 그런 필수요구/분리 저장소가 확인됐다고 주장하지 않는다. 단순히 구현이 편하다는 이유나 단일화면이라는 이유만으로 선정하지 않는다.

C-B라면 동의확정/게시확정 각각의 근거, 중간철회/직함종료, 부분성공 표시, 미확정 조사, 원문/증빙 보유, 재시도 식별을 함께 정해야 한다. 외부 동의서비스가 있다고 가정해 제품 경계를 변경하지 않는다. 동의를 저장하고 게시를 자동 재개하는 큐는 REC-071의 본인 명시 의사와 충돌할 수 있어 자동 도입하지 않는다.

## 재시도/실패 증거의 공통 게이트

P2/P3 모두 기존 요청의 확정 실패가 검증되고 옛 실행자가 더이상 커밋하지 못해야 한다. 실패 예외/타임아웃/404/만료로 대체하지 않는다. 기존 실패를 보존한 후속 명시 의도 후보는 여전히 REC-026과 키 의미의 호환 결정을 필요로 한다. 이 문서가 후보B를 승인하거나 새키 발급/후속관계 공개를 확정하지 않는다.

P1/C-A 명확롤백 뒤 같은 본인확인/동의 입력을 다시 제출할 때 확인란을 새로 눌러야 하는지 등 구체UX는 아직 OPEN이다. 서버가 저장하지 않은 동의를 저장됐다고 표시하는 것은 금지한다. 커밋불명이면 P1/P2/P3 모두 기존 요청 결과와 현재공개 조회를 우선하며 새쓰기 자동실행을 하지 않는다.

## 기술 후보 선정에 필요한 증거

| 게이트 | 요구 산출물 | 현재 상태 |
|---|---|---|
| CG01 | 동의/게시/감사/영수증/결과 실제 저장경계와 기존 DB계보 차이 | 미작성/NOT_RUN |
| CG02 | 철회/직함종료/사진차단과 게시의 현재검증·충돌순서·시간 경계 | 후보만/NOT_RUN |
| CG03 | P1 롤백·P2 유효동의 실패·P3 부분성공·COMMIT불명 판정 근거 | 인계조건만/NOT_RUN |
| CG04 | 기존키/후속명시의도·결과조회/관계응답/기간 호환 | LD03~05 OPEN |
| CG05 | 미디어/캐시/복원 최신철회·감사 최소화·보유 | LD06/LO02 OPEN |

CA131: P1 명확롤백을 동의저장 성공으로 표시하지 않고, P2/P3만 실제유효동의·확정실패에 재동의 생략을 적용하는 조건.

CA132: 동의/게시 커밋불명·철회경합·캐시전파실패를 구분하고 단일트랜잭션/한화면을 근거로 실행/노출 성공을 단정하지 않는 조건. 실행 검증은 모두 NOT_RUN이다.
