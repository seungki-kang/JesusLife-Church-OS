# M1 본인 소개 철회 명령 — 통합 계약 초안

2026-10-31 / r149 / COMMAND_CONTRACT_DRAFT / PARTIAL_RECOVERY / 실제 실행 NOT_RUN

[REC092 설계 방향](LEADER_INTRO_M1_DIRECTION_AGREED_HANDOFF.md), [REC091 근거](LEADER_INTRO_DURABLE_EVIDENCE_AGREED_HANDOFF.md), [r125 식별 역할](LEADER_INTRO_WITHDRAWAL_REQUEST_BINDING_DRAFT.md), [REC 원문](RECOVERY_DECISIONS.md)을 잇는다. M1 방향은 합의됐지만 아래 입력/분기/저장 방식은 초안이다. 소개 동의 한 세대의 본인 철회 명령에 한정한다. 새 API/테이블/권한을 구현하지 않았다.

## 입력과 신뢰 경계

| 논리 입력 | 서버 판정 | 금지 |
|---|---|---|
| 현재 공통 계정 인증 | 유효 계정 본인·명령 목적과 현재 자격 | 본문 actor/과거 토큰/이메일 일치로 대체 |
| 확인한 철회 대상과 동의 세대 T | 해당 본인과 그 세대의 관계·명시 철회 범위 | 이름으로 최신 동의 재결속·전체 철회 추정 |
| 기존 의도/멱등 참조 I/K | 고정 입력 의미·현재 본인·경로/교회/세대 범위의 결속 | 동일 키 변경 입력·새 키 자동 재실행 |
| 필요한 경합 참조/버전 | 실제 현재 대상과 충돌 조건 | 오래된 화면 버전으로 새 동의 철회 |

입력 필드명·정규화·I/K 동일성·서버 참조 발급 방식은 미선정이다. 소개 원문/사진·탈퇴 사유·타제품 기록을 요청 본문에 요구하지 않는다. 교회 범위는 대상 결속의 일부이며, 교회 전환 상태만으로 다른 교회의 요청으로 바뀌지 않는다. 계정 정지/탈퇴 예외는 OPEN이고 유효 계정 본인 원칙을 임의 확장하지 않는다.

| WC02 요청 결속 | 본인·I/K·T·고정 입력 대조 | 변경 입력/범위 충돌 차단; 기존 결과를 읽는 경로는 쓰기 재실행 아님 |
| WC03 확정 직전 현재 판정 | 본인 철회권·대상 세대·현재 상태·동시 변경 대조 | 소속/직함 종료만으로 재가입·관리자 승인 요구하지 않음; 새 동의로 바꿔 실행 금지 |

| WC06 최소 응답 | REC090 상한·현재 권한/조회 창 검증 | 응답 유실로 재실행하지 않음; 미검증 시각 생성 금지 |

WC04 내부의 실제 잠금·제약·DML/함수·감사 실패 처리·현재 권한 회수와의 직렬화 지점은 상세 기술 설계가 필요하다. 요청 시작 때만 권한을 검사하고 확정 때의 경합을 방치하지 않는다. 기존 관리자의 일반 쓰기 역할이나 tenant RLS만으로 본인 목적 검증을 대체하지 않는다.

## 상태·중복 판정표

| 서버에서 검증된 조건 | 계약상 처리 후보 | 남는 미결 |
|---|---|---|
| 해당 세대가 유효하고 명시 철회권 확인 | 효력 변경과 결과/감사 원자 확정 | 실제 권한/경합·저장 경계 |
| 같은 요청의 최종 근거가 있고 입력 일치 | 현재 권한과 유효 창에서 원래 결과 확인; 업무 재실행 안 함 | 기존 replay 계약과 조회 계약 분리/호환 |
| 같은 키인데 입력/대상 세대 다름 | 충돌 차단 | 외부 오류 코드·안내 |
| 같은 세대가 이미 철회됐고 이 요청 결과는 없음 | 아래 분리 후보 심사; 과거 실행 성공으로 소급 금지 | 새 요청 결과의 의미/저장/시각 |
| 이전 세대 요청인데 새 세대가 공개됨 | 새 세대 변경 금지; 명시적 새 확인·동의 계약 필요 | 과거 요청의 한정 결과 분류 |
| 현재 상태만 있고 요청 근거 없음 | 과거 결과 미입증 | 유한 확인/종결·근거 수명 |
| 키/결과 기록 만료·소실 | 부재로 미실행 추정 금지 | 옛 실행 보호와 정리 계약 |

### 이미 철회된 같은 세대 — 추천 후보

현재 본인/같은 세대 관계가 검증되고 이미 철회 상태라면 **추가 효력 변경 없이 이미 철회됨을 확인하는 별도 결과 의미**를 권고한다. 이 요청이 원래 철회를 실행했다고 표시하지 않는다. 그 확인을 새 요청의 내구 결과로 남길지, 별도 읽기 안내로만 둘지와 시각은 OPEN이다. 읽기 안내를 최종 업무 결과인 것처럼 기록하지 않는다. 새 동의 세대를 함께 철회하거나 옛 동의를 복원하지 않는다. 추천 후보이며 사용자 합의가 아니다.

## 거절과 실패를 분리

인증/형식/본인 관계를 확인하지 못한 요청은 타인의 업무 결과를 생성·공개하지 않는다. 관계가 검증된 요청의 최종 업무 거절을 내구 저장하려면 허용 사유·최소 기록·그 판정의 확정 경계를 별도로 설계해야 한다. 모든 예외를 성공 영수증처럼 보존하지 않는다. 업무 변경을 롤백하면서 조회용 거절 결과만 남겨야 한다면 원자성·권한·경합을 검토하고 별도 선접수 구조로 바뀌는지 확인해야 한다.

연결 종료·시간 초과·COMMIT 결과 불명은 일반 최종 거절이 아니다. 해당 I/K/R/T에 연결한 근거 확인을 먼저 하며 참조 전부 소실은 제한 재발견/지원 경계로 처리한다. 미확정 조회 종료·확인 불가 종결·재검토 개시는 각각 REC087~089에 따르고 철회 실패를 만들어내지 않는다.

## 최소 근거·시간·수명

내부 근거 후보는 요청/대상 세대 결속·결과 의미·필요한 업무 버전·감사 참조·검증된 사건 시각이다. 이것이 새 공개 필드 목록은 아니다. REC090 상한을 유지한다. created_at·트랜잭션 시작·기기 전송·사후 발견 시각을 실제 확정 시각으로 이름만 바꾸지 않는다. 조회 기산/숫자·최소 기록 수명·중복 방지 수명·삭제/백업·복원 보호는 여전히 미결이다.

## 검증 인계

정상 철회·동일 요청 동시 전송·다른 키 같은 대상·입력 변경·철회 직전 새 동의·계정 회수와 경합·감사/결과 저장 실패·COMMIT 응답 유실·기기 참조 소실·시각 불명·키 정리 후 옛 요청·복원 후 재생을 검증해야 한다. 특히 서로 다른 요청의 상태 확인과 과거 요청 실행 증명이 혼동되지 않아야 한다. 기존 CA144/159~162 세부 인계이며 새 시나리오/성공 수를 추가하지 않는다. 전부 NOT_RUN.

다음 좁은 결정은 **같은 세대가 이미 철회된 경우, 추가 효력 변경 없이 이미 철회된 상태를 구분하여 안내하고 이 요청의 과거 실행 성공으로 소급하지 않는 원칙**이다. 구체 상태명·내구 결과 저장·시각은 별도 결정한다.
