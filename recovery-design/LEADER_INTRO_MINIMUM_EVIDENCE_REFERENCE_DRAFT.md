# 동의·철회·명칭 최소 증빙의 필드·정본·삭제 의존관계 초안

2026-10-30 / r112 / TECHNICAL_CONTRACT_DRAFT / PARTIAL_RECOVERY / 실행 NOT_RUN

## 범위와 합의 유지

[REC-082 목적분리](RECOVERY_DECISIONS.md#rec-082-개인-소개자료교회-운영-이력최소-증빙의-목적-분리), [r109 LR02/03/10/12·RP02/04/05](LEADER_INTRO_SUPPORT_RECORD_RETENTION_COMPARISON.md), [r110 분류초안](LEADER_INTRO_CONTENT_CLASSIFICATION_DELETION_DRAFT.md), [r108 통합인계](LEADER_INTRO_WITHDRAWAL_SUPPORT_CONSOLIDATED_HANDOFF.md)를 잇는다. 본문은 논리 기록/API 설계 후보이며 실제 테이블·새 권한·보유기간 합의가 아니다. 기존 REC001~082와 canonical 구현은 수정하지 않는다.

최소 증빙은 ‘누가 어떤 범위에 어떤 조건으로 동의/철회했는가’를 필요한 한도에서 연결한다. 소개 전문/사진을 감사 기록으로 복제하지 않는다. 원문 없는 증빙으로 실제 어떤 개인 문구가 있었는지 완전히 재구성할 수 있다고 약속하지 않는다. 증거의 한계와 필요 목적을 함께 정해야 한다.

금지 필드는 소개 전문/일부 인용·사진바이트/썸네일/URL·연락처·신분증/서명 이미지·토큰/세션비밀·전체요청응답·다른 교인/수신자 명단·개인 신앙/관계 평가다. 공동체 기도·일기·코칭 원문과 생명일기 작성 상태도 받지 않는다. 당시 조직명은 허용 후보의 예외 목적이지만 개인 소개 원문을 다시 저장하는 통로가 아니다.

원문 해시를 추가한다면 필요성·충돌/변조·추측공격·키관리·수명·삭제후검증 한계를 먼저 검토한다. 해시가 동의 의사나 증거 완전성·익명성을 보장하지 않는다. 현재 계약은 원문해시 필수수집/영구보관·특정암호방식 채택을 확정하지 않는다.

정책문구 버전은 그 버전의 실제 고정 조건을 확인할 수 있어야 의미가 있다. 안내 문구가 변경됐는데 같은 버전참조가 다른 조건을 가리키지 않도록 버전 관리가 필요하다. 정책문구 정본에 개인 소개/이름/사진을 섞지 않는다. 당시 조건 문구 보존과 본인 동의 증빙 수명은 서로 다른 목적이다.

## 사건의 사실과 종결 구분

동의확정·철회확정·공개차단·담당확인완료·삭제완료·백업만료·목적별종결은 각각의 사건이다. 예: ‘철회 서버확정’은 EV02의 사실이지만 모든캐시 회수/원문삭제/백업만료 완료는 아니다. 한 전역 DONE 상태로 바꾸어 모든증빙의 보유기산을 통일하지 않는다.

| 종결 후보 | 필요한 판단 | 종결로 대체할 수 없는 것 |
|---|---|---|
| 대상추가확인 건 | 필요한관계확인/본인안내·남은정정/이의/통지실패 계약 | 담당자확인 버튼·본인철회명령 성공 |
| 원문삭제 작업 | 대상사본/파생/유효예외·실제운영본삭제·해당백업 처리 | 삭제요청202·큐비움·일부사본삭제 |
| 증빙 목적 | 유효이용/분쟁/정정/실행보호·보유근거와마감 | 원문삭제·직함종료·일반조회창 만료 |
| 복원/재실행 보호 | 남은백업/복원경로·지연작업/키재사용·필요사본계보 | 현재서비스에 원문이 없다는 사실·기기참조삭제 |

이 표는 종결 판정 입력의 초안이지, 모든 이의 가능성이 없어질 때까지 무기한 보관하라는 규칙이 아니다. 목적·상한·예외승인·장기미해결 처리·실제종결자격을 RP02/03/05로 정해야 한다. 기존 종료최소이력의1년을 소개철회/명칭증빙 전체에 자동 적용하지 않는다.

## 원문/명칭 삭제 전후의 의존관계

1. 원문/사진은 개인자료로, 업무이력/최소동의증빙은 별도목적으로 분류한다. 같은행/FK라는 이유로 원문삭제를 막거나 전부cascade삭제하지 않는다.
2. 원문 정리 후 확인버전 참조가 끊겨도 옛요청을 새소개·새동의에 붙이지 않는다. 필요한 최소의 사건/세대 결속만 남길 근거/수명을 설계하고 원문을 복구하지 않는다.
3. 당시명칭은 본인 대상선택 목적의 필요한 최소범위에서만 사용한다. 그수명이 끝나 삭제됐을 때 관계참조만으로 본인이 대상을 식별할 수 있는지 검토한다. 불가능하면 현재명칭을 당시명칭처럼 만들어 보여주거나 원문/백업을 복원하지 않고 제한확인 계약으로 연결한다.
4. EV02의 철회와 EV05의 차단근거를 지우기 전에 남은백업·미처리작업·재시도/옛키·복원공개 경로를 평가한다. 보존필요성과 최소필드·최종삭제시점을 함께 정한다. 안전검토를 무기한보관의 포괄근거로 쓰지 않는다.
5. 복원은 격리상태에서 최신삭제/동의철회/직함종료/담당회수/세대·실행확정 상태를 재적용한다. 필요한현재근거가 없으면 공개/권한활성화를 보류한다. 옛동의증빙만으로 소개나담당권한을 복원하지 않는다.

기술후보로는 원문에 대한 필수물리FK와 증빙 최소논리참조를 구분하고 삭제후참조를 안전하게 판정하는 모델을 비교한다. 구체FK/ON DELETE/파티션/토큰/SQL·마이그레이션은 미선정이다. canonical V001~V015를 수정하거나 실제 DDL을 실행하지 않는다.

## 실패/정정과 남은 선택

EV02 철회 확정 결과가 유실되면 기존 요청 결과와 현재상태를 조회한다. 404/만료/명칭없음/참조없음은 철회실패·미실행·완전삭제의 증거가 아니다. 동의확정과 게시원자성 후보 C-A/B, 멱등부모후속/조회기한 적용은 기존 DG02/03/05에서 미결로 남는다. 원문없는증빙이 있다는 이유만으로 COMMIT불명을 확정실패로 바꾸지 않는다.

잘못된증빙/연결 발견 시 원사건을 덮지 않고 정정관계/효력설명 후보를 둔다. 정정실행자격·근거/이의/해제·동시에새동의/탈퇴/삭제가발생한경우는 별도계약이며 확인담당에게 정정권한을 부여하지 않는다. 개인 이름/이메일이 같다는 이유로 증빙을 새계정에 옮기지 않는다.

다음 필요한 설계는 EV01~05 각각의 ‘사용중/목적종료/정리대기/삭제·백업종결’ 전환조건과 보유기산을 정의한 수명표다. 충분한근거 없이 새기간 숫자를 확정하지 않는다. 명칭필드/증빙열람/기한에 정책변경이 필요한부분만 묶어 질문하며 기존목적분리 원칙을 다시 묻지 않는다.
