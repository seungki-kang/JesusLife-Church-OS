## 권위·적용

[REC-084 적용](LEADER_INTRO_MINIMUM_RESULT_AGREED_HANDOFF.md)의 본인·특정 요청 최소 확인 권한을 [r125 결속](LEADER_INTRO_WITHDRAWAL_REQUEST_BINDING_DRAFT.md), [r126 처리 모델 비교](LEADER_INTRO_SYNC_ACCEPTANCE_MODEL_COMPARISON.md)에 이어 구체화한다. [REC 원문](RECOVERY_DECISIONS.md)을 보존한다. M1 동기 유지/한정 보완은 우선 검토일 뿐 선정되지 않았다. 아래는 필드·상태·시각의 후보이며 새 공개 항목/기간 합의나 구현이 아니다.

일반 Q의 다섯 공개 항목·현재 소속·168시간은 그대로다. E 장기 증빙 확인은 후속 기능이다. WR의 특정 요청 결과와 현재 소개/동의 상태, 사본 물리 삭제 상태는 분리한다.

|---|---|---|---|
| 요청 확인 번호 | 현재 본인과 정확히 결속된 요청에 한해 불투명 번호 | 서버 R과 I/K/T 관계, 현재 인증 검증 | 번호만으로 조회 허용하지 않음·임의 번호 생성 금지 |
| 요청 결과 | 아래 결과 근거 표에 따른 최소 의미 | 해당 요청의 실제 내구 근거와 확정 여부 | 현재 자원만으로 과거 결과를 구성하지 않음 |
| 최초 서버 접수 시각 | 내구 접수 사건이 실제 존재할 때만 | 그 사건의 정본·시계·의미 정의 필요 | 전송시각/자원생성시각/최종시각으로 대체 금지 |
| 최종 결과 시각 | 실제 최종 결과와 사건 의미가 확인될 때만 | 업무/결과 원자성 또는 검증 가능한 확정 근거 | now()/조회시각을 소급 입력하지 않음 |
| 결과 확인 종료 시각 | 조회 정책·기산·기간과 계산 근거 확정 후 | WR 전용 목적 계약 | 기존24h/168h/90일을 임의 대입하지 않음 |

정확한 JSON 키·필수/조건부 필드·null/생략·시간 정밀도·타임존 표현·HTTP 상태는 OPEN이다. 필드 후보가 있다고 모든 응답에 다섯 값을 채울 의무가 생기지 않는다. 기술 명세에 값을 제공할 수 없는 분기와 이유를 정의해야 한다.

내부 actor/교회/소개/동의 세대/입력 의미·접수 정본·최종 근거·정책 버전은 권한/결속 판정을 위한 논리 요소다. 공개 응답에 내부 식별자나 원본 입력을 추가하지 않는다. 이름·원문·사진·명단·연락처·다른 요청·상세 사유·감사 전문·토큰·다른 제품 기록을 제외한다. 필드별 최소 저장 필요성/접근/유한 보유는 별도다.

## 계약 카드 2 — 결과 근거와 사용자 의미

| 분류 후보 | 필요한 근거 | 말할 수 있는 것 | 말할 수 없는 것/후속 |
|---|---|---|---|
| 철회 확정 | 이 요청/동의 세대의 업무 확정과 최소 최종 결과가 일관되게 검증됨 | ‘해당 철회 요청이 확정됨’ | 다른 동의/전체 게시/모든 사본 삭제 완료를 보증하지 않음 |
| 변경 없이 최종 거절 | 같은 요청에 대한 실제 최종 거절 근거, 업무 변경 없음을 검증 | ‘해당 요청은 변경 없이 거절됨’ | 단순 4xx/타인 번호/인증 실패를 본인 업무 거절 결과로 등록하지 않음 |
| 접수 확인·미확정 | 실제 내구 접수는 확인되나 최종 근거 없음 | ‘접수는 확인됐고 최종 결과는 아직 확인되지 않음’ | 실제 접수 기능 없는 M1에서 가상 PROCESSING 생성 금지 |
| 확인 필요 | 해당 요청 관계는 확인되지만 근거 모순/확정 경계 불명 | ‘결과에 추가 확인이 필요함’ | 실패·미실행·다시 철회 필요로 단정하지 않음 |
| 조회로 확인 불가 | 참조/기한/권한/자료 정리 등의 이유로 결과 제공 불가 | 관계 존재를 새지 않는 일반 안내 | 없는 기록을 실패 영수증으로 채우지 않음 |
| 통신 실패 | 앱이 결과 응답을 받지 못함 | ‘결과를 확인하지 못함’이라는 앱 상태 | 서버 업무 결과나 내구 상태로 기록하지 않음 |

위 분류는 검토용 의미다. 별도 정식 서버 상태 여섯 개를 채택한 것이 아니다. ‘조회로 확인 불가’는 모든 원인을 공개적으로 구분하는 응답이 아니며 인증/권한·만료/부재의 존재 탐색 방지를 함께 검토한다. ‘확인 필요’를 무한한 정상 처리 중 상태로 쓰지 않는다. 유한 확인/운영 종결 계약은 아직 미결이다.

최종 결과 표기는 조회 당시 유효한 권한·목적/기한 안에서만 제공한다. 과거 성공 근거가 남았다고 자격 없는 본인/담당에게 공개하지 않는다. 반대로 현재 소속이 끝났다는 이유만으로 REC-084의 허용된 본인 요청 확인에 재가입을 요구하지 않는다.

## 계약 카드 3 — 시각의 사건과 한계

| 사건 | 정해야 할 의미 | 기존 필드 재사용 한계 |
|---|---|---|
| 기기 최초 전송 | 사용자가 보낸 시도, 서버 접수와 별개 | 기기 시계/재시도/오프라인 때문에 권위 기산으로 자동 채택 불가 |
| 내구 접수 | 서버가 어떤 기록을 어느 확정 경계에 남긴 것인지 | 별도 접수 기록 없는 경우 resource.created_at로 대신하지 않음 |
| DB 기록 생성/갱신 | 트랜잭션 내 해당 기록의 시각 | now()/created_at가 실제 커밋 성공 시각이라는 뜻 아님 |
| 업무/최종 결과 확정 | 해당 요청의 진실이 확정된 사건과 근거 | 커밋 전 기록 시각·커밋 후 관측 시각·정확한 커밋 시각 구분 |
| 결과 조회 관측 | 현재 검증 후 응답을 만든 시점 | 과거 확정 시각을 새로 구성하거나 기간 재시작 금지 |
| 조회 목적 종료 | 정해진 기산+유한 정책으로 산출 | 서버 보유/실제 삭제/백업 종료와 동일하지 않음 |

동기 모델에서 최초 접수와 최종 확정을 한 DB 경계에 묶더라도 두 사건의 의미가 자동 같아지지 않는다. 정확한 커밋 시각을 제공할 수 없다면 ‘검증된 최종 결과 기록 시각’ 등 실제 의미에 맞춘 이름/안내를 검토하고 사용자 합의와 기존 표기를 대조해야 한다. 이는 이번에 용어를 확정 변경한 것이 아니다.

동일 시간값/정밀도만으로 사건 순서를 판정하지 않는다. 요청/대상 세대·버전·업무 확정 경계가 필요하다. 윤일·타임존·시계 오차와 관계없이 재시도/재이용/이관으로 기존 기산을 초기화하지 않는다. 기간 숫자와 시각 권위의 실제 구현 선택은 OPEN이다.

## 성공·거절·불명을 다루는 계약 순서

1. 현재 인증과 해당 목적 자격을 확인한다. 실패한 입력의 모든 필드를 업무 결과 원장으로 복사하지 않는다.
2. 본인·특정 의도·교회/소개/동의 세대의 서버 관계를 확인한다. 번호 소지/표시명/이메일·현재 최신 동의로 대신하지 않는다.
3. 허용된 최소 기록에서 내구 접수·최종 근거·시각 의미를 확인한다. 기록 없음/기한 종료를 미실행으로 보지 않는다.
4. 근거가 일관된 범위만 표시한다. 충돌은 과거 결과를 수정해 맞추지 않고 확인 필요로 분기한다. 정정 권한은 별도다.
5. 응답 직전·늦은 응답 처리에서 계정/대상/현재 자격 변경을 검토한다. 로그아웃/계정 전환 후 다른 화면에 옛 결과를 적용하지 않는다.
6. 재조회는 읽기만 수행하고 W 쓰기·새 키/의도·재게시·담당 대리 철회를 호출하지 않는다.

최종 거절 기록을 실패한 업무 트랜잭션 밖에 남기는 경우에는 원래 시도 결속·현재 권한·경합·업무 미변경·제한 보유가 별도로 필요하다. 롤백될 기록에 ‘최종 거절 조회 가능’이라고 약속하거나 오류 로그만으로 결과를 소급 생성하지 않는다.
