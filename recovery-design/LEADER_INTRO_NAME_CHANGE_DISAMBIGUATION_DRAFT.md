# 명칭 변경·동명 철회 대상의 안전한 추가 확인 초안

2026-10-30 / r100 / TECHNICAL_DRAFT + POLICY_PROPOSAL / PARTIAL_RECOVERY / 실행 NOT_RUN

## 기준과 범위

[REC-076 본인 철회 자격](RECOVERY_DECISIONS.md#rec-076-종료-후-본인-소개-동의-철회), [REC-077 최소 표시](RECOVERY_DECISIONS.md#rec-077-철회-대상-최소-표시와-모호성-확인), [r98 표시 초안](LEADER_INTRO_WITHDRAWAL_TARGET_DISPLAY_DRAFT.md), [DG04/05·FD02/03/05](LEADER_INTRO_STAGE_GATE_CLASSIFICATION.md)을 잇는다. 이름으로 연결하지 않고 서버의 동의·교회·공동체 정본 참조로 동일 대상을 확인한다. 명칭 선택과 추가 확인의 담당/권한은 아직 제안이다. 기존 합의된 철회 권한과 원문/사진 비공개를 다시 묻거나 약화하지 않는다.

문서 제목의 이름 표시는 화면 표시 설명이며 API·새 식별자 규격이 아니다. ChurchOS가 소개 동의의 정본 제품이며 공통 계정은 본인 관계를 검증하는 근거다. CHGO/AI·검색·이름 유사도로 과거 교회 관계를 추론하거나 다른 제품 개인 자료를 확인 근거로 쓰지 않는다.

## 이름과 대상 동일성 분리

| 대상 변화 | 서버 확인 근거 후보 | 표시·처리 제안 | 금지 |
|---|---|---|---|
| 같은 교회/공동체의 단순 개명 | 동일 정본 참조와 검증된 명칭 변경 관계 | 동의 당시 명칭을 ‘동의 당시 이름’으로 표시하는 안 우선 검토 | 현재 명칭만 조용히 바꾸어 다른 대상으로 보이게 함 |
| 두 교회 또는 공동체가 동명 | 서로 다른 정본 참조·본인 동의 결속 | 기존 최소 항목+본인 범위 구분 표식; 모호하면 추가 확인 | 이름 일치로 병합·첫 항목 자동 선택 |
| 같은 공동체의 과거 동의 여러 건 | 소개/동의 세대·공개 범위별 원기록 | 서로 다른 동의는 분리; 표식만으로 본인이 구분 못하면 제한 확인 | 같은 이름이므로 모두 철회·최신 것만 남기고 이력 삭제 |
| 조직 합병·분리·소유 변경 | 원 조직 참조와 명시된 변경 기록 | 단순 개명으로 간주하지 않고 원 동의 범위를 확인 | 새 조직/다른 교회로 동의 자동 이전 |
| 과거 명칭 누락·오기 | 적법하게 남은 본인 동의 최소 증빙 | 누락을 사실대로 안내하고 식별 확인 절차로 이동 | 현재 이름을 과거 이름처럼 만들어 채움 |
| 대상 삭제·참조 정리됨 | 남아 있는 최소 처리 증거의 실제 범위 | 확인 가능한 사실만 안내; 대상 부재를 철회 완료로 단정 안 함 | 사진/원문/백업 복원으로 목록 재생성 |

구분 표식은 서버 참조와 결속된 보조 표시다. 짧은 코드가 다르다는 사실만으로 사람이 대상을 이해했다고 보지 않는다. 코드를 외웠는지 질문하거나 이름/교인번호/주민번호를 붙여 구분하지 않는다. 코드만 아는 사람에게 존재/상태/철회를 허용하지 않는다.

## 명칭 표시의 권장 후보 N-A

동의 당시 본인이 확인한 교회·공동체 명칭을 적법하게 보유한 최소 증빙에서 확인할 수 있으면 그 명칭을 우선 표시하고 ‘동의 당시 이름’이라고 안내하는 안을 권장한다. 이는 이름의 기준을 선택하는 정책 제안이다. 과거 이름을 새로 수집해 영구 보관하도록 승인하는 것이 아니다. 해당 증빙이 없으면 추측하지 않고 추가 확인으로 넘긴다.

현재 명칭 병기 N-B는 본인의 이해에 도움이 될 수 있으나 과거/현재 명칭 관계를 새로 공개하고 잘못 연결할 위험이 있다. 검증된 동일 정본 개명 관계와 필요성이 확인될 때만 별도 검토하며 기본 표시로 확정하지 않는다. 주소·목회자명·조직도·개인 소개·사진으로 명칭 식별을 보완하지 않는다. 동의 시각 추가 표시는 REC-077의 기본 표시를 자동 확대하는 것이므로 이번에 승인하지 않는다.

개명만으로 동의 범위/세대를 바꾸거나 새 동의를 만든 것으로 기록하지 않는다. 본인 확인 후 표시명이 바뀐 경우 기술적으로 동일 동의임이 검증되어도 사용자가 이해하지 못하면 최신 최소 설명으로 재확인하도록 한다. 단순 개명이 철회권을 장기간 가로막는 조건이 되지 않도록 오류 안내/추가 확인 경로를 제공하되 처리 기한이나 담당 배정 완료를 주장하지 않는다.

## 모호한 대상의 추가 확인 — 제안 절차

| 단계 | 동작 후보 | 최소 데이터·권한 | 완료/미확인 경계 |
|---|---|---|---|
| NC01 본인 선택 중단 | ‘대상을 구분하기 어렵습니다’ 선택 | 현재 인증과 선택된 본인 후보 참조만 | 잘못된 대상 철회나 일괄 철회 실행 안 함 |
| NC02 제한 확인 접수 | 안내 목적/입력 범위 확인 후 접수 | 서버의 본인-후보 결속·정형 사유 코드; 자유 서술/첨부 기본 제외 후보 | 접수 성공은 동의 철회 성공이 아님 |
| NC03 정본 관계 확인 | 별도 배정된 최소 권한 담당의 참조 관계 검토 후보 | 배정 건의 최소 교회/공동체/동의·명칭 관계만 | 교회 관리자 직함만으로 전체 조회/승인 권한 없음 |
| NC04 대상 설명 | 검증된 단일 대상의 허용 최소 설명을 본인에게 안내 | REC-077 표시 범위; 추가 항목 필요하면 별도 검토 | 담당자가 원문/사진을 보여주거나 대신 대상 선택하지 않음 |
| NC05 본인 명시 철회 | 본인이 식별 가능한 대상을 확인하고 철회 | 현재 본인 관계/동의 세대/범위를 다시 검증 | 지원 담당자 확인을 본인 철회 명령으로 자동 전환 안 함 |

NC02~04는 운영 권한 제안이며 담당 선임·허용 열람·재인증 방식·전달 기한·대행·미해결 통지는 OPEN이다. 기존 가입 정정 이의신청의 72시간/30일, 공통 탈퇴 전달의 24시간, 일반 요청의 168시간을 이 접수에 자동 적용하지 않는다. 담당자 없음/근거 부족이면 확인 중 또는 확인 불가를 사실대로 안내하며 자동 철회·재가입 요구·관리자 동의 대기·원문 제출 강요로 대체하지 않는다.

추가 확인은 본인의 철회 허가를 심사하는 절차가 아니라 ‘어느 본인 동의인가’를 확인하는 절차로 설계한다. 그렇더라도 새로운 지원 담당 열람권은 별도 명시 자격·배정·목적 제한 없이는 실제로 부여하지 않는다. 교회 관리자가 임의 원문을 확인해 사실을 인증하거나 민감한 탈퇴/징계 사유를 알려주는 구조는 채택하지 않는다.

## 입력·참조·응답 초안

공개 이름은 선택 설명이고 서버 변경 명령의 식별자가 아니다. 명령의 actor는 인증에서 도출하고 본인 후보 참조는 서버에서 소유 관계를 다시 검증한다. 본인이 기기에서 교회명/공동체명을 수정해 요청해도 대상 연결에 사용하지 않는다. 목록·접수·안내·철회 단계의 참조는 같은 동의 세대/범위에 결속하며 새 동의로 조용히 바꾸지 않는다.

NC02 접수 후보에는 본인 인증 관계·선택 후보 참조·정형 사유(동명 구분 불가/명칭 변경 확인 필요/명칭 누락 등)만 검토한다. 후보 목록 전체를 로그·푸시·이메일로 복사하지 않고 원문/사진·자유 기도문/개인 기록을 받지 않는다. 외부 알림은 인증 후 앱에서 확인하도록 하며 교회/공동체 명칭 노출을 기본으로 만들지 않는다. 재접수/통신 재시도의 동일성은 기존 멱등 설계와 연결할 기술 과제다.

정당하게 남은 최소 기록으로 대상 동일성을 입증하지 못하면 ‘추가 확인이 필요함’을 안내한다. 삭제된 데이터·철회된 동의를 복원하거나 다른 제품의 활동/기록으로 보강하지 않는다. 계정 연결이 충돌하면 공통 계정의 기존 별도 확인 경계로 넘기며 표시 이름·이메일 일치로 해결하지 않는다.

이미 직함 종료로 현재 게시가 내려간 사실이 확인돼도 잔존 동의가 철회됐다고 안내하지 않는다. 반대로 확인 중이라는 이유로 이미 종료된 소개를 계속 게시하지 않는다. 기존 자동 공개 차단은 별도 현재 조건에 따라 유지하고 추가 확인 접수로 재공개하지 않는다. 원문/사진 물리삭제·합법적 최소 이력 보유는 별개다.

## 수명·복원과 검증 인계

명칭 증빙·지원 접수·담당 배정·안내·감사·동의 정본·요청 결과의 수명은 각각 목적과 기산을 정해야 한다. 현재 부족한 식별 근거를 장기 무기한 보유의 이유로 삼지 않는다. 보관 정책 확정 전 실제 이용자 증빙을 수집하거나 신규 운영 테이블을 활성화하지 않는다. 복원 시 최신 철회/삭제/접근 상태를 먼저 재적용하며 과거 명칭/동의가 복원됐다는 이유로 현재 소개를 되살리지 않는다.

| 시나리오 | 확인할 조건 | 실행 상태 |
|---|---|---|
| CA145 | 동일 참조 개명·별개 동명·같은 공동체 여러 동의·합병/분리를 구분하고 이름으로 자동 연결/이전하지 않음 | NOT_RUN |
| CA146 | 추가확인 접수/관계 확인/본인 철회를 분리하고 담당권한 미배정·근거부족·응답유실·정지/탈퇴·복원 상태에서 추측 철회/원문노출/재게시 없음 | NOT_RUN |

전체 시나리오 146개는 설계 인계 조건이며 실행 성공 수가 아니다. REC001~077은 유지하고 새REC/새보유기간/지원담당 권한 확정 없음. 기존18B·DG04/05·FD02/03/05·RV는 남아 있으며 코드/API/DB/GitHub/실제SSO 변경 없음.

## 이번 단일 정책 질문

교회·공동체 이름이 바뀐 경우, 적법하게 남은 본인 동의 증빙의 ‘동의 당시 이름’을 우선 표시하고 이를 확인할 수 없거나 여전히 모호하면 추측하지 않고 추가 확인으로 넘기는 N-A 기준을 채택할까요? 현재 명칭 병기·추가 표시 항목·지원 담당 선임/권한/기한·보유는 별도 미결로 남긴다.

## r101 후속 결정 — REC-078

[REC-078 명칭 변경 시 동의 당시 이름 우선 표시](RECOVERY_DECISIONS.md#rec-078-명칭-변경-시-동의-당시-이름-우선-표시): 명칭 변경 시 적법하게 남은 본인 동의 증빙의 동의 당시 이름을 우선 표시하고, 확인할 수 없거나 여전히 모호하면 추측하지 않고 추가 확인으로 넘기는 기준을 확정했다. 담당 권한·처리 기한·보유기간은 미결이다. 위 r100 N-A 제안/질문은 당시 이력이다. 현재 명칭기준만 AGREED_SCOPED이며 NC01~05의 담당/권한/기한·보유·API 후보는 DRAFT/OPEN이다. 실행 NOT_RUN.
