# 리더 소개 개발 전 결정표

2026-10-30 / r87 / DESIGN_TRIAGE / PARTIAL_RECOVERY / 코드·실행 NOT_RUN

## 범위와 출발점

[통합상태표](LEADER_INTRO_STATE_RECONCILIATION.md), [최소 API 후보](LEADER_INTRO_MINIMUM_API_CONTRACT_DRAFT.md), [재시도 동일성 후보](LEADER_INTRO_RETRY_IDENTITY_DRAFT.md), [조회/앱 초안](LEADER_INTRO_RESULT_QUERY_APP_DRAFT.md)을 연결한다. 결정 권위는 [REC-060~075 및 기존 요청 합의](RECOVERY_DECISIONS.md)다. 이 표의 LD 식별자는 미결 추적용이며 AGREED 결정 ID가 아니다. 기존 LT/LO/LU 식별자를 대체/삭제하지 않는다. 현재범위는 리더 소개이며 ChurchOS 전체 개발준비 완료 판정이 아니다.

## 이미 합의해 다시 묻지 않을 내용

본인 편집·관리자 제안만, 사진/짧은소개 선택, 현재유효 공동체 참여자 대상, 저장과 게시 분리, 본인 명시 공개, 철회/직함종료시 중단, 구미리보기 게시차단, 응답미확인시 조회우선, 유효조건의 확정실패 본인재시도, 사진만 비공개/명시재공개를 유지한다. 다른제품 개인원문/연락처 자동수집·교회전체/인터넷 자동확대를 추가하지 않는다.

기간/권한이 필요한 항목에 운영 담당자가 이미 지정됐다고 쓰지 않는다. 기술 설계 담당이라는 표기는 작업 역할이지 교회 데이터 접근권을 부여하는 운영 역할이 아니다. 기술적 내부필드 선정은 기존합의를 지키는 범위에서 제안/검증할 수 있지만 정책확정과 구현검증을 혼동하지 않는다.

## 권장 진행 순서와 의존성

1. LD01/LD02의 최소 모델·확정단위/실패근거 후보를 함께 작성한다. 이 단계는 새 정책질문 없이 진행 가능하다. 동의와 게시를 한 확정단위로 묶는 후보와 분리후 게시실패를 표현하는 후보를 비교한다.
2. 그 결과로 LD03의 재시도의도 경계를 좁힌다. ‘네’ 한 번을 새키/후속조회/보유기간 일괄승인으로 기록하지 않는다.
3. LD04의 다른기기 후속발견과 기존5항목 최소응답을 비교해 필요한 정책선택 하나를 묻는다. 관계조회가 없는데 앱에서 후속을 항상 찾을 수 있다고 약속하지 않는다.
4. LD05의 행위별 조회기간/보유·LD07 수동확인을 연결한다. 404/만료는 실패증거가 아니라는 합의를 유지하며 무기한 보관/자동실행으로 해결하지 않는다.
5. LD06/LD08의 미디어/필드UX를 구체화하고 인계표를 갱신한다. 운영채택/실데이터/파일럿/코딩은 현재 단계에서 수행하지 않는다.

이는 설계 작업순서 제안이며 신규 배포/파일럿 일정이나 완료율이 아니다. 병행 가능한 검토를 위해 여러 정책을 한꺼번에 승인받을 필요는 없다.

## 완료 상태와 검사 범위

이번 정리로 완결된 것: 미결의 위치/분류/기존근거/다음산출물 추적. 미완료: 모든 LD 항목의 기술선정/정책해소·실행증거. 각항목은 관련 문서와 CA 조건으로 추적하고 정책 AGREED/기술선정/구현/실행 PASS를 별도 기록한다.

현재 작업14개·시나리오128개를 유지한다. 결정표 작성만으로 시나리오 숫자를 늘리거나 실행 PASS로 바꾸지 않았다. CA127/128의 기존 조회검증에 LD03~05/07 추적을 붙였다. 문서 링크/표 일치/원본 및 canonical 해시/ZIP 검사는 정적 검사이며 실제 권한/경합/화면 검증이 아니다.
