# 본인 소개 철회 처리 모델 — 추천안과 채택 조건

2026-10-31 / r147 / RECOMMENDED_NOT_ADOPTED / PARTIAL_RECOVERY / 실제 실행 NOT_RUN

[r126 비교](LEADER_INTRO_SYNC_ACCEPTANCE_MODEL_COMPARISON.md)를 재사용하고 [REC-091 인계](LEADER_INTRO_DURABLE_EVIDENCE_AGREED_HANDOFF.md), [통합 결정표](LEADER_INTRO_PREDEVELOPMENT_DECISION_MATRIX.md)를 연결한다. 기존 COS·REC001~091은 유지한다. 아래 M1/M2는 기술 후보이며 실제 처리 시간·운영 부하를 측정한 결론이 아니다.

## 추천

첫 구현의 우선 설계안은 **M1: 소개 철회 효력 변경과 최소 결과 근거를 하나의 동기 트랜잭션에서 확정하는 방식**이다. 별도 선접수 큐를 기본으로 도입하지 않는다. 현재 정본의 동기 구조와 연속성이 있고, 접수 후 미처리 작업을 별도로 운영하는 책임을 줄일 수 있기 때문이다. 현재 코드를 그대로 사용해도 된다는 뜻은 아니다. 본인 권한·응답 유실 조회·거절 결과·시각·기록 수명·복원 보호는 보완해야 한다.

M1 채택 여부는 아직 미결이다. 사용자의 이번 ‘진행해줘’는 모델 선택이나 구현 착수 승인이 아니다.

## 요구사항별 비교

| 요구 | M1 동기 처리 보완 | M2 별도 내구 수용 후 처리 |
|---|---|---|
| 내구 접수 의미 | 별도 선접수 확정 없음. 요청/업무/결과가 함께 확정되는 경계 명세 | 수용만 먼저 확정. 처리 책임·최종화 수명 별도 필요 |
| 응답 유실 | 기존 의도/키를 최소 조회 근거에 결속; 조회는 쓰기를 재실행하지 않음 | 접수번호 응답도 유실 가능하므로 동일 문제 해결 필요 |
| 최종 성공 | 동의 세대 효력과 최소 성공 근거를 원자적으로 결속 | 지연 실행 시 현재 권한·동의 세대 재검증 후 원자 확정 |
| 최종 거절 | 검증 가능한 요청에 대한 한정 거절 근거의 저장 경계 필요 | 수용 후 거절 기록과 최종화 필요; 무권한 데이터 공개 금지 |
| 처리 중 표현 | 실제 내구 수용/진행 근거 없으면 표시하지 않음 | 수용·대기·실행·중단 등의 실제 상태 근거 필요 |
| 장애 복구 | COMMIT 불명 조회·현재 상태/근거 불일치 점검 | 추가로 실행자 재시작·임대·중복·미종결 복구 필요 |
| 기록 수명 | 결과 조회와 키/옛 실행 방지 수명 분리 | 접수/작업/결과/임대/재시도/보호 수명 추가 |
| 외부 사진/알림 | 효력 변경과 후속 물리 정리 구별 | 선접수 자체가 모든 사본 삭제를 보장하지 않음 |
| 범위 | ChurchOS 해당 명령에 한정 | 필요해도 타제품/모든 명령을 공통 큐로 통합하지 않음 |

## M1 채택 전 필수 조건

| 조건 | 채워야 할 설계/근거 | 미충족 시 |
|---|---|---|
| MC01 작은 확정 경계 | 외부 STT/사진 물리삭제/알림을 기다리지 않고 동의 효력을 서버 업무로 확정할 수 있는지 확인 | M1 적합성 재검토; 외부 작업 성공을 가정하지 않음 |
| MC02 본인/세대 결속 | 소속 종료 후 본인 권한·대상 세대·현재 조건·중복/경합 판정 | 관리자 일반 쓰기 권한으로 대체 금지 |
| MC03 원자 결과 | 효력 변경·최소 성공 근거·감사의 일관된 확정 경계 | 일부만 성공한 결과를 사용자 성공으로 만들지 않음 |
| MC04 첫 응답 전 복구 | 앱 의도/기존 키와 서버 요청 근거를 결속하는 읽기 경로·참조 전부 소실 처리 | 새 키 재실행이나 최근 이름 추정으로 해결 금지 |
| MC05 거절 경계 | 사전 인증 실패와 식별된 요청의 최종 업무 거절을 구분; 최소 거절 근거 저장/권한 | 모든 예외를 조회 가능한 거절로 자동 저장 금지 |
| MC06 시간·수명 | 사건 의미·조회 기산/기간·최소 결과·멱등 보호·삭제/백업 | 기존 created_at/24h로 치환 금지 |
| MC07 옛 실행/복원 | 직접 DML·옛 API/키·새 동의·복원 시 최신 철회 보호와 유한 정리 | 문서만으로 복원 안전 PASS 금지 |
| MC08 실제 검증 | COMMIT 경계·응답 유실·동시 요청·권한 회수·삭제/복원 | 구현/출시 준비 완료 표시 금지 |

MC01~07은 설계/운영 근거 조건, MC08은 구현 후 검증 조건이다. MC08을 먼저 실행하라는 요청이 아니다. 조건을 충족하기 전에도 기술 문서를 더 구체화할 수 있지만 실제 코드/DDL/배포로 넘어가지 않는다.

## M2로 다시 검토할 계기

동의 효력 확정 자체가 여러 외부 단계에 의존하거나 장시간 작업을 반드시 요구하는 근거가 확인되면 M2를 재검토한다. 단순 네트워크 응답 유실·나중 사진 삭제·알림 필요만으로 M2를 선택하지 않는다. M2를 선택하려면 실제 책임자·유한 처리 상한·실행 시 권한/세대 재검증·중복 실행 방지·고장 복구/미종결 종결·자원/결과 일관성이 채워져야 한다. 실제 요구가 미확인인 지금 필요하다고 단정하지 않는다.

## 실무 이행 범위

정본 v2.6 기존 마이그레이션/코드는 보존한다. 이후 구현을 결정하더라도 현재 배포 DB 계보 확인과 추가 이행 설계가 필요하며 과거 SQL을 덮어쓰지 않는다. Idempotency-Key와 기존 경로/입력 충돌·버전 경합 계약을 새 본인 철회에 어떤 범위로 재사용할지 명세해야 한다. 새 결과 조회는 같은 명령을 다시 호출하는 동작이 아니다.

동기 모델에 접수 전용 트랜잭션/비동기 워커를 섞으면 실제로 M2에 가까워지는지 경계를 다시 검토한다. 반대로 M1이므로 ‘미확정 요청이 절대 없다’고 주장하지 않는다. COMMIT 결과 불명은 여전히 존재하며 REC088/089의 유한 확인·재검토가 필요하다.

## 인계와 다음 결정

권고는 M1 우선 설계이며 추천 근거는 현재 정본과의 연속성과 추가 작업 운영 책임의 최소화다. 기존 코드 보완량이나 실제 성능은 미측정이다. 실제 시간 숫자·내구 기록 형식·테이블/API·거절 사유 목록·신규 실행 권한을 선택하지 않았다.

다음 질문은 **첫 구현을 M1 동기 처리 보완 방향으로 설계하고, 별도 내구 선접수는 필요가 확인될 때 재검토할지**다. 이 방향을 합의하더라도 MC01~08 충족 선언·실제 구현 착수·출시 승인이 아니다.

기존 CA144/159~162 세부 검증 인계이며 새 성공 수를 추가하지 않는다. 작업14/CA162/MVP34·18B/DG/FD/RV·다른 MVP33행·과거 원문 보존. 코드·DB·GitHub 변경 없음. PARTIAL_RECOVERY·실제 실행 NOT_RUN.
