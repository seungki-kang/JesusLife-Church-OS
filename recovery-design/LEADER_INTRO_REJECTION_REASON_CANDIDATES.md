# 철회 명령의 거절 후보·안내·기록·재시도 경계

2026-10-31 / r155 / REJECTION_CANDIDATE_DRAFT / PARTIAL_RECOVERY / 실제 실행 NOT_RUN

[REC095 인계](LEADER_INTRO_FINAL_REJECTION_AGREED_HANDOFF.md), [결과 경계표](LEADER_INTRO_REJECTION_REASON_CANDIDATES.md), [M1 명령](LEADER_INTRO_M1_COMMAND_CONTRACT_DRAFT.md), [REC 원문](RECOVERY_DECISIONS.md)을 따른다. 이번 표는 실제 거절 사유의 후보 분류다. 서비스 정책이나 정식 상태/코드의 승인 목록이 아니며 코드·DB를 변경하지 않는다.

## 검토 결론

본인 철회는 본인과 특정 동의 세대 관계가 명확하면 허용하는 기존 방향을 유지한다. 거절 종류를 늘리기 위해 새 정책을 만들지 않는다. 현재 확인된 주요 실패 사례 대부분은 인증/식별/충돌/불명/무변경 분기이며, 영속 최종 업무 거절로 일괄 등록할 근거가 없다. 실제 거절 사유가 확정되지 않은 상태에서 범용 ‘거절’ 저장기를 구현하는 것은 권고하지 않는다.

## RJ06을 최종 업무 거절 후보로 삼으려면

본인·요청·명시 대상은 검증됐지만 해당 입력의 세대 조건으로는 더 이상 변경할 수 없다는 최종 판정이 필요한 경우에 한해 검토한다. 단순히 최신 세대와 다르다는 이유만으로 옛 세대의 이미 철회됨 확인을 금지하지 않는다. 옛 세대를 안전하게 확인할 수 있으면 RJ05 적용 가능성을 먼저 구분한다.

최종 거절 후보에는 다음 근거가 모두 필요하다: 고정된 요청 입력, 해당 본인/대상 관계, 실제 조건 불충족의 의미, 이 요청에 의한 변경 없음, 그 거절 판정과 결과/감사가 일관되게 확정됐다는 근거. 실제 사유를 확정하기 전에는 이를 허용 거절 목록으로 사용하지 않는다. 다른 요청의 변경이 없다는 뜻으로 확대하지 않는다.

소속 종료·직함 종료·관리자 미승인 자체는 이 본인 철회의 새 거절 사유가 아니다. 계정 정지/탈퇴 예외는 별도 미결이다. 원문/사진이 없다는 이유로 본인 철회 권리를 없애거나 원문을 복구하지 않는다. 본인/대상 식별이 부족하면 RJ02와 제한 지원의 문제로 구별한다.

## 입력 수정과 새 요청의 경계

입력 충돌/세대 변경 후 새 제출이 필요하더라도 먼저 기존 요청의 결과를 확인한다. 새 요청은 현재 본인이 새로 확인한 특정 세대에 대한 명시 행위여야 한다. 앱의 자동 전환·무응답 타이머·지원 담당의 대리 제출로 생성하지 않는다. 어떤 오류에 재입력을 허용하고 어떤 조건에 새 의도가 필요한지 정식 계약을 채워야 한다.

‘다시 시도’ 버튼을 모든 오류에 공통 노출하지 않는다. 인증 재확인·입력 검토·읽기 조회·지원 문의·명시 새 제출의 동작을 구분하며 자동 재실행은 허용하지 않는다. 기기 캐시가 이전 계정/교회의 요청을 다시 실행하지 않도록 기존 기기 격리 계약도 유지한다.

## 개발 인계

실제 거절 후보를 채택하려면 사유별 판정 근거·현재 권한·트랜잭션/감사·내구 결과·공개 의미·기산/수명·동시성·안전한 다음 행위를 함께 채운다. 확정되지 않은 사유는 OPEN으로 남기고 구현 enum/데이터에 넣지 않는다. 목록 밖 예상 못한 예외는 검증된 최종 거절로 자동 승격하지 않는다.

검증 계획은 소속/직함 종료, 이미 철회된 옛 세대, 새 세대 공개, 동시 요청, 인증 회수, 변조 키, 실제 결과 저장 실패, COMMIT 불명, 원문 부재, 조회 만료다. 허용된 본인 권리를 부당 차단하지 않는 정상 사례와 타인 노출/옛 요청 재생이 없는 금지 사례를 함께 확인해야 한다. 기존 CA144/159~162 세부 인계이며 전부 NOT_RUN.

다음은 후보 거절을 임의 확정하기보다 **현재 합의된 실제 철회·무변경 결과의 공통 최소 내구 기록과 오류 전용 기록의 분리**를 설계한다. 실제 최종 거절 사유는 검증된 요구가 있을 때 별도로 채택한다. 이번 ‘진행해줘’는 RJ06 또는 전체 후보의 합의가 아니다.
