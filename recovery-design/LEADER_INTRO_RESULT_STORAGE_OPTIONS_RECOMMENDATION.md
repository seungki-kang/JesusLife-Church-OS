# 철회 최소 결과 저장 구조 — 비교와 권고

2026-11-01 / r164 / STORAGE_RECOMMENDATION_NOT_ADOPTED / PARTIAL_RECOVERY / 실제 실행 NOT_RUN

[r164 원자 저장 명세](LEADER_INTRO_RESULT_STORAGE_OPTIONS_RECOMMENDATION.md), [REC096 인계](LEADER_INTRO_P1_P2_DIRECTION_AGREED_HANDOFF.md), [r157 기존 코드 대조](LEADER_INTRO_INTEGRATED_REVIEW_1_CODE_MAPPING.md)를 잇는다. 이번은 P1/P2 안의 저장 방향 제안이며 테이블/DDL·정리 기간·보호 방식의 선정이 아니다.

## 권고

**S2: 새 본인 철회 명령의 최소 결과를 기존 일반 API 영수증과 별도 목적의 저장 단위로 두는 방향**을 권고한다. 실제 효력 변경·그 결과와 필요한 의도 결속·감사는 같은 동기 트랜잭션에서 확정한다. 기존 일반 API 영수증 구조와24시간/재전송 계약은 보존한다.

별도 저장 단위는 별도 서버·DB·큐나 두 번째 실행기를 뜻하지 않는다. 처음 구현은 새 명령에서 한 번만 판정/확정하고 결과 조회는 그 결과를 읽는다. 기존 영수증과 새 결과 양쪽에 독립 성공 판정을 쓰는 이중 정본을 만들지 않는다. 새 명령 의도 결속을 어디에 물리 저장할지는 실제 제약/수명 설계에서 결정한다.

## 구조 대조

| 기준 | S1 기존 영수증 확장 | S2 별도 최소 결과 단위 — 권고 |
|---|---|---|
| 레거시 호환 | 기존 코드/기록과 새 분류를 함께 관리해야 함 | 기존 생성/변경 경로를 보존하고 새 명령 범위만 추가 |
| 결과 의미 | 기존 자원 응답과 실행/무변경 결과를 구분하는 버전/제약 필요 | 새 결과 의미를 목적에 맞춰 명세 가능 |
| 현재 권한 | ACTIVE/관리자 경로와 본인 목적 읽기 분리 필요 | 본인 목적 읽기 경계를 새 단위에 한정할 수 있음; 자동 보장 아님 |
| 수명 | 단일 expires_at에 키/조회/정리 의미를 섞지 않도록 확장 필요 | 결과 수명과 키 보호 목적 분리 용이; 실제 보호 계약은 필요 |
| 원자성 | 동일 트랜잭션 설계 가능 | 동일 트랜잭션 설계 가능; 별도 커밋이면 추천 취지 위반 |
| 최소 자료 | 기존 자원 id/created_at로 새 의미 표현 불충분 | 요청/본인/세대·판정·근거만 한정할 수 있음 |
| 이행 비용 | 행 종류/제약/읽기/삭제의 기존 영향 분석 | 새 제약·grant·정리·조회·감사 관계 설계 추가 |
| 보호/복원 | 확장만으로 해결 안 됨 | 분리만으로 해결 안 됨; P4 유지 |

S2 권고는 현재 보존된 소스와 요구의 차이에 따른 설계 판단이다. 실제 성능·운영 부하·이행 비용을 측정한 결과가 아니다. S1도 엄격한 버전/권한/수명 분리로 가능할 수 있지만 현재 영수증에 필드 몇 개를 추가하는 단순 변경으로 취급해서는 안 된다.

## S2 논리 구조의 최소 제안

| 구성 | 역할 | 경계 |
|---|---|---|
| 요청/결과의 내구 정본 | R·검증 본인·정확한 세대·결과 의미/근거·사건 의미 | 원문/사진/전체 자원 응답 저장 금지 |
| 의도 결속 | I=K와 명령범위·고정 입력을 한 결과에 연결 | 동일 범위/키로 복수 독립 결과 생성 금지 |
| 감사 관계 | 판정 주체/목적·실행/무변경 구별 | 결과와 같은 확정 경계; 내부 원문 공개 아님 |
| 목적별 수명/보호 참조 | 결과 조회·정리와 옛 실행 보호 구분 | 별도 유한 근거·실제 보호 종료 미확인 |

물리적으로 결과와 의도 결속을 한 테이블에 둘 수도 있으나 그때도 결과 조회 종료와 보호 종료가 다르면 필드별 정리/남는 검증 관계를 채워야 한다. 결과를 지운 뒤 다른 보유 기록이 전체 결과를 계속 공개하는 우회 정본이 되지 않도록 한다.

## 하나의 실행 경로

새 본인 철회 명령은 현재 본인/입력 검증→한 의도 결속 확인→정확한 세대 판정→효력 변경 또는 무변경→최소 결과/감사 원자 확정으로 설계한다. 레거시 생성/변경 API는 기존 계약을 따른다. 두 경로가 같은 철회 의도를 각각 실행하지 않도록 새 명령 종류/범위를 명확히 해야 한다.

새 명령이 기존 create/mutate도 호출하고 새 저장기도 따로 성공 처리하는 구조를 권고하지 않는다. 동일 트랜잭션에 참여하는 저장 로직을 재사용하는 것과 독립 명령을 두 번 실행하는 것을 구별한다. COMMIT 불명 때 어느 기록을 신뢰할지는 정본 관계와 원자 근거를 따라야 하며 로그 유무로 판정하지 않는다.

## 채택 전 필요한 조건

- 새 명령의 한 의도/본인/대상 세대 유일성·고정 입력·현재 권한 회수 경합의 실제 제약/잠금 설계.
- 실행/무변경 결과·필수 감사의 단일 확정과 실패 시 일관성.
- 본인 목적 읽기의 권한/기간 검증·레거시 영수증/다른 사용자 자료 비공개.
- 키/결과 정리 이후 옛 요청 재생·복원 재등장 방지의 유한 보호 계약.
- 실제 운영 DB 계보 확인과 추가 이행, 기존 마이그레이션/경로/기록 보존.
- 결과/키 보호·감사·오류·사본/백업의 목적별 수명과 고아 참조 처리.

기존 grant를 복사해 새 결과 단위에 광범위 SELECT/UPDATE를 주지 않는다. 새 테이블을 만들었다는 사실만으로 최소권한이나 본인 격리가 보장되지 않는다. 실제 DB역할/함수/DML 경로 검증은 미실행이다.

## 인계 상태와 다음 선택

P1/P2 안의 저장 방향을 S2로 구체화해 제안했다. P3 시간/수명·P4 보호·P5 권한/운영 근거는 해결되지 않았다. 새 테이블명·DDL·API/상태 코드·기간·키 퇴역/복원 방식을 임의 채택하지 않는다. 이미 승인된 M1·I=K·R·읽기 확인 방향은 유지한다.

다음 묶음 선택은 **새 본인 철회의 최소 결과를 기존 일반 API 영수증과 별도 목적 단위로 두되, 의도 결속·효력·결과·감사는 한 실행 경로와 동기 원자 경계로 유지하는 방향**이다. 이는 실제 물리 테이블/추가 DB 또는 코드 착수의 승인이 아니다.

검증 인계는 동일키/다른키·부분 기록 실패·COMMIT 불명·레거시 응답 불변·현재 본인 읽기·권한 회수·정리/복원이다. 기존 CA144/159~162 상세이며 전부 NOT_RUN. 기존 COS·REC001~096·정본·과거 자료·작업14/CA162/MVP34·다른 MVP33행·18B/DG/FD/RV 보존. 코드·DB·GitHub 변경 없음. PARTIAL_RECOVERY 유지.
