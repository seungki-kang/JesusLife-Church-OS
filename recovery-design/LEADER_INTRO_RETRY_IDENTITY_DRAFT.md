# 확정 실패 후 재시도 동일성 계약 후보

2026-10-30 / r85 / TECHNICAL_DRAFT / PARTIAL_RECOVERY / 실행 NOT_RUN

## 범위와 권위

[최소 API 후보](LEADER_INTRO_MINIMUM_API_CONTRACT_DRAFT.md)의 LT03 쟁점을 [기존 요청 식별 합의](COMMAND_IDEMPOTENCY_STATUS_CONTRACT_DRAFT_2026-10-27.md), [접수/실행/확정 후보](ACCEPT_EXECUTE_FINALIZE_DRAFT.md), [결정 기록](RECOVERY_DECISIONS.md)의 REC-026/027/068~075에 대조한다. 기존 합의는 동일 요청 식별자에 같은 업무/내용, 다른 내용 거절, 응답유실 시 기존결과 우선확인이다. REC-073은 동일유효조건의 확정 게시실패에 본인 명시 재시도와 재동의 생략을 허용하지만 식별자 교체/최종실패 덮어쓰기를 확정하지 않았다.

이 문서는 구현 전 후보 비교다. 신규 필드/경로/상태/키 발급/실행 구조와 아래 권장 후보를 AGREED로 승격하지 않는다. 새 REC 없음·코드/DDL/원격 변경 없음.

## 세 가지 재시도 의미

| 구분 | 조건 | 후보 동작 | 금지 |
|---|---|---|---|
| 같은 전송 다시 확인/전달 | 동일 의도·기존 키·같은 입력 | 읽기 우선; 같은요청 재도착은 동일 결과/상태로 수렴 | 새 업무 실행/키 자동교체 |
| 확정 실패 후 본인 다시 실행 | 동의저장 확인·미반영 최종확정·조건 동일유효·본인 새 클릭 | 이전 실패를 참조한 후속 명시 의도 후보 | 이전 실패를 성공으로 덮어쓰기 |
| 변경된 내용/대상으로 게시 | 기존 확인/동의 범위와 달라짐 | 최신재확인/필요한 동의 절차 | 동일 키에 입력만 교체 |

후속 클릭을 기술적으로 새로운 명시 의도로 구분할 수 있는지가 REC-026과의 핵심 호환성 게이트다. 같은 업무라는 이유만으로 언제나 새 키를 허용하지 않는다. 결과미확인/PROCESSING/REVIEW_REQUIRED/404/만료/로그부재는 확정 실패가 아니다. 기존 요청 성공 여부와 현재 공개 상태도 별개다.

## 후보 비교

| 후보 | 장점 | 해결되지 않는 점 | 현재 판정 |
|---|---|---|---|
| A 기존 키의 확정실패를 다시 열어 실행 | 키 유지가 단순 | 최종결과 불변성·과거 실패조회 의미 충돌, 구작업/새작업 경합 | 채택 비권장·선정 없음 |
| B 기존 실패를 보존하고 명시적 후속 의도를 연결 | 실패이력/전송재시도와 실제재실행 분리 가능 | REC-026의 의도 경계·발급/중복후속 제어·조회 계약 필요 | 우선 기술 검토 후보·미확정 |
| C 앱이 임의 새 키로 동일 게시 | 클라이언트 구현 단순 | 실패/미확정 검증·동시기기·중복 실행을 우회 | 채택 비권장·선정 없음 |

B의 논리 기록도 별도 범용 실행기가 아니라 기존 자원별 행위/멱등 영수증에 종속된다. 새로운 식별자 규칙에 정책적 의미 변경이 생기면 그 좁은 항목만 사용자 결정으로 요청해야 한다.

## 후보 B의 내부 결속

필드명과 기록 분리는 DRAFT이며 공개 다섯 항목에 그대로 노출하지 않는다.

| 참조 | 목적 | 제약 후보 |
|---|---|---|
| prior_confirmation_ref | 이전 실패를 정확히 지목 | 동일 본인·교회·공동체·소개·행위·실패확정·게시 미반영 확인 |
| retry_parent_generation | 동일 실패에서 동시후속 생성 제어 | 이전 시도에 하나의 정식 직계후속만 연결; 직계후속 미확인이면 재조회 |
| explicit_retry_ref | 본인의 이번 명시 클릭 동일성 | 전송 전에 최소 참조 보존·응답유실에도 같은 참조 사용; 별도 업무실행기 아님 |
| successor_confirmation_ref | 정식 후속 요청 결과 참조 | 부모 실패 변경 없이 불변 연결; 부모에 후속이 있으면 새 생성 안 함 |
| existing_route_key/key | 후속 자원행위 실행의 멱등성 | 서버가 검증한 행위/본인 범위에 결속; 키발급/연결 프로토콜 OPEN |
| checked_version/consent_generation | 동일유효조건 입증 | 내용·대상·직함·동의/사진상태를 현재 서버 상태와 검증 |

‘직계후속 하나’는 중복 클릭/동시 기기의 중복 실행을 막기 위한 기술 후보이며 전체 재시도 횟수 1회 정책이 아니다. 후속도 확정 실패했다면 그 실패에서 다시 명시 후속을 만들 수 있는 구조를 비교하되 재시도 횟수/간격/원인별 허용은 OPEN이다. 기존 실패 요청의 일반 조회기한을 후속 생성만으로 다시 시작하지 않는다. 후속 자체의 조회기간/기산은 별도 적용 범위 검토가 필요하다.

## 후보 처리 순서와 일관성

1. 현재 인증/본인·교회/공동체·소개/행위 경계를 확인한다. 읽기 전용 결과조회 권한이 있다고 새 쓰기 권한을 부여하지 않는다.
2. 부모의 내구 최종실패 증거와 게시 미반영, 옛 실행자가 더이상 커밋할 수 없음을 확인한다. 타임아웃·임대만료·롤백 로그 한 줄만으로 대체하지 않는다. 증명 불가면 미확정/수동확인 경로이며 후속 실행하지 않는다.
3. 부모에 이미 직계후속이 있으면 현재 허용되는 최소 결과로 안내한다. 자격 없는 사람에게 참조/존재를 노출하지 않는다.
4. 본인의 명시 재시도 의도와 확인 버전/동의를 검증하고 부모-후속 연결 및 정식 후속 한 개를 원자적으로 생성한다. 두 기기가 동시에 요청해도 한 후속으로 수렴하도록 유일성/잠금/충돌 복구 계약을 작성한다.
5. 후속을 실행할 때와 최종쓰기 경계에서도 현재 동의·직함·내용/대상·사진차단 및 실행권 세대를 검증한다. 후보 생성이 실행권을 영구 보장하지 않는다.
6. 업무변경·최소감사·성공영수증·후속 최종결과의 일관성을 확보한다. 부모 결과를 고치거나 과거 실패를 성공으로 표시하지 않는다.

위 순서는 코드/DB에서 검증된 원자성이 아니다. 부모실패 증거·실행차단/복구·서버시계·프로세스중단/확정불명·경로간 공개의도 결속이 구현 전 게이트다. 후보 생성 응답을 잃어도 새 후속을 만들지 않고 기존 부모/명시 참조의 연결을 읽기로 확인한다. 부모의 후속 연결은 실행 성공 증거가 아니다.

## 상태별 앱 안내 후보

| 확인된 사실 | 안내/행위 후보 | 제한 |
|---|---|---|
| 동의저장/실패확정·조건 동일유효 | 공개 반영 다시 시도 | 본인 명시 실행·서버 재검증 |
| 확정 결과 불명 | 결과 확인 중·조회 | 자동 실행/새 키 금지 |
| 이미 후속 존재 | 기존 후속 결과 확인 | 두번째 후속 자동생성 금지 |
| 과거 성공·현재 비공개 | 과거 처리 결과와 현재 비공개 분리 | 현재 공개의도/동의 없이 재게시 금지 |
| 내용/대상/직함 변경 | 최신 미리보기 재확인 | 기존 동의 자동확대 금지 |
| 동의 철회/직함 종료 | 새동의/현재자격 절차 또는 공개차단 | 재시도버튼으로 복구 금지 |

앱 안내 후보는 사용자에게 기술 키/세대/펜싱 설명을 요구하지 않는다. 사진 재공개 전용 실패의 동일 적용은 미확정이며 REC-075를 넘어 일괄 승인하지 않는다.

## 기존 API 및 보유와의 호환성

v2.6 성공 영수증 24시간/만료409·route+actor+tenant+key·If-Match 입력동일성·REPLAY_SUPERSEDED를 변경하지 않는다. 현재 v2.6에는 새 영속실패/부모후속/읽기연결이 없다. 168시간 최소 결과조회는 실행 허용시간/멱등키 재사용 허가/기록 물리삭제기한이 아니다.

부모/후속 연결을 삭제하거나 복원했을 때 또 후속이 생성되지 않도록 최소 중복차단 근거와 최신 철회/삭제 상태 재적용이 필요하다. 중복차단 근거를 영구 보유한다고 확정하지 않으며 기간·삭제후 재사용차단·최소증빙/기기참조 수명은 OPEN이다. 일반7일/30일/1년을 자동 적용하지 않는다. 입력 원문·사진·토큰을 연결 기록/감사/이벤트로 복제하지 않는다.

## 검증 인계와 다음 미결

CA125: 같은 실패를 두 기기에서 동시에 본인 재시도→정식 후속 한 개/기존연결 재조회, 부모 실패 불변, 응답유실시 자동 새후속 금지.

CA126: 실패확정처럼 보이나 옛작업 커밋가능/결과미확인 또는 철회/버전변경/조회만료/복원→후속 생성/실행을 우회하지 않음. 롤백/정지주입·세대/유일성·시각/복원 검증은 NOT_RUN이다.

다음 순서: (1) 후보 B와 REC-026의 의도 정의/키발급 호환 판단, (2) 부모·후속 결과 조회의 적용 기간/응답 최소화, (3) 동의/게시 확정 단위와 실제 실패 증거, (4) 미디어/캐시. 기술 후보 선정이나 새 운영 기간을 이번 ‘진행해줘’의 정책 합의로 기록하지 않는다.
