# 본인 철회 요청의 서버 사건·결과 근거 계약 초안

2026-10-31 / r145 / SERVER_EVENT_EVIDENCE_DRAFT / PARTIAL_RECOVERY / 실제 실행 NOT_RUN

[REC-090 공개 상한](RECOVERY_DECISIONS.md#rec-090-본인-철회-결과-공개-정보의-다섯-종류-상한), [합의 인계](LEADER_INTRO_PUBLIC_RESULT_LIMIT_AGREED_HANDOFF.md), [통합 결정표](LEADER_INTRO_SERVER_EVENT_EVIDENCE_DRAFT.md)를 잇는다. 이번 문서는 사건 의미와 근거 요건의 제안이다. 처리 모델·시각 구현·기간 숫자를 확정하지 않는다.

## 구별할 서버 사건

| 사건 후보 | 뜻 | 근거 요건 | 그 자체로 입증하지 않는 것 |
|---|---|---|---|
| SE01 도착 | 서버가 요청 바이트를 받음 | 수신 계층의 제한된 기록 | 적격 요청 접수·철회 성공 |
| SE02 내구 수용 | 현재 본인/대상과 결속한 요청을 처리 책임으로 내구 수용 | 선정 모델의 원자적 수용 기록과 식별 관계 | 최종 처리 성공·정확한 COMMIT 시각 |
| SE03 최종 결과 확정 | 특정 요청/동의 세대의 업무 결과를 내구 확정 | 해당 결과·대상/버전·업무 반영과 일치하는 근거 | 모든 사본 삭제·클라이언트 수신 |
| SE04 서버 확인 | 서버가 수용/최종 근거의 확정을 확인 | 해당 기록/결과를 신뢰할 수 있는 방식으로 검증 | 확정 순간의 정확한 시각 |
| SE05 응답 전달/수신 | 응답을 보내거나 앱이 받음 | 전송과 실제 수신은 구별 | 원래 접수/최종 사건 시각의 대체 |
| SE06 사후 발견 | 뒤늦게 근거를 찾음 | 기존 요청과 근거의 검증된 관계 | 새 최종 시각·새 조회 창 |

이는 여섯 개 새 공개 필드를 추가하는 안이 아니다. 공개는 REC090 다섯 종류 상한을 유지한다. 내부 사건 구별과 외부 필드의 이름/값 매핑은 후속 계약이다.

## 처리 모델별 수용 의미

기존 동기 모델에서는 업무 반영·성공 영수증이 같은 트랜잭션에 포함된다. 별도 수용 건이 내구 저장되지 않았다면 최종 확정 전 ‘접수 완료’를 보장하는 기록이 있다고 말할 수 없다. 수용과 최종이 하나의 내구 경계에서 성립할 수도 있지만, 두 공개 시각을 근거 없이 동일 값으로 채우지 않는다.

별도 내구 수용 모델을 선택한다면 수용만 확정되고 업무가 아직 처리되지 않은 구간이 생긴다. 그 모델은 처리 책임·현재 권한 재검증·작업 수명/복구·유한 종결·결과 근거를 추가로 설계해야 한다. 이번 문서가 큐/워커나 새 테이블을 채택한 것은 아니다. 동기 방식이든 별도 수용이든 클라이언트 응답 유실과 서버 최종 여부는 독립적으로 판정해야 한다.

## 기존 정본 코드 정적 대조

대조 파일: [postgres.ts](../canonical/ChurchOS_Canonical_v2.6/services/church-core/src/postgres.ts). r126 조사와 일치하는지 다시 읽었으며 실행하지 않았다.

| 코드에서 확인한 것 | 설계상 한계 |
|---|---|
| 자원 생성/변경 후 감사·성공 영수증 저장, 바깥 트랜잭션 COMMIT 후 반환 | 성공 반환 경로는 확인되지만 실제 소개 철회 수용/결과 API 구현 증거는 아님 |
| response_created_at에 자원의 created_at 사용 | 해당 요청의 수용 시각/최종 확정 시각으로 이름만 바꿔 사용 불가 |
| expires_at은 now()+24시간 | 기존 영수증 수명이며 새 본인 결과 창/조사 기한과 동일하지 않음 |
| COMMIT 오류 뒤 ROLLBACK 시도 | 이미 확정됐는지 불명인 오류를 롤백 시도만으로 미실행 판정 불가 |

같은 트랜잭션에 기록한 사건 시각도 정확한 물리 COMMIT 순간이라는 보장은 별도로 검증해야 한다. 서버가 확정을 확인한 시각을 저장한다면 그 의미를 구별하고 과거 실제 확정 순간으로 소급하지 않는다. 정확한 확정 시각을 확보할 수 없다면 미검증 값을 만들지 말고, 채택할 시각 의미/표시·조회 기산 정책을 다시 결정해야 한다.

## 판정 카드

| 관찰 | 허용할 판정 후보 | 금지 |
|---|---|---|
| 도착 기록만 존재 | 접수/결과 미입증 | 접수 완료 또는 실패 확정 |
| 수용 근거만 검증 | 모델이 허용하는 수용 사실 | 철회 성공 표시 |
| 업무·결과 근거가 동일 요청에 결속 | 검증한 최종 결과 | 현재 소개 상태로 옛 요청 보완 |
| COMMIT 응답 유실/연결 종료 | 특정 요청의 내구 근거 추가 확인 | 자동 재실행·실패 확정 |
| 영수증 만료/조회404 | 현재 조회 한계 | 원래 미실행·키 새로 발급해 재실행 |
| 늦은 최종 근거 발견 | 원래 사건 근거로 판정 | 발견 시각으로 기산 초기화 |
| 현재 결과는 검증됐으나 시각 불명 | 결과 근거와 시간 불명을 구별 | 임의 시각 생성·무기한 조회 허용 |

마지막 경우에는 현재 조회 자격/기간 판정이 가능한지도 별도로 확인해야 한다. 공개 상한이 미검증 시각을 생략할 수 있다는 뜻이지, 만료 검증을 건너뛰고 결과를 공개해도 된다는 뜻은 아니다.

## 최소 근거 관계와 수명

내부 후보는 요청 식별, 현재 본인/당시 대상 동의 세대 관계, 입력 동일성 확인에 필요한 최소 표현, 수용/결과 사건 근거, 업무 버전 결속, 시간 의미/권위, 정정/발견 관계다. 원문/사진·토큰·타제품 기록을 증빙에 복사하지 않는다. 단순 해시는 익명성이나 실제 커밋의 증명이 아니다. 모든 후보의 필수성·보유/삭제·백업은 별도 설계다.

조회 근거가 필요한 동안 결과를 검증할 수 있어야 하고, 중복 방지 보호는 조회 수명과 구별해야 한다. 기록 부재를 미실행으로 간주하지 않는다. 기존24시간을 무조건 연장하거나 새 기록을 영구 보유하는 선택을 이번에 하지 않았다.

다음 좁은 질문은 서버 도착/응답 시각이 아닌, 해당 요청과 결속된 내구 근거로 수용·최종 결과를 판정하는 원칙이다. 정확한 사건·시각 구현과 처리 모델은 여전히 별도 결정이다.
