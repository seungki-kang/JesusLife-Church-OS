## 범위와 근거

[REC-084 적용 인계](LEADER_INTRO_MINIMUM_RESULT_AGREED_HANDOFF.md), [r125 I/K/R/T/F 결속](LEADER_INTRO_WITHDRAWAL_REQUEST_BINDING_DRAFT.md), [r123 결과 확인](LEADER_INTRO_WITHDRAWAL_LOST_RESPONSE_RESULT_DRAFT.md)을 이어 기존 구현과 후속 설계의 차이를 정리한다. E 장기 증빙 조회는 후속이다. 이번 권고는 기술 선정 합의가 아니며 코드/DDL/마이그레이션을 변경하지 않는다.

정적 확인 범위는 보존된 canonical v2.6의 [postgres.ts](../canonical/ChurchOS_Canonical_v2.6/services/church-core/src/postgres.ts), [app.ts](../canonical/ChurchOS_Canonical_v2.6/services/church-core/src/app.ts), [commands.ts](../canonical/ChurchOS_Canonical_v2.6/services/church-core/src/commands.ts), [ports.ts](../canonical/ChurchOS_Canonical_v2.6/services/church-core/src/ports.ts)다. 해당 소스의 바이트는 보존했다. 현재 운영 배포·실DB 설정·실제 카탈로그와 동일한지는 미확인이다. 실행 테스트는 수행하지 않았다.

## 코드에서 확인한 사실과 확대하면 안 되는 의미

| 위치/동작 | 확인한 정적 사실 | 의미의 한계 |
|---|---|---|

| PgSession.create/mutate | tenant/actor/route/key의 트랜잭션 advisory lock·입력 해시 대조 | 경로/입력·actor 범위가 다른 새 철회 권한까지 보장하는 것은 아님 |
| create/mutate 성공 경로 | 업무 변경·append_event·성공 idempotency_record를 같은 client에서 처리 | 별도 선접수/작업 큐·본인 철회 실행이 구현된 것은 아님 |
| 기존 영수증 | now()+24 hours, 만료된 기존 키는409, 다른 입력은 충돌 | 물리 삭제된 키의 재접수/복원 후 안전성·새 WR 조회 기간을 보장하지 않음 |
| 생성 재전송 | 저장된 resource id/created_at와 일치 입력을 이용한 응답 구성 | 임의 과거 업무 원문/철회 증빙 조회에 재사용하면 안 됨 |
| 변경 재전송 | 현재 row_version이 저장 버전과 다르면 REPLAY_SUPERSEDED | 과거 성공 영수증이 있어도 후속 변경 이후 원래 성공 응답을 그대로 재현하지 않음 |
| roles·컨트롤러 | 유효 ACTIVE 소속/바인딩·현재 역할, 쓰기는 TENANT_ADMIN | REC-084의 소속 종료 후 본인 최소 확인을 그대로 지원하지 않음 |

외부 오류 감사 등 다른 경로가 있을 수 있지만 그것만으로 R/T와 결속된 최종 거절 영수증이 존재한다고 보지 않는다. 이 조사 범위에서 직접 확인한 함수와 실제 운영의 전체 경로를 구분한다. 일반 쓰기 컨트롤러/SessionPort에 소개 철회·WR 조회 계약은 확인되지 않았다.

## 시각 해석 — 접수·생성·커밋은 다름

기존 response_created_at는 자원 created_at를 저장한다. 변경 함수에서도 updated.created_at를 사용하며 이것을 변경 확정 시각으로 이름만 바꿔 쓰면 안 된다. now() 기반24시간 마감은 실제 서버가 업무 커밋을 확정해 응답한 순간부터24시간이라는 증거가 아니다. 따라서 기존 필드를 최초 내구 접수·최종 확정·조회 종료 시각으로 그대로 전환하지 않는다.

후보 계약에는 각각의 사건과 시각 권위가 필요하다. DB 기록 시각·커밋 후 관측 시각·최종 결과 확정 근거가 무엇을 뜻하는지 정의하고, 정밀한 실제 커밋 시각을 확보할 수 없으면 그 한계를 숨기지 않는다. 클라이언트 송신 시각이나 현재 시각을 누락값 대체로 넣지 않는다. 기간 기산은 아직 OPEN이다.

M1 권고 이유는 철회 효력 변경을 작은 서버 업무로 한정하고 현재 코드와의 이행 폭을 줄이기 위해서다. 실제 처리 시간/트래픽/외부 의존을 측정한 결과가 아니다. 사진 물리삭제/복원/알림이 오래 걸려도 본인 동의 효력 확정까지 그 작업을 모두 기다려야 하는지 별도로 구분한다. M1 선택 자체가 현재 코드의 보안·권한·결과 보유 문제를 해결하지 않는다.

M2를 나중에 택해도 일반 API 전체를 범용 명령 엔진으로 바꾸거나 모든 제품을 같은 큐/DB에 넣지 않는다. 이번에는 어느 모델도 운영/구현 채택하지 않았다.

## 결과 보유와 멱등 보호의 세 갈래

| 역할 | 필요한 것 | 첫 출시에서 남는 결정 |
|---|---|---|
| 업무 효력 정본 | 해당 동의 세대의 현재 공개 허용/차단 | 조회 창 종료가 철회 취소가 되지 않게 유지 |
| 최소 요청 결과 | 본인이 제출한 특정 요청 결과를 권한 안에서 확인 | I/K/R/T/F·성공/거절·시각·조회 창·삭제/백업 계약 |
| 옛실행/복원 보호 | 만료/정리 뒤 키·이전 원천/작업의 재등장 방지 | 유한 상한·현재 근거·퇴역/정리 조건과 검증 |

같은 영수증을 여러 목적에 재사용할 수 있는지는 별도 판정한다. 재사용하더라도 필드·접근·수명은 목적별로 분리해야 한다. 결과 확인 기간이 기존24시간보다 길면 ‘영수증24시간 종료 후에도 무엇을 조회하는가’가 명세돼야 한다. 그렇다고 조회 창을24시간으로 자동 결정하거나 영수증을 임의로168시간/90일로 바꾸지 않는다.

성공 변경 뒤 자원이 수정/삭제돼도 과거 특정 요청의 최소 확정 사실과 현재 자원 표현을 혼동하지 않아야 한다. 현재 row_version만 조회하는 재전송 응답은 WR의 과거 결과 확인을 완전히 대신하지 못한다. 반대로 WR을 위해 자원 원문 전체를 응답 스냅샷으로 보관하지 않는다.

## 성공·거절·부재의 저장 조건

- 성공: 업무 효력과 최소 최종 결과의 일관성을 보장하는 후보가 필요하다. 영수증 저장 실패시 업무가 확정됐는지의 진실을 검증해야 한다.
- 변경 없이 최종 거절: 실제 권한 검증과 해당 요청의 결속이 확인된 경우만 최소 결과를 검토한다. 거절을 기록하려고 실패한 업무 트랜잭션을 커밋하거나 권한 없는 대상 관계를 저장/공개하지 않는다.
- 인증 실패/잘못된 참조: 모든 입력을 내구 요청으로 등록하지 않는다. 토큰/입력 전문/타인 식별자를 결과 원장에 쌓지 않는다. 안전한 거절 감사와 본인 요청 결과는 목적이 다르다.
- 부재/조회 종료/접수 불명: 현재 없다는 관측만으로 실패 영수증을 새로 만들지 않는다. 실제 최종 거절과 구분한다. 재확인 또는 한정 지원은 기존 원칙을 따르며 대리 철회·자동 새 키는 금지한다.

거절 결과를 저장하는 별도 트랜잭션을 쓴다면 원래 시도와 결속·권한/상태 재검증·경합·보유를 명세해야 한다. 구체 구조는 OPEN이며 기존 롤백 경로를 문서로 성공 처리한 것은 아니다.
