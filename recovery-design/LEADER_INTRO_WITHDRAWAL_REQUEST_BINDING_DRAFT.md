# 본인 철회 요청의 최초 참조·접수·동의 세대·최종 결과 결속

2026-10-31 / r125 / REQUEST_BINDING_CONTRACT_DRAFT / PARTIAL_RECOVERY / 실행 NOT_RUN

## 범위와 권위

[REC-084 적용 인계](LEADER_INTRO_MINIMUM_RESULT_AGREED_HANDOFF.md), [r123 응답 유실 계약](LEADER_INTRO_WITHDRAWAL_LOST_RESPONSE_RESULT_DRAFT.md), [REC 원문](RECOVERY_DECISIONS.md)을 따른다. 교회 소속 종료 후 특정 본인 철회 요청의 최소 결과 확인은 합의됐으나, 아래 식별/접수/저장 방식은 기술 초안이다. 새 REC·기간·권한을 확정하지 않는다. E 장기 증빙 조회는 REC-083의 후속 범위를 유지한다.

이번의 식별자는 **논리 역할**이다. 새 UUID 종류/테이블/API를 모두 만들라는 의미가 아니며, 기존 식별자를 재사용할 수 있는지 실제 호출자·멱등 계약과 대조해야 한다. 본문 actor/tenant 값만 믿지 않고 현재 인증과 서버 관계를 검증한다.

## 식별 역할과 결속 조건

| 역할 | 생성/확인 후보 | 연결할 것 | 연결하지 않을 것 |
|---|---|---|---|
| 최초 의도 참조 I | 최초 전송 전 클라이언트 생성 후보 | 현재 본인·철회 행위·확인한 대상/동의 세대와 입력 의미 | 인증 자격/접수 증명·기기 시각 |
| 기존 멱등 키 K | 기존 API 계약을 유지/확장하는 후보 | tenant/actor/경로 범위·같은 의도의 고정 입력 | 다른 경로/세대·만료 키의 새 의도 |
| 서버 요청 참조 R | 내구 접수와 결속해 서버 생성/확인 후보 | 인증된 본인·I/K·서버가 검증한 대상·실제 접수 시각 | 화면 클릭·HTTP 연결 성공만으로 접수 확정 |
| 대상 결속 T | 서버가 확인하는 교회/소개/동의 세대 | 그 요청이 명시적으로 철회할 범위 | 최신 동의·동명 조직·새 계정으로 치환 |
| 최종 결과 F | 실제 업무 확정 근거와 함께 기록 | R/T·결과 종류·실제 확정 시각·필요한 최소 감사 | 현재 상태만 보고 과거 실행 결과 재구성 |

I와 K를 동일 값으로 쓸지 별도로 결속할지는 OPEN이다. 임의로 두 멱등 실행기를 병렬 생성하지 않는다. R은 결과 조회용 불투명 참조이며 비밀 토큰/권한 증명이 아니다. 필요한 T는 내부 결속 대상이지 본인 화면의 추가 공개 필드로 채택하지 않는다.

같은 I/K를 받았을 때 대상·세대·의미가 다르면 새 실행이나 자동 재결속을 하지 않는다. 충돌 응답 자체가 다른 사람의 요청/자료 존재를 노출하지 않아야 한다. 입력 비교의 정규화·버전·해시 사용 여부는 기술 명세로 정하며 해시가 익명성/본인 의사 증명이 된다고 보지 않는다.

## 접수 모델 비교 — 현재 구현과 구분

| 모델 | 장점 | 필요한 조건/한계 |
|---|---|---|
| 동기 원자 확정 | 업무 변경·최종 결과·멱등 영수증을 하나의 트랜잭션에서 확정하는 후보 | 커밋 전 프로세스 종료에는 R이 없을 수 있음. 없는 기록으로 미실행을 단정하지 않음 |
| 먼저 내구 접수 후 처리 | I/K→R 접수 사실을 먼저 남길 수 있음 | 미처리/재시작/중복 실행/실행 임대·최종 확정·유한 종결 계약이 추가로 필요 |

v2.6의 동기 처리·성공 영수증을 두 번째 모델이 이미 존재하는 것처럼 설명하지 않는다. 이번에는 어느 모델도 최종 선정하지 않았다. 내구 접수 상태를 제공하려면 실제 재시작 후 남는 기록과 실행/복구 계약이 있어야 한다. 접수 행만 만들고 처리 중 상태를 무기한 유지하는 것은 해결이 아니다.

공통 요구는 ‘업무가 확정됐는데 요청 결과 근거가 없어 성공 여부를 임의 추측하는 구조’를 피하는 것이다. 동의 상태 변경·최종 결과·필요한 감사의 원자성 또는 검증 가능한 복구 방식이 필요하다. 트랜잭션 경계/외부 사본 효과는 별도 명세하며 외부 삭제까지 같은 DB 커밋으로 완료됐다고 표시하지 않는다.

## 최초 응답 전후의 조회 분기

| 관측 | 서버 확인 동작 후보 | 본인 안내/허용 행위 |
|---|---|---|
| R 수신, 최종 응답 유실 | 현재 본인+R의 정확한 관계/목적/기한 확인 | 해당 요청 최소 결과만 조회 |
| R 미수신, I/K 보존 | 인증된 본인·행위/범위에 결속된 I/K로 기존 R/F를 확인하는 후보 | 기록이 확인된 경우만 접수/최종 안내, 쓰기 재전송과 조회를 분리 |
| I/K/R 모두 소실 | 임의 시간/이름 검색으로 결과를 맞추지 않음 | 최소 확인 경로/지원 검토, 새 전체 이력 목록 제공 금지 |
| 기록 없음/조회 불가 | 권한·조회 창·정리/복원·접수 불명 가능성을 구분해 내부 검토 | ‘결과를 확인할 수 없음’, 미실행/안전 재실행으로 해석 금지 |
| 현재 동의는 철회, F 근거 없음 | 현재 상태와 과거 요청 결과를 구분 | 현재 철회 관측을 이 요청의 완료 증명으로 바꾸지 않음 |
| 같은 I/K, 다른 T/입력 | 다른 의미 충돌을 검출 | 새 세대로 자동 연결하거나 새 실행 금지 |
| 실제 다른 요청이 먼저 철회 | 각각 요청의 확정 근거 대조 | 원래 요청이 수행한 것처럼 소급 성공 구성 금지 |

R 미수신 조회를 실제로 제공하려면 해당 I/K의 서버 결속과 제한 검색 방식이 있어야 한다. 현재 존재한다고 주장하지 않는다. 멱등 키 만료·물리 정리 후에도 과거 I를 새로 접수해 재실행하지 않도록 기존 보호/유한 상한 계약과 연결한다. 조회 목적의 읽기가 새 접수/실행을 발생시키지 않아야 한다.

## 불변 조건 — 구현 인계 초안

1. 인증 actor·제품/API 목적·교회/소개/동의 세대·철회 의도를 서버에서 결속한다. 계정 표시명/이메일·번호 소지로 대신하지 않는다.
2. 같은 의도는 같은 입력 의미를 유지한다. 대상이 바뀌면 원래 요청을 수정해 덮지 않는다. 새 의도가 필요한 경우에도 이전 미확정 요청과 현재 상태를 먼저 판정한다.
3. 확정된 결과는 다른 요청 결과로 덮거나 재시도로 확정 시각을 초기화하지 않는다. 별도 정정 권한/절차는 이 초안으로 신설하지 않는다.
4. C1 철회 요청이 미확정/완료인 동안 C2가 생성돼도 C1 조회/늦은 실행을 C2에 붙이지 않는다. 새 토큰·새 키가 과거 의도를 현재의 새 게시/철회 의도로 바꾸지 않는다.
5. 조회는 매번 현재 본인 관계와 유효한 목적을 검증하며 일반 교회 자료·전체 이력을 공개하지 않는다. 소속 재가입/관리자 승인은 요구하지 않는 REC-084를 유지한다.
6. COMMIT 결과 불명 뒤 ROLLBACK 시도만으로 업무 실패를 단정하지 않는다. 응답 유실·404·기록 없음으로 자동 새 키/새 철회 실행을 만들지 않는다.
7. 기기 계정 전환·로그아웃·화면 종료 후 늦은 응답을 다른 계정/동의 화면에 반영하지 않는다. 기기 참조 수명/OS 백업은 별도 계약이다.
8. 조회 결과 확정과 실제 저장/사본 삭제 완료를 분리한다. 감사/복원 보호 목적에 개인 원문·사진을 복제하지 않는다.

## 보존/복원과 호환성

기존 v2.6 Idempotency-Key 범위·24시간 성공 영수증·만료 키 거절은 변경하지 않는다. I→R→F가 그 영수증을 재사용할지 조회용 최소 참조를 보완할지는 미결이다. 일반 Q의168시간이나 E 후보30/90일을 이번 WR 기간으로 이식하지 않는다.

각 I/K/R/T/F의 목적·접근·기산·유한 보유·실제 삭제 마감·백업/처리자·복원 재적용을 정해야 한다. 결속 참조를 영구 보유하거나 모두 지웠으니 오래된 요청을 새 의도로 인정하는 양쪽 오류를 피한다. 과거 원천/큐·구앱/직접 DB 경로까지 기존 GS01~05/FG01~06에서 검증해야 하며 현재 실제 환경 근거는 미확인이다.

새 논리 역할을 위해 모든 제품에 공통 원문 저장소나 범용 명령 실행 서비스를 추가하지 않는다. ChurchOS의 소개 동의/철회 정본과 현재 인증 계약의 경계를 유지한다. 다른 제품의 실제 모바일/MySQL/Core 테스트 결과를 이 계약의 성공 근거로 승계하지 않는다.
