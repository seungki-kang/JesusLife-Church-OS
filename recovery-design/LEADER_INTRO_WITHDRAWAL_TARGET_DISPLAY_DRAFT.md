# 본인 소개 철회 대상의 최소 표시·확인 계약 초안

2026-10-30 / r98 / TECHNICAL_DRAFT + DISPLAY_POLICY_PROPOSAL / PARTIAL_RECOVERY / 실행 NOT_RUN

## 목적·합의 경계

[REC-076](RECOVERY_DECISIONS.md#rec-076-종료-후-본인-소개-동의-철회)의 종료 후 본인 철회 접근을 [r96 접근 검토](LEADER_INTRO_WITHDRAWAL_MINIMUM_ACCESS_REVIEW.md), [CMND04](LEADER_INTRO_COMMAND_END_TO_END_CONTRACT_DRAFT.md), [DG04/05·FD02/03](LEADER_INTRO_STAGE_GATE_CLASSIFICATION.md)에 연결한다. 이번 문서는 표시·발견·확인 절차의 제안이다. REC-076의 철회 자격은 다시 묻지 않으며 새 표시 정책을 AGREED로 간주하지 않는다.

사용자가 얻는 결과는 ‘어느 교회·어느 공동체의 어느 소개 동의를 철회하는지 알아보고 그 한 범위만 확정’하는 것이다. 원문·사진 미리보기나 종료 교회 메뉴 재접속 없이 앱에서 수행한다. ChurchOS가 소개 동의 정본과 본인 관계를 검증한다. 공통 인증은 본인 확인 근거를 제공하되 전체 제품의 동의 목록을 모으지 않는다. CHGO 추론/이름 유사도는 대상 식별 근거가 아니다.

## 화면의 최소 표시 제안

| 항목 | 기본 표시 후보 | 최소화·정확성 조건 |
|---|---|---|
| 교회 | 해당 동의에 결속된 교회 표시명 | 현재 교인 명단/교단/주소/목회자 이름을 덧붙이지 않음 |
| 공동체 | 해당 동의에 결속된 공동체 표시명 | 조직도·다른 공동체 목록·다른 리더를 보여주지 않음 |
| 철회할 범위 | ‘이 공동체 참여자에게 내 리더 소개 공개’처럼 기록된 동의 범위의 짧은 설명 | 기록이 뒷받침하는 범위만; 교회전체/인터넷 동의가 있다고 추정하거나 일괄철회 안 함 |
| 동의 상태 | 유효/철회됨/확인 중 등 서버가 확인한 동의 상태 | ‘동의 유효’와 ‘현재 공개 중’을 동일시하지 않음; 공개 여부를 모르면 단정 안 함 |
| 구분 표식 | 중복 이름일 때만 본인 범위의 짧은 구분 코드 | 코드만으로 선택을 강요하지 않음; UUID/계정/교인번호 노출 안 함 |

예시(합성): ‘한빛교회 / 청년공동체 / 이 공동체 참여자 대상 / 동의 유효 / 구분 K7M2’. 아래 안내: ‘동의 상태는 현재 게시 여부와 다릅니다. 철회해도 직함·소속·다른 제품 기록은 바뀌지 않습니다.’ 소개 제목/본문 일부, 사진 썸네일·URL·EXIF, 연락처, 담당자 이름, 다른 교인의 정보, 가입·정지 사유, 활동 이력은 표시하지 않는다. 화면 예시는 문구 후보이며 실제 데이터/화면 구현이 아니다.

이름이 바뀐 경우 기본 후보는 본인이 동의할 때 확인했던 표시명이며 ‘동의 당시 명칭’이라고 명시한다. 적법하게 남아 있는 본인 동의 증빙의 최소 명칭을 사용하는 후보이지 새 과거 명칭 영구 저장 승인이 아니다. 현재 명칭으로 조용히 대체해 다른 대상처럼 보이게 하지 않는다. 과거 명칭이 없거나 오기/동명이라 식별이 불충분하면 추측 표시/추론 병합 대신 제한 확인으로 보낸다. 현재 명칭 병기나 본인 동의 시각을 추가 표시해야 하는 경우는 별도 필요성 검토다.

짧은 구분 코드는 화면 항목과 서버 대상의 일관된 대응을 돕는 보조 수단이다. 다른 계정/교회 데이터와 공통으로 상관분석할 수 있는 전역 코드로 만들지 않는다. 코드의 길이·충돌 처리·유효기간은 기술 미결이며 코드는 인증/권한 증명이 아니다. 같은 명칭의 여러 동의가 사람이 구별할 수 없으면 임의 첫 항목 선택이나 전부 철회를 제안하지 않는다.

## 발견부터 확인까지

| 단계 | 사용자 행위 | 서버·앱 조건 | 실패/이탈 처리 |
|---|---|---|---|
| WD01 진입 | 앱의 본인 공개 관리 진입점 선택 | 현재 공통 인증·서비스 상태·REC-076 목적 자격 검증 | 로그인 실패·정지/탈퇴는 별도 제한 절차; 교회 재가입 요구 안 함 |
| WD02 대상 목록 | 본인 대상 중 하나 선택 | 서버 소유 관계로 한정한 최소 목록; 개인정보 없는 페이지 처리 후보 | 로딩 실패/권한 미확인/빈 결과 구분; 빈 목록을 전체 철회 완료로 안내 안 함 |
| WD03 확인 | 선택한 교회·공동체·범위·동의 상태를 다시 읽음 | 같은 대상 참조·동의 세대·표시 버전 결속 | 계정 전환/다른 대상/범위 변경이면 확인 취소·최신 내용 재확인 |
| WD04 철회 | ‘이 소개 공개 동의 철회’ 명시 버튼 선택 | 현재 본인·대상·범위 검증 후 CMND04로 전달 | 대상 기본 선택 없음; 스크롤/뒤로가기/화면 진입만으로 실행 안 함 |
| WD05 결과 | 서버 확인 결과 또는 확인 중 안내 | 요청 결과와 현재 동의/공개 상태를 분리 | 응답 유실은 조회 우선·자동 새 키 실행 금지 |

기본 진입은 교회 전환 메뉴가 아닌 본인 관리 영역 후보다. 종료 교회의 자료 접근을 복구하지 않는다. 목록·검색은 서버가 본인 관계로 먼저 제한한다. 전 교회/타인 동의 검색이나 클라이언트 tenant/account 필터에 의존하지 않는다. 모든 대상 개수를 타인/다른 계정에게 알려주지 않는다. 로그인하지 않은 공유 링크/알림/딥링크에는 교회·공동체 명칭이나 동의 상태를 담지 않는 후보로 두고 인증 후 서버에서 대상과 권한을 확인한다.

목록 발견은 r86의 일반 업무 후속 결과 찾기와 별도 목적 계약이다. REC-029의 일반 조회 소속 조건을 완화하거나 REC-031의 다섯 결과 항목에 위 대상 표시 필드를 추가하지 않는다. 후보 응답은 ‘대상 선택용 최소 설명’과 ‘철회 요청 결과’로 계약을 분리한다. 실제 endpoint/DTO는 아직 선정하지 않는다.

## 명령 결속과 변경·삭제 경계

화면 표시는 권한이 아니다. 서버는 불투명 대상 참조를 받더라도 actor를 현재 인증에서 도출하고 교회/공동체/소개/동의 소유 관계를 다시 확인한다. 대상 식별자만 알거나 화면 코드가 일치한다고 쓰기를 허용하지 않는다. 다른 계정의 존재·교회 관계를 오류 응답으로 노출하지 않는 세부 오류 계약이 필요하다.

사용자가 확인한 동의 범위와 실제 철회 대상이 다르면 실행하지 않는다. 같은 소개에서 새 동의 세대가 생겼다면 옛 확인/옛 요청이 새 동의를 자동 철회하거나 새 게시를 복구하지 않도록 세대를 결속하는 후보를 검토한다. 이미 철회한 동일 대상은 중복 업무 이력을 만들지 않고 사실에 맞게 안내한다. 직함 종료로 이미 게시가 중단됐어도 잔존 동의를 철회할 수 있다. ‘게시 중단됨’을 ‘동의 철회됨’으로 바꾸어 안내하지 않는다.

삭제된 대상은 원문/사진/예전 명칭을 복원해 선택 화면을 만들지 않는다. 적법하게 남아 있는 최소 증거만으로 본인·범위를 확인할 수 있는 경우와 참조 자체가 없는 경우를 구분한다. 404/만료/조회 실패만으로 이미 철회/삭제/미실행을 단정하지 않는다. 동의 목록의 발견 기간·표시 자료 보유·멱등 결과·기기 참조 수명은 서로 다르며 이번에 168시간/30일/1년을 정하지 않는다.

표시 버전이 바뀌어 재확인이 필요하더라도, 원문을 보여주거나 관리자 승인을 받는 단계로 대체하지 않는다. 범위가 그대로인 단순 표시명 변경까지 반드시 철회를 막아야 하는지와 최신 표시 재확인 방식은 기술/UX 검토 항목이다. 권한 검증을 건너뛰는 낙관적 성공 화면은 두지 않는다.

## 기기·접근성·감사

오프라인에서는 원문 없는 과거 대상 목록을 신뢰해 철회 완료를 표시하거나 자동 전송 대기열을 만들지 않는다. 기본 후보는 이 화면의 목록을 영속 캐시하지 않고 민감한 화면 내용의 분석 로그 수집을 제외하는 것이다. 로그아웃/다른 계정 전환 시 대상 선택·확인 결속을 제거하고, 늦은 응답은 현재 계정과 맞지 않으면 폐기한다. 같은 계정 교회 전환 시 다른 교회 자료로 섞지 않으며 목적 범위는 서버에서 다시 확인한다. 기존 기기 요청 참조 정책은 보존한다.

버튼은 색/아이콘만으로 구분하지 않고 교회·공동체·범위를 읽을 수 있는 접근성 레이블을 제공한다. 구분 코드를 화면 읽기 도구로 낭독할 때도 다른 계정 식별자를 쓰지 않는다. 목록 항목 선택과 최종 철회 실행은 분리하되 추가 승인자·불필요한 원문 확인을 요구하지 않는다.

최소 감사 후보는 actor·대상 동의/범위 참조·처리 시각·결과이며 명칭/원문/사진·토큰을 반복 복제하지 않는다. 실제 감사 보유·허용 열람·거절 관측은 FD02/05에서 확정한다. 플랫폼 지원은 소유 미확인 건을 안내할 수 있어도 대신 동의·대신 철회·교회 관리자 열람권을 자동 취득하지 않는다.

## 검증 인계와 남은 결정

- CA143: 동명·명칭 변경·대상 여러 개·삭제/누락 시 원문 없이 안전하게 선택하며 모호하면 추측 실행하지 않음. 타인/다른 계정 대상 치환과 전체 목록 조회 차단.
- CA144: 확인 후 동의 세대/범위 변경·계정 전환·응답 유실·이미 철회/공개중단/삭제 상태를 구분하며 옛 확인으로 다른 동의를 바꾸지 않음.

두 조건은 새 설계 시나리오이며 전체 CA144개 모두 실행 NOT_RUN이다. 기존 18B·DG04/05·FD02/03/05는 남아 있다. 본문 필드/문구/발견/기한/재인증/API 후보를 일괄 합의로 표시하지 않는다.

정책 질문은 하나로 좁힌다: 철회 대상 화면에 본인 동의와 연결된 교회명·공동체명·공개 범위·동의 상태만 표시하고, 중복 시 구분 표식으로도 구별되지 않으면 추가 확인으로 넘기는 기준을 채택할까요? 명칭 변경 시 동의 당시 명칭 사용·최소 증빙 수명 등은 세부 검토로 남긴다. 기본 권장안은 이 최소 표시다.

## r99 후속 결정 — REC-077

[REC-077 철회 대상 최소 표시와 모호성 확인](RECOVERY_DECISIONS.md#rec-077-철회-대상-최소-표시와-모호성-확인): 본인 철회 대상은 교회명·공동체명·공개 범위·동의 상태만 표시하고 중복 구분 보조 표식으로도 모호하면 추가 확인으로 넘기는 최소 표시 기준을 확정했다. 소개 원문·사진·연락처·다른 교인 정보는 표시하지 않는다. 위 r98 PROPOSED/질문은 당시 이력이다. 현재 합의는 REC-077 최소 표시 및 모호성 경계이며 과거명칭 사용·표식 규격·발견/기간·API·캐시 후보는 여전히 DRAFT/OPEN이다. 실행 NOT_RUN.
