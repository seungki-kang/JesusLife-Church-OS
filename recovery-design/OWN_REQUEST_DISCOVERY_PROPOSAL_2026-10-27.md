# 기기 기록 손실 후 본인 요청 찾기

> 현재성 안내: 부분 합의·과거 제안·기술 초안을 구분합니다. [결정 색인](RECOVERY_DECISIONS.md)과 [현재 상태](../START_RECOVERY_CURRENT.md)을 함께 읽으세요. 상단 AGREED가 모든 기술 항목의 승인을 뜻하지 않습니다.

2026-10-27 / 본인 요청 최소 상태 발견 기능 범위 AGREED / 나머지 DISCOVERY_FLOW_PROPOSAL / 구현·실행 NOT_RUN

확정 근거: 사용자가 직전 ‘내 처리 확인’ 기능 제공 범위 질문에 “네”로 동의했다. 기기 기록 소실 후 재로그인하여 현재 선택 교회의 유효 소속을 검증한 본인에게 최소 요청 상태 발견을 제공한다. 원문·업무 내용·타인 요청은 제외한다. 미확정 발견 수명·추가 필드·페이지·API 경로 등은 미결이다.

※ 후속 갱신(r27 주): 미확정 발견 기한은 이후 REC-030(실제 최초 서버 접수+168시간)으로 합의됐다. 위 문장은 r17 당시 질문 범위의 기록이다. 추가 필드는 REC-031의 다섯 항목을 따른다.

## 1. 목적과 범위

누적 r15를 이어 작성한다. 로그아웃 시 기기 확인 기록을 제거한다는 합의를 유지하면서, 재로그인·앱 재설치·기기 변경 후에도 중복 업무를 만들지 않고 결과를 확인할 경로를 설계한다. 이번 문서는 일반 업무 요청의 최소 상태 발견 기능을 새로 제안한다. 기존 직접 상태 조회 권한을 목록 공개로 자동 확대했다고 간주하지 않는다. 다른 제품의 개인 기록·초안·내용을 복원하는 기능이 아니다. 부분 복원 상태 유지.

## 2. 권장 화면

앱의 본인 영역에 ‘내 처리 확인’을 제안한다. 사용자가 직접 열면 현재 선택 교회의 본인 요청만 연결 상태에서 확인한다. 전체 교회 통합 목록·다른 담당자 목록·관리자에 의한 타인 요청 검색은 이 기능에 포함하지 않는다.

표시 후보는 요청 확인 번호, 제출 시각, 처리 상태, 최종 확정 시각, 조회 가능 기한이다. 사람 이름·업무 제목·대상 명단·본문·변경 값·사유·감사 이력·개별 대상 ID는 표시하지 않는다. 현재 공개 다섯 항목은 REC-031로 합의됐다. 제출 시각은 서버 접수 시각과 혼동하지 않으며 필드 대응표를 따른다. 같은 시각에 여러 업무가 있으면 사용자가 내용으로 구분하지 못할 수 있으므로 목록 선택으로 새 실행·취소·정정을 하지 않는다.

## 3. 조회 자격

- 인증된 공통 계정과 현재 ChurchOS 이용 상태를 확인한다. 서버가 확인한 계정 ID로 요청 소유자를 제한한다. account_id·이메일·표시 이름을 검색 입력으로 받지 않는다.
- 현재 선택 교회의 유효 소속을 검증한다. 교회 역할이 없어진 경우에도 유효 소속을 유지하면 본인 최소 상태 조회 범위 내에서만 목록을 허용하는 안이다.
- 소속 탈퇴·정지·유효성 확인 불가이면 해당 교회 요청 존재·상태·개수·제출 시각도 공개하지 않는다. 접근 확인 안내만 제공한다.
- 교회 관리자라고 타인의 요청 발견 권한을 자동 부여하지 않는다. 별도 운영 조사 권한은 별도 계약이다.
- 공통 계정의 단순 로그인 성공만으로 교회 요청을 조회할 수 없다. 이름·이메일 일치, 기기 지문, 다른 제품의 프로필로 자동 연결하지 않는다.

## 4. 발견 대상과 기간

| 요청 | 목록 포함 제안 | 제한 |
|---|---|---|
| 최종 COMMITTED·REJECTED | 실제 최종 서버 확정부터 168시간 이내 | 기존 기한을 재로그인·발견·조회로 초기화하지 않음 |
| 미확정·수동 확인 필요 | 실제 최초 서버 접수+168시간 이내 | 무기한 공개·보관을 기본으로 하지 않음 |
| 최종 상태 조회 만료 | 제외 | 미실행·실패라고 판단하지 않음 |
| 다른 계정·다른 교회 요청 | 제외 | 개수·페이지 정보에도 반영하지 않음 |

미확정 발견 기한은 REC-030으로 실제 최초 접수+168시간으로 합의됐다. 수명이 확정되지 않은 채 운영 목록을 무기한 제공하지 않는다. 최초 실패·결과 불명부터 24시간 내 수동 확인 이관이라는 기존 기준과 별개로, 미확정을 가짜 최종 상태로 전환해 168시간 기산점을 만들지 않는다. 보유·삭제·복구 설계가 끝나기 전 운영 구현을 시작하지 않는다.

## 5. 후보 API와 데이터

GET /api/v1/church/tenants/{tenant_id}/commands/mine/statuses

기존 직접 조회 후보 /commands/{request_id}/status와 별개의 신규 계약 후보다. 기존 라우트와 충돌 여부는 미검증이며 특히 고정 경로 mine과 동적 경로의 판별을 명시해야 한다.

서버는 검증된 계정·교회로 먼저 필터링한 후 페이지를 구성한다. 응답 항목의 최신 대응은 PUBLIC_STATUS_FIELD_MAP.md를 따른다. request_id·status·accepted_at·confirmed_at(최종일 때)·query_expires_at의 다섯 항목만 의미상 허용한다. 정확한 필드명과 페이지 메타데이터는 초안이다. 전체 개수는 기본 제공하지 않는다. 페이지 크기·조회 빈도·정렬·속도 제한 수치는 미결이다. 커서는 계정·교회·필터·만료에 결합해 변조·다른 계정 재사용을 차단해야 하며 구체 형식은 미결이다.

응답·페이지 이동 시마다 현재 권한을 다시 검증한다. 커서 발급 시 유효했다는 이유로 탈퇴 후 다음 페이지를 제공하지 않는다. 조회 응답은 보호 데이터이며 공유 캐시·외부 검색·분석 로그에 저장하지 않는다.

## 6. 결과 없음·조회 실패

권한 내에서 목록이 비어도 ‘처리 확인 목록이 없습니다’라는 일반 안내를 제안한다. ‘요청이 전송되지 않았습니다’ 또는 ‘저장되지 않았습니다’로 표시하지 않는다. 접수 전 통신 단절, 확정 결과 조회 만료, 기록 손실·복구 중, 다른 교회 선택 등 여러 이유가 있을 수 있다.

기존 기록을 찾지 못하면 현재 권한으로 업무 원본을 별도 확인하거나 허용된 운영 문의 경로로 이관한다. 이 화면에서 새 요청 식별자를 발급해 이전 업무를 자동 재실행하지 않는다. 반복 결과 확인도 요청 수행이나 권한 연장을 유발하지 않는다.

## 7. 세션 전환·다중 기기

같은 계정으로 다른 기기에 로그인해도 그 기기의 현재 교회 소속 검증을 통과해야 한다. 목록은 서버의 허용된 최소 상태에서 읽으며 다른 기기의 기도·일기·토큰·명령 본문을 복사하지 않는다.

로그아웃·계정 변경·교회 전환 중 늦게 도착한 목록 응답은 이전 세션·교회 응답으로 판별해 적용하지 않는다. 앱이 백그라운드에서 돌아왔을 때 이전 목록을 즉시 재공개하지 않고 필요한 현재 접근 검증을 수행한다. 구체 메모리 초기화·OS 화면 보호·네트워크 캐시 기술은 후속 구현 명세다.

## 8. 설계 수용 조건 — 실행 테스트 아님

- 기기 기록을 삭제한 뒤 같은 계정·유효 교회 소속으로 로그인하면 허용된 본인 요청만 찾는다.
- 다른 계정·교회 항목과 개수·커서 정보가 섞이지 않는다.
- 소속 상실 후 목록·다음 페이지·기존 응답 재표시를 차단한다.
- 최종 확정 168시간이 지나면 발견 목록에서도 제외한다.
- 목록 조회·복구로 완료 시각·조회 기한·업무 권한이 늘어나지 않는다.
- 빈 목록으로 미실행을 단정하거나 자동으로 새 저장을 하지 않는다.
- 관리자 권한만으로 타인의 요청을 검색하지 못한다.

## 9. 확정 질문과 답변

기기 기록이 없어져도 재로그인 후 ‘현재 선택 교회의 본인 요청 최소 상태’만 다시 찾는 화면을 제공할까요?

답변: 네. 2026-10-27 기능 제공 범위 설계 합의. 원문·업무 내용·타인 요청은 제외하는 안을 권장한다.

이번 질문은 발견 기능의 제공 범위에 한정한다. 미확정 발견 수명·추가 필드·페이지·API 경로·기술 구현의 일괄 확정은 아니다. 코드·파일럿·GitHub 반영 없음.
