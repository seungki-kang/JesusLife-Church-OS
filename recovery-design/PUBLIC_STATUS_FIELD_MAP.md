# 처리 확인 다섯 공개 항목과 과거 필드 대응

> 현재성 안내: 부분 합의·과거 제안·기술 초안을 구분합니다. [결정 색인](RECOVERY_DECISIONS.md)과 [현재 상태](../START_RECOVERY_CURRENT.md)을 함께 읽으세요. 상단 AGREED가 모든 기술 항목의 승인을 뜻하지 않습니다.

2026-10-28 / 의미 범위 REC-031 AGREED / 정확한 JSON 이름·경로·이행 DRAFT

| 확정 의미 | 통일해 읽을 후보 이름 | 과거 표기 | 해석/이행 |
|---|---|---|---|
| 요청 확인 ID | request_id | request_id | 기존 Idempotency-Key와 연결 방식 OPEN. 키는 경로별로만 유일하므로 키 값을 그대로 쓰면 조회가 모호하다. 서버 발급 불투명 ID 권장안은 [기준선 대조](IDEMPOTENCY_BASELINE_ALIGNMENT.md) 참조. 새 실행 식별 체계를 추가하지 않음 |
| 처리 상태 | status | status | 상태 enum은 초안. 기존 서버의 처리 중 상태 구현을 뜻하지 않음 |
| 서버 최초 실제 접수 시각 | accepted_at | submitted_at | 기기 submitted_at_local과 다름. 실제 증거 없는 기존 영수증을 소급 접수로 만들지 않음 |
| 실제 최종 확정 시각 | confirmed_at | confirmed_at | 최종 확정된 경우에만. 업무 생성/트랜잭션 시작과 자동 동일시하지 않음 |
| 현재 상태 조회 만료 | query_expires_at | status_expires_at | 미확정·최종 각 실제 기산점+168h. 영수증 expires_at(24h)과 다름 |

과거 4개 필드 응답 후보는 최신 5개 의미 범위로 갱신한다. 정확한 API 필드 이름 변경/호환 이행을 이번 문서로 실행하지 않는다. submitted_at이 과거 서버 접수를 뜻했는지 증거 없이 자동 변환하지 않는다. 응답의 이름·제목·대상·원문·변경값·상세 사유는 제외한다. 페이지 커서는 업무 내용이 아닌 전송 제어 후보이며 필요성·권한·만료를 별도 검토한다. 푸시에 이 다섯 항목을 넣어도 된다는 합의가 아니다.

## r28 연결 계약 참고

[송신 전 기기 참조와 서버 확인 ID](SUBMISSION_RECEIPT_BINDING_DRAFT.md)를 함께 적용한다. 서버 확인 ID가 없는 응답 유실은 새 쓰기나 새 키 발급으로 해결하지 않는다. 연결 ID·정확한 경로 범위·영속 접수·읽기 연결의 구체 방식은 DRAFT다. 다섯 공개 항목 합의에 기기 내부 필드를 추가 공개하지 않는다.
