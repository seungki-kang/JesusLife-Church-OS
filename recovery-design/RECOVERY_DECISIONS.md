## REC-033 공동체 참여 대상

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 질문 “공동체 참여 대상을 해당 교회의 가입 승인된 유효 소속 교인으로 제한하는 권장안으로 확정할까요?”에 사용자가 “네”라고 답함. 이 문서는 그 대화 내용을 기록한 것이며 소실 문서 복구나 실제 구현 증거가 아니다.
- 결정: 공동체의 신규 참여 대상은 해당 교회에서 가입 승인된 유효 소속 교인으로 제한한다. 가입 대기·거절·정지·탈퇴 상태와 다른 교회에만 소속된 사람은 새 참여 대상으로 허용하지 않는다. 다른 교회 소속자는 대상 교회 가입 승인 후 현재 자격으로 판단한다.
- 방문자·외부 봉사자는 자동 교인/공동체 구성원으로 등록하지 않는다. 필요한 행사 참여 경로는 추후 별도 검토하며 이번 결정으로 모든 공개 행사 참여를 금지하지 않는다.
- 과거 참여자의 현재 접근 자격과 과거 출석·활동 이력 보유를 분리한다. 현재 무자격을 과거 기록 포괄 삭제로 처리하지 않는다.
- 이유: 교회 가입 승인 우회와 명단/자료 접근 확대를 방지하며 실제 교회 운영 사실을 개인 영성 기록과 분리한다.
- 검토 대안: 방문자/외부인을 일반 공동체 구성원에 함께 포함하는 방식은 이번 기본 경로에 채택하지 않는다. 별도 방문자 경로는 미결이다.
- 확정하지 않은 것: 공동체 신청 심사/자동승인, 관리자 배정 본인수락/기한, 복수/주공동체, 이동 확정 방식, 리더/명단 공개, 탈퇴/보관, 정지 해제/재가입 후 참여 회복 방식·보유기간·API/DDL.
- 영향: 공동체 상세·작업 인계·수용 시나리오·MVP16·용어집·현재 안내. 서버는 실제 처리의 최신 자격을 검증해야 하며 검사 시점/최종확정 경합 기술은 후속 계약이다.
- 증거/한계: 문서 합의만 기록. 코드·DB·앱·실제 권한/연동 검증 NOT_RUN. 기존 COS/REC001~032 범위는 변경하지 않음.

## REC-034 공동체 본인 신청 수동 승인

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 질문 “본인이 공동체 가입을 신청하면 교회 관리자 또는 해당 공동체의 명시적 참여심사 권한을 받은 담당자가 승인한 뒤 참여하도록 하는 수동 승인 방식으로 확정할까요?”에 사용자가 “네”라고 답함. 기록한 질문은 직전 제안/질문의 의미를 함께 명시한 것이며 원문 파일 복원이나 구현 증거가 아니다.
- 결정: REC-033 자격을 갖춘 본인의 공동체 참여 신청은 자동 승인하지 않는다. 해당 교회 현재 유효 관리자 또는 해당 공동체의 명시적 참여심사 권한을 받은 현재 유효 담당자가 승인한 뒤 참여하도록 한다.
- 권한 경계: 리더/보조리더/목회자 직함이나 교회 가입심사 권한만으로 공동체 신청을 승인할 수 없다. 승인자는 현재 교회·대상 공동체·행위 범위와 유효 권한을 검증받아야 한다. 본인 신청 접수만으로 참여 명단/보호자료 접근권을 만들지 않는다.
- 이유: 교회 가입과 별개인 공동체 운영·대상 확인을 유지하고 직함만으로 권한이 확장되는 것을 방지한다.
- 대안: 본인 신청 즉시 자동 가입하는 방식은 이번 기본 흐름에 채택하지 않는다. 교회별 자동승인 선택 기능도 이번 결정으로 승인하지 않는다.
- 미결: 참여심사 담당자의 지정 주체/자격/수락/임기 상세, 자기 신청 자기 심사 여부, 표준 거절 사유/통지, 신청 취소·동시 처리 기술, 관리자 배정 제안의 본인 수락·기한, 이동·리더·명단·탈퇴/종료·수명. 교회 가입 승인 담당자의 특별 규칙을 그대로 복사하지 않는다.
- 영향: 용어집·공동체 계약/작업 인계/수용 시나리오·MVP16·현재 안내/게이트/인벤토리. REC-033과 이전 합의는 유지한다. REC-033 기록의 당시 미결 중 신청 승인 방식만 이번 합의로 해소한다.
- 구현 차이: 공동체 신청/참여심사 전용 API·업무 상태/권한은 구현 완료가 아니다. 실제 권한/동시성/원자성·앱/DB/연동 검증 NOT_RUN. 원격 변경 없음.

## REC-035 공동체 배정 제안 본인 수락

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 질문 “배정 제안도 본인 수락 후 활성화하도록 확정할까요?”에 사용자가 “네”라고 답함. 직전 제안은 담당자가 교인을 배정할 때 강제 등록 대신 제안을 보내고 대상 본인 수락 후 참여를 활성화하며 수락 기한은 별도로 정한다는 내용이다.
- 결정: 담당자의 공동체 배정은 제안으로 접수하고, 대상 본인이 명시적으로 수락한 뒤 참여를 활성화한다. 미수락 제안 자체는 실제 공동체 참여나 명단/보호자료 접근권을 만들지 않는다.
- 자격: REC-033의 해당 교회 가입승인 유효소속 교인 자격은 유지한다. 유효한 제안과 인증된 대상 본인·현재 자격을 확인해야 한다. 담당자가 본인을 대신해 수락하거나 알림 전송·열람만으로 수락 처리하지 않는다.
- 범위 분리: 본인이 직접 신청한 경우는 REC-034의 담당 수동 승인 경로다. 배정 본인 수락을 모든 신청에 두 번째 수락으로 자동 추가하지 않는다. 다만 세부 화면/전이와 신청 변경 재확인은 후속 계약이다.
- 이유: 담당자의 운영 제안과 개인의 실제 참여 의사를 구분하고 미수락 배정으로 권한이 열리는 것을 방지한다.

- 권위: 직전 제안 “서버의 유효 지정부터 7일(168시간) 동안 수락, 만료 후 현재 자격 확인해 새 지정, 알림 재전송으로 연장하지 않음, 실제 담당 임기와 별개”와 질문 “이 수락 기한으로 확정할까요?”에 사용자가 “네”라고 답함.
- 결정: 공동체 심사/배정 담당 지정은 서버의 유효 지정 시점부터168시간 동안 대상 본인이 수락할 수 있다. 기한 도달 시 수락을 차단한다. 통지/열람/재전송·앱 재방문으로 기산점과 기한을 바꾸지 않는다.
- 만료 뒤: 필요하면 REC-038의 관리자 지정 경로에서 현재 자격과 범위를 확인한 새 지정으로 처리한다. 옛 지정의 시각을 덮어써 되살리거나 자동수락하지 않는다. 이전 지정·결과와 새 지정은 구별한다.
- 유지 조건: REC-039 해당교회 유효소속 자격 및 REC-040 본인 공동체/업무범위 확인·명시수락을 유지한다. 미수락/만료 담당은 업무권한이 활성화되지 않는다.
- 범위: 담당 지정 수락기한이며 실제 담당 임기/연장·공동체 참여기간·물리보유/백업·일반조회기한이 아니다. 공동체 배정참여제안 기한(REC-036)과 숫자는 같아도 사건/기록은 별개다.
- 이유/대안: 오래된 지정을 무기한 수락하지 않고 최신자격 확인 경로를 유지한다. 무기한수락/통지 때마다 자동연장하는 방식은 채택하지 않는다.
- 미결: 서버 유효지정/최종수락 근거·기한 경합/필드·시간/버전 구현, 실제임기/연장·해제/거절·범위변경/중복/반복 재지정·지정자 권한상실 후 기존지정 효력·해당공동체 참여요건·보유/복구. 실제 임기/최대1년을 이번 답으로 자동확정하지 않는다.
- 영향: 용어집·공동체 계약/작업/시나리오·MVP16·현재 안내/게이트/인벤토리. COS/REC001~040은 보존하고 당시 수락기한 미결만 구체화한다.
- 검증/한계: 문서 합의 기록. 실제 지정/수락/만료/API/권한/DB/앱/경합 실행 NOT_RUN. 코드/DDL/GitHub 변경 없음.

## REC-042 공동체 담당 임기·연장 기간 기준

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 권장안 “기존 일반 업무 위임 기준을 적용해 종료 시점을 미리 정하고, 한 번의 지정·연장은 최대1년, 연장은 본인 수락 필요·자동 연장하지 않음”과 질문 “이 기간 기준을 공동체 심사·배정 담당자에게도 적용할까요?”에 사용자가 “네”라고 답함.
- 결정: 공동체 심사/배정 담당 권한은 종료 시점을 미리 정한다. 한 번의 지정과 각 연장 기간은 최대1년이며 더 짧게 정할 수 있다. 연장은 본인 수락이 필요하고 자동연장하지 않는다. 최대1년은 자동 기본임기가 아니다.
- 기준 연결: 일반업무 기간·1년 계산의 기존 REC-008/009/018/022/023 범위를 참조한다. 교회 기준 달력1년이며365일 고정이 아니다. 2월29일→다음해2월28일 같은시각, 종료경계 비포함·날짜만 입력 시 다음날 시작 경계와 상한 비교 등 기존 계산 기준은 [1년 계산](ONE_YEAR_LIMIT_PROPOSAL_2026-10-26.md)을 따른다. 그 문서 규칙7의 시간대 예외 기술 DRAFT를 AGREED로 승격하지 않는다.
- 수락/기한 분리: 최초 활성화는 REC-040 본인수락과 현재 유효조건을 확인하고 REC-041의 지정수락168h를 적용한다. 수락기한이 남았어도 미리 정한 업무 종료 시점이 지났으면 업무 권한을 만들 수 없다. 늦은 수락/알림 재전송으로 약정 종료를 자동 이동하지 않는다.
- 연장 경계: 기존 일반업무 기준처럼 종료 전 유효수락은 기존 종료부터, 공백 후 유효수락은 재활성화부터 구간을 판단한다. 공백 기간의 권한을 소급 부여하지 않고 제안 종료를 자동 이동하지 않는다. 실제 연장제안/취소·경합·시간필드/버전 구현은 별도 계약이다.
- 범위: 심사/배정 업무권한 임기다. 공동체 참여기간·리더 직함 자체·교회 관리자/가입승인 특별역할·제공자 권한/공유·기록 보유기간으로 확대하지 않는다.
- 이유/대안: 담당권한을 정기적으로 재확인하고 무기한/자동연장을 방지한다. 무기한 담당권한·미수락 자동연장은 채택하지 않는다.
- 미결: 공동체 담당 연장제안 수락기한의 구체 적용·해제/종료와 진행중업무·미수락 배정제안 효력, 범위 변경/동시성·시간대 예외/정확 확정시각·보유/복원 등. 이번 답으로 모든 일반위임 기술/API를 완성했다고 보지 않는다.
- 영향: 용어집·공동체 상세/작업/시나리오·MVP16·현재 안내/게이트/인벤토리. 기존 COS/REC001~041 보존, 담당임기/연장 기준 미결만 구체화한다.
- 검증/한계: 문서 합의 기록. 실제 임기/종료/연장/수락/API·DB/앱/권한·경합 실행 NOT_RUN. 코드/DDL/GitHub 변경 없음.

## REC-043 공동체 담당 소속상실·권한회복

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 제안 “정지·탈퇴 등으로 유효 소속을 잃으면 심사·배정 권한을 즉시 차단, 소속 회복돼도 자동 복원하지 않고 관리자 재지정과 본인 수락”과 질문 “이 회복 기준으로 확정할까요?”에 사용자가 “네”라고 답함.
- 결정: 공동체 심사/배정 담당자가 해당 교회의 유효 소속을 상실하면 그 소속 근거의 공동체 심사·배정 권한을 즉시 차단한다. 정지 해제·재가입·소속 복구만으로 이전 담당권한을 자동 복원하지 않는다.
- 회복 경로: 현재 유효 관리자의 재지정(REC-038)과 대상 본인의 공동체/업무범위 확인·명시수락(REC-040)을 거쳐야 한다. 현재 자격(REC-039), 지정 수락기한(REC-041), 실제기간(REC-042)을 각각 재검증한다. 과거 수락을 새 재지정 수락으로 대신하지 않는다.
- 범위: 해당 교회 소속 근거의 심사/배정 업무권한이다. 다른 교회/공통 계정·독립 제품 개인 이용·개인 공유를 이 결정만으로 일괄 종료하지 않는다. 공동체 참여 자체 회복·리더 직함 재활성은 별도 정책이며 담당권한 재지정으로 자동 처리하지 않는다.
- 자료/실행 경계: 현재권한이 없는 새 조회/심사/배정은 허용하지 않는다. 이미 유효하게 확정한 결과/과거이력은 소속상실만으로 소급 취소·삭제하지 않는다. 진행중/미확정 요청은 최신권한과 실제확정 근거를 대조하며 실제 서버 경합·응답/캐시 차단은 후속 기술검증이다.
- 이유/대안: 종료된 소속에 붙은 옛 담당권한이 되살아나는 것을 방지한다. 정지해제/재가입 시 자동 권한복원을 채택하지 않는다.
- 미결: 소속상실 전 담당자가 만든 미수락 공동체 참여 배정제안의 효력·보류/취소/관리자 인수 절차, 소속상실과 동시 확정의 기술규칙/근거, 차단 표시/통지·미수락 담당지정 기록·복원 필터·보유. 이번 결정으로 미수락 제안을 자동 취소/연장/수락시키지 않는다.
- 영향: 용어집·공동체 상세/작업/시나리오·MVP16·현재 안내/게이트/인벤토리. 기존 COS/REC001~042 보존, 담당 소속상실·권한회복 기준만 구체화한다.
- 검증/한계: 설계 합의 기록. 즉시차단/재지정/수락/서버권한·DB/앱/경합/연동 실행 NOT_RUN. 코드/DDL/GitHub 변경 없음.

## REC-044 권한상실 제안자의 미수락 배정 제안

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 권장안 “권한을 잃은 담당자가 이전에 보낸 미수락 배정 제안은 바로 수락되지 않게 보류하고 현재 관리자가 유효성을 재확인한 뒤 처리, 기존168시간 기한은 늘리지 않음”과 질문 “이 보류·재확인 방식으로 확정할까요?”에 사용자가 “네”라고 답함.
- 결정: 해당 공동체 배정 제안 생성권한을 상실한 담당자가 이전에 보낸 아직 미수락인 배정 제안은 수락을 보류한다. 현재 유효한 해당 교회 관리자가 제안의 현재 유효성을 재확인한 뒤 처리한다. 기존 제안을 자동 승인/자동 수락하거나 담당자 권한회복만으로 자동 재개하지 않는다.
- 기한: 원래 서버 유효 제안 생성부터168시간(REC-036)을 유지한다. 보류/관리자 확인·인계·통지 재전송으로 정지/연장/초기화하지 않는다. 원기한이 도달한 제안은 관리자 확인만으로 수락 가능하게 되살리지 않는다. 필요하면 현재 자격을 확인한 새 제안 경로를 따른다.
- 본인/조건: 관리자 재확인은 대상 본인 수락(REC-035)을 대신하지 않는다. 수락 가능 여부를 판단할 때 현재 교회/대상 자격(REC-033)·공동체/제안 상태·본인/기한을 확인한다. 실제 서버최종검증/버전·경합은 기술후속이다.
- 범위: 제안자의 해당 배정 권한상실에 따른 미수락 배정 제안 처리다. 이미 유효하게 수락·확정된 공동체 참여를 이 절차로 소급 취소/보류하지 않는다. 제안자의 다른 교회/개인제품 권한으로 확대하지 않는다.
- 이유/대안: 제안의 운영 책임 근거가 사라진 상태에서 즉시 참여가 확정되는 것을 막고 현재 관리자 책임으로 검토한다. 무조건 자동취소·무조건 계속수락 허용을 이번 기본경로로 채택하지 않는다.
- 미결: 재확인 상세 필드/기록·결과종류/취소 주체/본인통지·대상/내용 변경 처리·다른관리자 반복확인 경합, 관리공백/장기보류·재제안 제한·정확한 권한상실 감지와 수락동시성·미확정/최종상태조회·보유/복원. 보류가 영구보관 허가나 기한연장 근거가 아니다.
- 영향: 용어집·공동체 계약/작업/시나리오·MVP16·현재안내/게이트/인벤토리. 기존 COS/REC001~043 보존. REC-043의 기존미수락제안 효력 미결을 이 보류/재확인·원기한 범위에서만 구체화한다.
- 검증/한계: 문서 합의 기록. 실제 권한상실 감지/보류·관리자재확인·수락/만료/API/DB/앱/경합/연동 NOT_RUN. 코드/DDL/GitHub 변경 없음.

## REC-045 재확인 시 대상·공동체 변경 제안

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 권장안 “재확인 과정에서 대상 교인이나 공동체를 변경하면 기존 제안을 덮어쓰지 않고 기존 제안은 취소 이력으로 보존, 변경 내용은 새 제안으로 보내 본인이 확인·수락”과 질문 “이 변경 처리 방식으로 확정할까요?”에 사용자가 “네”라고 답함.
- 결정: REC-044의 보류 제안을 관리자 재확인하는 과정에서 대상 교인 또는 공동체가 바뀌면 기존 미수락 제안의 내용을 덮어쓰지 않는다. 기존 제안은 취소 이력으로 보존하고 변경된 대상/공동체로 새 제안을 생성하여 대상 본인이 확인·수락하도록 한다.
- 적용조건: 처리 직전 기존 제안의 현재 상태/실제확정을 검증해야 한다. 이미 유효하게 수락·확정된 참여를 미수락 취소로 소급 변경하지 않는다. 이미 만료/취소 등 종결된 결과를 새 취소로 덮어쓰지 않는 조건은 기존 종결보존 원칙과 함께 기술계약에서 대조한다.
- 새 제안: REC-037의 현재 유효 생성권한, REC-033 대상 자격·공동체 조건을 다시 확인한다. REC-035에 따라 새 대상 본인이 새 내용을 명시수락한다. 옛 본인의 수락/열람·취소를 새 본인의 참여 동의로 재사용하지 않는다.

## REC-046 복수 공동체 참여와 권한 독립

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 권장안 “목장·찬양팀·봉사팀 등에 복수 참여를 허용하되 공동체별 승인·역할·권한은 독립적으로 관리”와 질문 “복수 공동체 참여를 허용할까요?”에 사용자가 “네”라고 답함.
- 결정: 같은 교회에서 한 교인이 여러 공동체에 동시에 참여할 수 있다. 각 공동체의 참여 승인·리더/담당 역할·업무권한은 독립적으로 관리한다. 하나의 참여/승인이 다른 공동체 참여를 자동 활성화하지 않는다.
- 자격/절차: 각 참여는 REC-033 해당교회 가입승인 유효소속 자격과 REC-034 본인신청 승인 또는 REC-035 배정본인수락 등 해당 경로의 유효조건을 따로 확인한다. 복수참여가 자동가입/대리수락을 허용하는 것은 아니다.
- 추가와 이동: B 공동체에 추가 참여하는 것만으로 기존 A를 종료하거나 A의 역할/권한/과거기록을 B로 옮기지 않는다. A종료를 포함하는 이동은 별도 의사·권한/확정 계약이다. 특정 공동체 종료/탈퇴를 다른 참여 포괄종료로 처리하지 않되 교회소속 상실 등 공통 자격 사건은 해당 기존규칙으로 별도 검증한다.
- 권한/공개: A 리더·심사/배정/연락 담당이라는 이유로 B의 같은 권한·명단/연락처를 얻지 않는다. 공동체 계층도 자동상속 근거가 아니다. 관리자 교회운영 권한은 해당 목적/필드별 기존 기준을 따르며 복수참여로 확대하지 않는다.
- 이유/대안: 목장·찬양·봉사 등 서로 다른 교회생활을 함께 수행할 수 있게 한다. 교인당 전체 공동체1개만 허용하는 방식은 기본정책으로 채택하지 않는다.

## REC-047 공동체 이동 확정

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 질문 “기존 공동체를 떠나 다른 공동체로 이동할 때, 이동 중에는 기존 참여를 유지하고 새 공동체 참여가 유효하게 확정될 때 기존 참여 종료를 함께 처리한다. 거절·취소되면 기존 참여 유지. 이 이동 방식으로 확정할까요?”에 사용자 “네”.
- 결정: 같은 교회 A에서 B로 이동하는 경우, B 참여의 유효한 확정과 A 참여 종료를 함께 처리한다. 확정 전에는 A를 먼저 종료하지 않는다. 미확정 상태·이동 거절·취소만으로 A 참여를 잃지 않는다.
- 범위: 이동은 REC-046의 추가참여와 구분한다. B 추가참여만으로 A를 종료하지 않는다. 기존 역사기록이나 A 리더/업무권한을 B에 복사하는 합의가 아니다. 교회소속 상실 등 별도 자격차단을 무시하고 A 접근을 계속 허용한다는 뜻도 아니다.
- 이유/대안: 이동 심사 중 소속 공백과 실패 시 기존 참여 상실을 막는다. A부터 종료한 뒤 B 가입을 시도하는 방식을 채택하지 않는다.
- 실패 계약 후보: 중간 실패가 한쪽만 확정된 성공으로 노출되지 않도록 설계하고, 응답 유실은 결과 확인 우선으로 처리한다. 이미 확정된 이동을 미확정 요청 취소로 되돌리지 않는 초안은 유지한다. 구체 트랜잭션/멱등성/복구/경합 구현은 TECHNICAL_DRAFT이며 실행 증거가 아니다.
- 미결: 이동 의사에서 A종료를 본인이 명시 확인하는 세부, 이동 승인/취소 주체와 A측 승인 필요 여부, 기한/만료·동시 이동/이미B참여/조직보관·리더 인계, 명단/보유기간. 확정 시 현재 계정/교회 자격·참여/공동체 상태·권한 재검증 상세는 기술 계약으로 이어간다.

## REC-050 새 공동체 이동 승인자

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 권장안 “기존 참여 신청과 동일하게 현재 교회 관리자 또는 해당 공동체의 명시적 참여심사 담당자만 승인. 리더 직함만으로 승인권을 주지 않음”과 질문 “이 범위로 확정할까요?”에 사용자 “네”.
- 결정: 같은 교회 A→B 이동의 B측 승인은 현재 해당 교회의 유효 관리자 또는 B에 명시적 참여심사 권한이 유효한 담당자만 수행한다. REC-034 일반 참여신청 심사의 권한 범위를 이동의 B측 승인에도 적용한다.
- 격리: A의 심사 담당·리더 직함·교회가입 심사 담당·배정 제안 생성권만으로 B 이동 승인권을 얻지 않는다. B 리더도 명시 심사권한이 없으면 승인하지 못한다. 교회/공동체·업무범위가 일치하고 현재 유효해야 한다.
- 기존 합의: REC-048 본인의 A종료+B참여 명시동의, REC-049 A측 추가승인 불필요/결과안내·별도인계, REC-047 B 유효참여확정+A종료 함께처리, REC-033 현재 대상 자격을 유지한다. B승인만으로 본인 동의 누락이나 자격상실을 우회하지 않는다.
- 담당 유효성: REC-038~043의 관리자 지정/본인수락·기한/임기·소속상실 차단/회복후 재지정 등 기존 담당 규칙을 따른다. 예전에 심사 화면을 열었다는 이유로 해제/만료/소속상실 후 승인하지 못한다. 실제 확정 시점 재검증/경합 제어는 TECHNICAL_DRAFT/NOT_RUN이다.
- 이유/대안: 신규 참여 심사와 이동 심사의 책임 범위를 일관되게 유지한다. 리더 직함만으로 자동 승인하거나 기존 공동체 담당자가 대상 공동체 승인까지 처리하는 방식은 채택하지 않는다.
- 미결: 본인 요청/담당 제안 등 이동 접수 경로, 승인자 자신의 이동에 대한 셀프심사·대체담당, 거절/취소권·기한/만료·철회/확정경합·이미B참여·통지/인계/증빙/보유기간. 이번 답변으로 승인권을 제안생성/강제종료/타공동체 명단공개까지 확대하지 않는다.
- 영향: 용어집·공동체 계약·CM07·CA63/64·MVP16·현재안내/게이트/인벤토리. 기존 COS/REC001~049·canonical/Git 이력 보존.

## REC-051 공동체 이동 셀프승인 금지

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 권장안 “본인 요청은 다른 유효 승인자가 처리. 승인자가 없을 때의 예외 절차는 별도로 설계”와 질문 “자신의 이동 요청을 스스로 승인하지 못하도록 확정할까요?”에 사용자 “네”.
- 결정: 이동 대상 본인은 자신의 공동체 이동 요청을 승인하지 못한다. 현재 교회 관리자 또는 대상 공동체 참여심사 담당자이더라도 동일하게 적용한다. REC-050의 범위에 속하는 본인 외 다른 현재 유효 승인자가 처리한다.
- 동의/승인 분리: REC-048 본인의 A종료+B참여 동의는 계속 필요하다. 자신의 동의를 기록하는 행위와 이동 심사 승인은 별개이며, 본인 동의 기록은 금지하지 않는다. 관리자 역할 전환이나 담당 역할 선택만 바꿔 같은 사람이 셀프승인할 수는 없다. 실제 식별/연결 검증 방법은 기술초안이며 표시이름/이메일만으로 동일인 자동연결하지 않는다.
- 기존 합의: REC-047 B유효참여 확정+A종료 함께처리, REC-049 A측 추가승인 불필요·결과안내/별도인계, REC-033 자격 및 REC-050 현재권한 검증을 유지한다. 셀프승인 차단 때문에 이동 미확정 중 A를 먼저 종료하지 않는다. 별도 교회자격 차단은 그대로 적용한다.
- 이유/대안: 본인 의사와 심사 권한을 분리한다. 관리자/리더라는 이유로 자기 요청을 승인하는 예외는 이번 합의에서 허용하지 않는다.
- 미결: 다른 유효 승인자가 없을 때의 처리·대체담당 지정/수락, 승인 대기기한/만료·본인취소, 셀프거절/다른 심사행위 범위, 동시 확정/권한철회 경합·증빙/보유기간. 자동승인·플랫폼 운영자 대리승인·타교회 승인권·강제이동을 새로 만들지 않는다. 일반 가입/모든 제품의 셀프심사 정책으로 확대하지 않는다.

## REC-052 다른 이동 승인자 부재 처리

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 권장안 “자동 승인 대신, 관리자가 기존 자격·본인 수락 절차에 따라 다른 심사 담당자를 지정한 뒤 처리. 지정 전에는 이동을 확정하지 않고 기존 참여 유지”와 질문 “이 방식으로 확정할까요?”에 사용자 “네”.
- 결정: REC-051에 따라 본인 외 현재 유효 승인자가 없는 이동은 자동 승인하거나 셀프승인 예외로 처리하지 않는다. 현재 유효 교회 관리자가 대상 공동체의 다른 심사 담당자를 기존 규칙으로 지정하고, 그 담당자가 본인 수락 등 유효조건을 충족한 뒤 REC-050 범위에서 심사한다. 지정 제안만으로 심사권이 생기지 않는다.
- 기존 절차: REC-038 관리자 지정, REC-039 해당교회 승인 유효소속 자격, REC-040 본인수락 후 활성화, REC-041 지정수락168시간, REC-042 임기/연장, REC-043 소속상실 차단/회복후 재지정 기준을 유지한다. 이동 대상 본인과 다른 사람이어야 하며, 다른 공동체/배정권을 대신 쓰지 않는다. 담당 지정권은 이동 승인권과 구분한다.

- 이유/대안: 셀프승인 금지를 유지하면서 기존 위임 절차로 심사 가능 상태를 마련한다. 승인자 부재를 자동 승인이나 자기승인 예외로 해결하지 않는다.
- 미결: 유효 관리자도 없거나 지정 가능한 다른 교인이 없는 경우의 운영 안내/보호 절차, 이동 대기기한/취소/만료, 지정과 이동의 참조·수락후 알림/재심사·경합, 증빙/보유·실제 원자성. 대기와 자료 보유기간은 별도다.
- 영향: 용어집·공동체 계약·CM07·CA67/68·MVP16·현재안내/게이트/인벤토리. 기존 COS/REC001~051·canonical/Git 이력 보존.

## REC-053 공동체 이동 요청 본인 취소

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 권장안 “이동이 확정되기 전에는 본인이 취소할 수 있고, 이미 확정된 이동은 요청 취소로 되돌리지 않음”과 질문 “이 기준으로 확정할까요?”에 사용자 “네”.
- 결정: 이동 대상 본인은 아직 확정되지 않은 자신의 공동체 이동 요청을 취소할 수 있다. 이미 유효하게 확정된 이동은 요청 취소로 A참여를 되살리거나 B참여를 소급 말소하지 않는다. 새 이동/정정이 필요하면 별도 현재 의사·자격·권한 계약으로 다룬다.
- 기존 경계: REC-047에 따라 미확정 이동의 취소는 기존 A참여를 유지한다. 취소는 교회 탈퇴/다른 공동체 종료·일반 담당 위임해제·타제품 탈퇴가 아니다. REC-048 본인동의와 REC-050~052의 승인자/셀프승인금지/부재 처리는 유지한다. 별도 계정/교회 자격차단은 무시하지 않는다.
- 실패 계약 후보: 버튼 클릭·기기 시각만으로 취소 완료라고 단정하지 않고 서버의 현재 확정 결과를 확인한다. 응답 유실은 확인 우선·자동 재이동 금지, 중복취소는 이력을 중복 생성하지 않는 기술초안으로 대조한다. 이미 거절/취소/만료된 결과를 새 취소로 덮어쓰지 않는 방향을 유지한다.
- 이유/대안: 확정 전 의사 철회를 허용하고 확정된 참여/역사를 소급 변경하는 일을 막는다. 취소 버튼으로 확정 이동을 되돌리는 방식은 채택하지 않는다.
- 미결: 취소와 승인/최종확정 동시 경합 시 우선순위, 담당자 취소권·기한/만료, 자격상실 중 본인취소 경로/재인증, 표준 사유·통지/증빙/보유·구체 API/원자성. “네”를 먼저 도착/클릭한 요청 우선이나 모든 상태의 본인취소 허용으로 확대하지 않는다.
- 영향: 용어집·공동체 계약·CM07·CA69/70·MVP16·현재안내/게이트/인벤토리. 기존 COS/REC001~052·canonical/Git 이력 보존.
- 검증/한계: 설계 한정 합의. 실제 취소/경합/결과조회/이동·DB/API/앱/연동 실행 NOT_RUN. 코드·DDL·GitHub 변경 없음.

## REC-054 이동 승인·취소 경합 최종확정 기준

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 질문 “서버에서 현재 권한·상태를 검증해 먼저 유효하게 최종 확정한 결과 하나만 인정하는 방식으로 확정할까요? 기기에서 먼저 누른 순서나 서버에 도착한 순서를 뜻하지 않음”에 사용자 “네”.
- 결정: 동일 이동 요청의 승인/이동 확정과 본인 취소가 경합하면 현재 권한·상태 검증을 통과해 서버에서 먼저 유효하게 최종 확정된 결과 하나만 인정한다. 접수·화면진입·기기 클릭·네트워크 도착 순서나 잠금 획득만으로 승자를 정하지 않는다. 실패/롤백된 시도는 유효 확정 결과가 아니다.
- 취소 먼저: 취소가 유효 최종확정되면 이번 이동으로 A를 종료하거나 B참여를 활성화하지 않으며, 뒤늦은 승인으로 취소 결과를 덮어쓰지 않는다. 별도 교회/계정 자격차단은 그대로 적용한다.
- 이동 먼저: B참여 유효확정과 A종료를 REC-047대로 함께 처리한 결과가 먼저 확정되면 뒤늦은 요청 취소로 소급 복구하지 않는다(REC-053). 기존 역사·다른 추가참여를 변경하지 않는다.
- 기존 권한: REC-048 본인 명시동의, REC-049 A추가승인 불필요, REC-050 B현재 승인권, REC-051 셀프승인금지, REC-052 승인자부재 처리와 REC-033 자격을 유지한다. 이 합의는 권한철회 이후 과거 권한으로 확정할 수 있는 유예가 아니다.
- 이유/대안: 상충 최종결과/중복참여를 방지한다. 클릭 우선·도착 우선·일괄 취소우선·나중 요청 덮어쓰기를 채택하지 않는다.
- 기술 경계: r59 경합 상세의 처리실패/유실/통지·멱등성 후보는 기술초안이다. 정확한 최종확정 지점·권한검증 시점/철회 경합·잠금/트랜잭션/영수증/응답코드/조회수명은 별도 계약·실행 검증이 필요하다. 기존 Idempotency-Key 기준선을 보존한다.
- 미결: 동시 다중 이동 A→B/A→C·이미B참여, 이동 대기기한/만료·담당취소권/사유·통지/인계·증빙/보유/백업. 본 정책을 모든 업무/다른 제품의 경합 규칙으로 확대하지 않는다.
- 영향: 용어집·공동체 계약·경합 상세·CM07·CA71/72·MVP16·현재안내/게이트/인벤토리. 기존 COS/REC001~053·canonical/Git 이력 보존.
- 검증/한계: 설계 한정 합의. 실제 병렬처리/취소/권한철회/이동·DB/API/앱/연동 실행 NOT_RUN. 코드·DDL·GitHub 변경 없음.

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 권장안 “추가참여는 별도로 허용하되 같은 기존 공동체 참여를 종료하는 미확정 이동 요청은 하나만 유지. 목적지를 바꾸려면 기존 요청을 취소하고 새로 신청”과 질문 “이 기준으로 확정할까요?”에 사용자 “네”.

- 목적지 변경: 기존 미확정 요청을 취소하고 새 목적지로 새 신청한다. 기존 요청의 목적지를 덮어쓰거나 옛 동의를 새 목적지 동의로 재사용하지 않는다. REC-048의 새 참여/기존 종료 본인확인과 현재 자격/승인권 검증은 새 요청에도 필요하다.
- 취소 확인/경합: REC-053/054에 따라 취소가 실제 유효 확정됐는지 확인한 뒤 새 신청한다. 취소 응답 유실/최종결과 불명 상태에서 새 키로 자동 대체신청하지 않는다. 이동이 먼저 확정됐다면 옛 A참여를 미확정 취소로 복구하지 않고 현재 관계를 확인한다. 구체 생성/취소의 경쟁 제어는 기술초안이다.
- 추가참여와 구분: REC-046 복수참여는 유지한다. 본 정책은 교인당 전체 공동체 하나 제한이나 모든 추가참여 요청 하나 제한이 아니다. 별도 출발참여의 이동·이미B참여 상태의 전환/합병·추가참여와 이동 간 경합 상세는 OPEN이다.

## REC-056 목적지 공동체 이미 참여 중인 경우

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 권장안 “목적지 공동체에 이미 참여 중인 경우 새 이동 신청을 만들기보다 기존 공동체 참여 종료 절차로 안내하고 목적지 참여는 유지”와 질문 “이 기준으로 확정할까요?”에 사용자 “네”.
- 결정: 같은 교회 A참여자가 B에도 이미 참여 중이면 A→B 새 이동 신청을 생성하지 않는다. 현재 B참여를 유지하고 A참여를 종료하려는 본인에게 A의 별도 참여 종료 절차를 안내한다.
- 안내와 실행 구분: 안내만으로 A를 종료하지 않는다. 본인의 A종료 의사 확인과 실제 종료의 승인 필요/권한·실패/확정 조건은 별도 공동체 종료 계약을 따른다. 이번 합의는 자유탈퇴 즉시실행이나 관리자 강제종료권의 승인이 아니다.
- 목적지 보존: B참여를 중복 생성/재가입 처리하거나 기존 승인·역사/역할을 덮어쓰지 않는다. A 역할/권한/역사를 B에 복사하지 않는다. B참여 유지가 별도 계정/교회 정지·권한해제를 무시하고 접근을 계속 허용한다는 뜻은 아니다.
- 현재 상태: 이미 참여 중인지 현재 관계를 확인한다. 과거 종료/정지 관계·미수락 제안·미확정 가입 요청을 현재 유효 참여로 자동 간주하지 않는다. 정확한 상태집합/참여세대 판정은 기술초안이다.
- 이유/대안: 복수참여에서 필요한 A종료를 불필요한 B중복가입/이동으로 처리하지 않는다. B관계를 새로 만들거나 기존 B기록을 이동 결과로 덮어쓰는 방식은 채택하지 않는다.
- 미결: 이동 신청 뒤 확정 전에 B가 별도 경로로 활성화되는 경합, 기존 미확정 이동의 종결 방식/자동 전환 여부, 종료 승인 필요/권한·기한/사유·리더/인계·통지/증빙/보유. 오래된 A→B 동의를 자동 A종료 실행으로 전환하지 않는 방향을 기술계약에서 검토하며 해당 경합 정책은 아직 미확정이다.
- 영향: 용어집·공동체 계약·경합 상세·CM07·CA79/80·MVP16·현재안내/게이트/인벤토리. 기존 COS/REC001~055·canonical/Git 이력 보존.
- 검증/한계: 설계 한정 합의. 실제 B참여 판정/종료 안내/경합·DB/API/앱/연동 실행 NOT_RUN. 코드·DDL·GitHub 변경 없음.

## REC-057 본인 공동체 탈퇴 별도 승인 불필요

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 권장안 “본인이 종료 영향을 확인하면 별도 승인 없이 탈퇴하고 담당자에게 결과 안내·업무 인계를 연결. 교회 소속과 다른 공동체 참여 유지”와 질문 “이 기준으로 확정할까요?”에 사용자 “네”.
- 결정: 본인이 자신의 해당 공동체 참여 종료 영향을 확인하고 탈퇴 의사를 명시하면 담당자의 별도 승인 없이 해당 참여를 종료할 수 있다. 단순 화면 진입·안내 열람·알림 확인은 종료 의사가 아니다. 실제 본인/교회/대상 관계·현재 상태 검증은 유지한다.
- 범위: 공동체 A의 본인 탈퇴는 교회 탈퇴·공통계정/제품 탈퇴·다른 공동체 B종료·개인기록 삭제가 아니다. 교회 소속과 다른 공동체 참여를 유지한다. 별도 계정/교회 자격차단·각 범위 권한해제를 무시하고 접근을 계속 허용하지 않는다.
- 결과/인계: 현재 업무상 권한 있는 담당자에게 종료 결과를 알리고 진행 업무는 별도로 인계한다. 안내 열람·담당 승인·후임 수락·인계 완료를 본인 탈퇴의 대기조건으로 삼지 않는다. 인계를 이유로 종료자의 접근을 유지하지 않는다. 최소 수신정보/실패 전달/인계 담당·증빙/보유는 기술/운영 상세로 남긴다.
- 기존 경계: REC-056의 이미B참여 경로는 이 A종료 절차로 연결한다. A참여 근거의 접근/업무권한을 재검증하고 과거 유효 출석/참여를 소급 말소하지 않는 기존 보호 기준을 유지한다. 정확한 직함/독립위임·미확정 요청의 종료 연계는 별도 상세다.
- 이유/대안: 본인 의사에 따른 공동체 참여 종료를 담당자 미응답/인계 지연으로 묶지 않는다. 별도 수동 탈퇴승인을 필수로 하는 방식은 채택하지 않는다.
- 미결: 리더 직함/담당권한·미확정 이동/배정/행사의 연계정리, 본인탈퇴와 승인/이동/강제종료의 경합, 정지 중 탈퇴 경로/재인증, 강제종료권자·사유/통지·취소/복구/재가입·기록수명. 공동체 마지막 리더 보호나 모든 독립위임 자동삭제를 새로 확정하지 않는다.
- 영향: 용어집·공동체 계약·CM11·CA81/82·MVP16·현재안내/게이트/인벤토리. 기존 COS/REC001~056·canonical/Git 이력 보존.
- 검증/한계: 설계 한정 합의. 실제 본인탈퇴/접근차단/통지/인계·DB/API/앱/연동 실행 NOT_RUN. 코드·DDL·GitHub 변경 없음.

## REC-059 공동체 재가입과 과거 권한 자동복원 금지

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-29.
- 권위: 직전 권장안 “다시 참여하려면 현재 자격과 승인·수락 절차를 새로 확인하고 과거 리더 직함·업무권한은 자동 복원하지 않음”과 질문 “이 기준으로 확정할까요?”에 사용자 “네”.
- 결정: 탈퇴했던 공동체에 다시 참여하려면 현재 해당교회 승인 유효소속 등 자격과 현재 공동체 상태를 확인하고 해당 가입 경로의 승인/수락을 새로 거친다. 과거 승인·수락·리더 직함·업무권한만으로 재가입 참여나 권한을 자동 활성화하지 않는다.
- 경로 구분: 본인 신청은 REC-034의 현재 유효 관리자/해당 공동체 명시 참여심사 담당자 승인, 배정 경로는 REC-035 본인 새수락 및 REC-036/037의 유효제안 조건을 따른다. 모든 경로에 승인+수락을 무조건 두 번 요구한다는 새 정책은 아니다. 과거 제안/동의를 새 참여 의사로 재사용하지 않는다.
- 권한 구분: 참여가 다시 활성화되어도 과거 LEADER/ASSISTANT 직함·심사/배정/명단/연락/게시/출석 등 업무권한을 자동 복원하지 않는다. 필요한 권한은 현재 유효 지정·본인수락 등 해당 절차를 새로 따른다. 독립 권한의 이미 유효한 별도 근거를 재가입이 신규로 부여/확장한다는 뜻도 아니다.
- 역사/타제품: 과거 유효 참여·출석/직함 이력은 재가입으로 덮어쓰거나 소급 말소하지 않는다. 재가입 사실이 과거 모든 자료의 열람권/개인 공유/JLPrayer 방/Academy 수료·생명일기 상태를 자동 회복시키지 않는다. 보유기간과 역사자료 열람 범위는 별도 계약이다.

## REC-063 리더 소개 공개 동의 본인 철회

- 화면 계약 초안: 확인란은 과거 동의로 미리 선택하지 않고 본인이 현재 내용/대상에 대해 선택하도록 한다. 선택 전 공개 반영 실행을 막고, 제출 중 중복 클릭을 방지하며 취소/뒤로가기만으로 동의·공개를 확정하지 않는 방안을 UX_DRAFT로 둔다. 글자 크기/스크롤·스크린리더·오류 문구/정확한 배치는 미검증이며 동의 문구 전문은 별도 검토한다.
- 변경/권한: 화면을 연 뒤 내용·공개 대상·직함이 바뀌면 REC-068대로 최신 재확인과 연결한다. 기존 확인란 상태를 새 버전에 자동 승계하지 않는 방안은 기술/UX 초안이다. 직함 종료/동의 철회/소속 및 대상 제한은 계속 검증하며 결합 버튼으로 우회하지 않는다. 교회전체/인터넷 공개를 새로 허용하지 않는다.
- 이전 요청/실패: REC-069/070/071대로 이전 게시 요청 자동 재개 금지·결과 미확인 시 기존 요청 결과/현재 공개 우선 조회를 적용한다. 버튼 클릭 직후 성공 표시를 하지 않는다. 동의만 저장되고 게시 실패한 경우의 재시도/동의 재확인 UX는 OPEN이며 자동 재게시를 허용하지 않는다.
- 이유/대안: 중복 화면 이동을 줄이면서 공개 의사를 명확히 한다. 별도 세 화면 강제 또는 확인란 선택 즉시 자동 게시 대안을 채택하지 않는다.
- 미결: 동의 문구·기본 선택 상태/동의 증거·최신버전 결속·동의/게시 원자성/부분실패·미확인 수동해결·조회/보유/캐시. 단일화면 합의만으로 API/증빙/보유기간이 확정된 것은 아니다.
- 영향: 용어집·공동체 계약·CM10·CA111/112·MVP16·현재 안내/게이트/인벤토리. 기존 COS/REC001~071·canonical/Git/과거 기록 보존.
- 검증: 설계 한정 합의. 실제 화면/접근성/재동의/게시/부분실패/앱/API/DB/연동 검증 NOT_RUN. 코드·DDL·GitHub 변경 없음.

## REC-073 동의 저장 후 게시 실패의 본인 재시도

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-30.
- 권위: 직전 질문은 동의 저장 후 게시 실패가 확정되고 내용·대상·직함·동의가 그대로 유효하면 같은 동의를 반복하지 않고 본인이 ‘공개 반영 다시 시도’를 선택하며 결과 미확인 시 먼저 조회하는 기준이었고 사용자 “네”로 답변했다.

- 이전요청 경계: 이번 본인 재시도는 REC-071의 철회 전 요청 자동 재개 금지를 변경하지 않는다. 저장된 동의가 그대로 유효한 동일 조건의 확정 실패에만 적용한다. 같은 의도 동일 식별자 원칙과 실패 영수증의 최종성·재시도 실행 식별 관계는 별도 기술 계약으로 정하며 새 키 발급을 정책 승인으로 간주하지 않는다.
- 이유/대안: 유효 동의를 불필요하게 반복하지 않으면서 중복 게시와 철회 우회를 막는다. 모든 통신 오류에 재동의 강제 또는 자동 재게시 대안을 채택하지 않는다.

## REC-074 소개 유지와 사진만 즉시 비공개

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-30.
- 권위: 직전 질문은 전체 소개를 유지하면서 본인이 사진만 즉시 비공개로 전환할 수 있도록 하고 원본 파일 삭제·보유는 별도로 다루는 기준이었으며 사용자 “네”로 답변했다.
- 결정: 본인이 리더 소개 전체를 철회하지 않고 사진만 즉시 비공개로 전환할 수 있으며, 나머지 소개는 유효한 공개 조건 안에서 유지한다. 원본 파일 삭제·보유는 별도로 다룬다. 관리자 승인이나 다른 내용 편집/전체 재게시를 기다려야 사진 공개가 중단되는 방식으로 만들지 않는다.
- 범위: 해당 공동체의 해당 리더 소개 사진 공개를 중단하는 행위다. 계정/다른 공동체/다른 제품 사진을 일괄 변경하거나 직함·업무권한·전체 소개 동의를 자동 해제하는 정책이 아니다. 나머지 이름/현재직함/짧은소개도 기존 동의·대상·현재 직함 등 조건이 유효할 때만 유지한다. 전체 동의철회/직함종료가 함께 발생하면 기존 규칙대로 소개 전체를 중단한다.
- 즉시의 의미: 별도 관리자 승인이나 예약 게시 시점 없이 본인의 사진 비공개 요청을 처리하도록 하는 정책이다. 통신이 끊겨 서버에 전달되지 않은 요청까지 이미 확정됐다고 표시하지 않는다. 서버 유효확정 시 사진 공개를 중단하고 현재 공개본 유지 규칙으로 사진을 계속 노출하지 않도록 설계한다. 이미 다운로드된 외부 사본의 즉시 회수나 모든 오프라인 기기의 동시 삭제를 보장하는 말은 아니다.
- 구버전/초안: 사진을 포함한 오래된 공개본·초안 게시나 재시도로 비공개 사진이 뜻하지 않게 다시 보이지 않도록 사진 공개 상태를 현재 버전과 연결할 기술계약이 필요하다. 편집 중 기존 공개본 유지(REC-067)는 사진 비공개를 우회하지 않는다. 사진만 다시 공개하는 구체적 확인/동의 UX와 교체 사진 처리 방식은 OPEN이며 이번 결정으로 자동 재공개를 승인하지 않는다.
- 원본/정리: 공개 중단과 저장 원본/파생이미지/백업/감사자료의 물리삭제를 구분한다. 본인 미리보기 원본 접근 조건·정확한 삭제/보유기간·다른 유효 참조 처리·캐시/서명URL 차단은 별도 계약이 필요하다. 파일 영구보존 또는 즉시 물리삭제를 추가 합의하지 않는다.
- 이유/대안: 선택 항목인 사진을 내리기 위해 전체 소개를 철회하거나 관리자 승인을 기다리지 않도록 한다. 사진이 선택 항목이라는 REC-062와 연결하며 나머지 유효 소개의 안내 기능을 유지한다.
- 기술 후보: 사진 공개 차단 상태/버전과 현재 소개의 허용 필드를 결합해 조회·미리보기/게시·미디어 접근을 검증한다. 정확한 필드/API/트랜잭션·오래된 작업 차단·CDN/캐시 무효화·지연 상한/실패안내는 TECHNICAL_DRAFT/NOT_RUN이다. 응답유실은 결과 우선 확인 원칙과 연결하되 사진비공개 전용 조회 계약은 미구현이다.
- 미결: 사진 재공개 UX·짧은소개만 별도 비공개 범위·실기기/캐시 전파상한·파일/참조/백업 보유 및 삭제·결과조회/미확인 수동해결. 전체 소개 철회 합의를 사진별 새 보유기간으로 확장하지 않는다.
- 영향: 용어집·공동체 계약·CM10·CA117/118·MVP16·현재 안내/게이트/인벤토리. 기존 COS/REC001~073·r80 선택항목 대조·canonical/Git/과거 기록 보존.
- 검증: 설계 한정 합의. 실제 사진 비공개/구버전게시/미디어차단/앱/API/DB/캐시/연동 검증 NOT_RUN. 코드·DDL·GitHub 변경 없음.

## REC-075 사진 재공개의 본인 확인과 명시적 반영

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-30.
- 권위: 직전 질문은 본인이 사진과 공개 대상을 다시 확인하고 ‘사진 공개 반영’을 선택해야 하며 예전 요청으로 자동 복원되지 않도록 하는 기준이었고 사용자 “네”로 답변했다.
- 결정: 비공개로 내린 소개 사진은 본인이 사진·공개 대상을 다시 확인하고 ‘사진 공개 반영’을 선택해야 다시 공개하며, 예전 요청으로 자동 복원하지 않는다. 사진 파일 선택/업로드/초안 저장·재로그인·관리자 제안만으로 사진을 공개하지 않는다.
- 공개 전제: 해당 소개 자체의 현재 유효 공개 동의/직함·소속/참여·수신범위와 본인 권한이 유효해야 한다. 전체 소개 동의가 철회됐다면 사진 버튼으로 전체 소개를 복원하지 않고 REC-071/072의 새 동의/공개 절차를 적용한다. 직함이 종료됐다면 재확인만으로 공개하지 않는다. 사진 재공개로 교회전체/인터넷 공개를 추가 허용하지 않는다.

- 권위: r102 최종 질문 ‘이 담당 체계로 확정할까요? 선임 책임자의 구체 자격·겸임·임기·처리 기한·보유기간은 별도 미결로 남깁니다.’에 사용자 ‘네’. r102의 모든 역할/선임 수락/필드/기간/구현 후보를 일괄 승인한 것은 아니다.
- 결정: 모호한 본인 소개 철회 대상을 추가 확인하는 업무는 ChurchOS 운영 주체가 별도로 지정한 담당 중 해당 건에 배정된 담당자만 업무에 필요한 최소 정보로 수행한다. 별도 지정과 건별 배정이 모두 필요하며 일반 교회 관리자·목회자·가입 승인 담당·일반 고객 상담 담당자라는 이유만으로 이 조회권을 얻지 않는다.
- 목적과 제한: 본인-대상 및 명칭의 정본 관계를 확인하는 업무다. 철회를 허가하는 심사가 아니며 담당자는 본인 대신 철회·동의·재게시하거나 소속/역할·계정 연결을 변경하지 않는다. 소개 원문·사진·연락처·다른 교인 명단·다른 제품 개인 기록을 열람하지 않는다. 본인이 대상을 식별할 수 있는 일반 철회에 담당 배정을 선행 조건으로 붙이지 않는다.
- 현재 권한: 배정 해제·담당 자격 상실 후 해당 건의 접근을 차단하고 미종결 업무는 별도로 인계한다. 선임만/다른 건 배정만으로 접근하지 않으며 복귀·재선임만으로 과거 건 권한을 자동 복원하지 않는다. 업무 인계가 본인 동의 철회 실행이나 자동 종결을 뜻하지 않는다. 서버 재검증·처리 중 경합·캐시/기기 정리의 실제 기술 보장은 미검증이다.
- 기존 합의 유지: REC-076 본인 철회 자격·REC-077 최소 표시·REC-078 적법한 동의 당시 이름 우선 기준을 유지한다. 추가 확인 접수/담당 설명은 본인의 최종 명시 철회와 구분한다. 대상/본인 관계를 확인하지 못하면 추측 실행하지 않고 관리자 승인·재가입·원문 제출로 대체하지 않는다. 직함 종료에 따른 현재 소개 중단은 확인 중에도 유지한다.
- 미결: 선임 책임자의 구체 자격·외부 위탁 자격·겸임/자기 선임/자기 배정/이해충돌·선임 수락/임기·배정/대행 주체·정확한 허용 필드/재인증·처리 기한·첫/정기/지연 안내·예외 조정·감사/보유/삭제/백업·API/실효권한/지연요청 회수는 별도 설계다. 168시간/1년/24시간/72시간 등 기존 다른 업무 규칙을 자동 적용하지 않는다.
- 실제 운영 구분: 이번 답변은 체계에 대한 설계 합의다. 운영 조직/개인의 실제 선임·권한 부여·건별 배정·책임자 확보를 수행하거나 검증한 것이 아니다. 이 기능의 실데이터/출시 전 게이트는 남는다. 지원 책임자 직함만으로 접수 상세 접근을 자동 부여하지 않는다.
- 영향: 용어집·r102 초안의 후속 상태·공동체 계약·CM10·CA147/148·MVP16·현재 안내/게이트/인벤토리에 연결한다. 기존 COS/REC001~078·canonical/Git·과거 기록은 보존한다. DG04/05/06 전체 해소를 뜻하지 않는다.
- 검증: 설계 한정 합의. 실제 권한 차단/회수/인계·앱/API/DB/SSO/삭제/복원 실행 NOT_RUN. 코드·DDL·GitHub 변경 없음. PARTIAL_RECOVERY 유지.

## REC-080 선임·배정의 자기확정 금지와 이해충돌 분리

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-30.
- 권위: r104 최종 질문 ‘이 책임 분리 기준으로 확정할까요? 구체 책임자 자격·겸임 범위·기간·처리 기한·보유기간은 별도 미결로 남깁니다.’에 사용자 ‘네’. 초안의 모든 이해충돌 사례·역할 겸임·정형 코드·기술 후보를 일괄 승인한 것이 아니다.
- 결정: 추가 확인 담당의 자기 선임·자기 배정·이해충돌 자기승인을 금지한다. 필요한 선임/배정·충돌 회피는 다른 현재 유효한 적격 책임자의 확인·재배정을 거치도록 한다. 자신의 권한 생성·연장·확대나 자기 건 처리 자격을 스스로 확정하지 않는다. 논리 역할이 다르거나 계정을 바꿨다는 이유만으로 동일인의 자기확정을 허용하지 않는다.
- 범위: 해당 본인 소개 철회 대상의 추가 확인 운영 권한에 관한 기준이다. 교회 가입 승인·교회 관리자 지정·다른 제품 권한까지 새로 바꾸지 않는다. 구체적인 겸임 허용 범위는 미결이며 모든 업무에 서로 다른 세 사람을 요구한 것으로 해석하지 않는다. 다른 사람의 확인은 자격·범위·배정·충돌을 실제로 검토하는 것이어야 한다.
- 대행/공백: 대행자도 REC-079의 현재 유효 별도 지정과 해당 건 배정이 필요하다. 계정 공유·임의 재위임·복귀 후 옛 권한 자동 복원을 허용하지 않는다. 적격 인력 부재를 자기승인 예외·무권한 처리·대리 철회로 해결하지 않는다. 필요한 별도 인력 확보·지연 안내를 마련해야 하며 영구 대기를 정상 처리로 확정한 것은 아니다.
- 본인 권한 유지: 지원 담당 자신의 요청은 본인으로서 REC-076의 일반 철회를 할 수 있지만 지원 권한으로 자기 추가 확인을 끝내지 않는다. 본인이 대상을 식별할 수 있는 일반 철회에 별도 담당/승인을 붙이지 않는다. 담당은 대신 철회할 수 없고 원문·사진·다른 제품 개인 기록을 열람하지 않는다. 직함 종료/철회에 따른 공개 중단은 배정·대행 중에도 유지한다.
- 현재 권한/인계: 자격 상실·회수·배정 종료 이후 접근 차단과 별도 인계는 REC-079를 따른다. 다른 적격 담당의 유효 배정이 필요하며 지연 요청·열린 화면·재시도로 옛 권한을 사용하지 못하도록 기술 계약을 검증해야 한다. 담당 교체·회피·대행으로 최초 접수 시각이나 이미 정해질 안내 기한을 초기화하지 않는다. 아직 없는 기한 값을 확정하지 않는다.
- 미결: 선임/배정 책임자의 구체 자격·최초 책임자 지정/교체·겸임 범위·외부 위탁·직접 이해관계의 세부 판단/이의제기·대행 승인·임기/수락·처리 기한/상향 전달·허용 필드/기록 보유/삭제·실제 actor 결속/경합/DB권한은 별도 설계다. 최초 책임자를 자기선임 예외로 자동 허용하지 않는다. 일반 교회 관리자·상담자·보안 담당 직함만으로 적격 책임자를 대체하지 않는다.
- 영향: 용어집·r104 초안의 후속 상태·공동체 계약·CM10·CA149/150·MVP16·현재 안내/게이트/인벤토리에 연결한다. 기존 COS/REC001~079·canonical/Git·과거 파일 보존. DG/FD/RV 전체 해소를 뜻하지 않는다.
- 검증: 설계 한정 합의. 실제 선임/배정/충돌 판단/대행·권한 회수·앱/API/DB/SSO/복원 검증 NOT_RUN. 코드·DDL·GitHub 변경 없음. PARTIAL_RECOVERY 유지.

- 최소권한: 지정·등록 권한이 소개 원문/사진·접수 상세·다른 제품 기록 열람권이나 본인 대신 철회 권한을 만들지 않는다. REC-079의 별도지정/건별배정 최소접근과 REC-080의 자기선임/배정/충돌 자기승인 금지를 유지한다. 적격 확인자 직함만으로 실제 근거 검토·현재 신원/범위 확인을 대체하지 않는다.
- 본인 권한 유지: 식별 가능한 본인의 일반 철회는 REC-076을 따르며 운영 책임자 공백을 새 승인 조건으로 붙이지 않는다. 이미 중단된 소개 공개를 인계/복구 중에 되살리지 않는다. 접수·담당 교체·전달로 최초 접수 시각과 이미 정해질 안내 기한을 초기화하지 않는다. 아직 없는 기한 값을 확정하지 않는다.

## REC-082 개인 소개자료·교회 운영 이력·최소 증빙의 목적 분리

- 상태: AGREED_SCOPED / DESIGN. 날짜: 2026-10-30.
- 권위: r110 최종 질문 ‘이 분류 기준으로 확정할까요? 구체 보유기간·명시삭제 권한·공동 문서 정정 방식은 미결로 남깁니다.’에 사용자 ‘네’. DC01~09/E01~08의 모든 기술 후보·사본 분리/정정 방식·삭제 API/기간을 일괄 승인한 것은 아니다.
- 결정: 본인이 작성한 소개 문구와 선택 사진은 개인 소개자료로, 교회의 실제 직함·지정·참여 사실은 운영 기록으로, 동의·철회 사실은 소개 원문 없는 최소 증빙으로 목적을 분리한다. 서비스 탈퇴 등 사건별 삭제 대상은 각 목적/기여/자료 범위를 구분해 판정한다. 공동 문서는 본인 자료와 타인 기여를 구분한다.
