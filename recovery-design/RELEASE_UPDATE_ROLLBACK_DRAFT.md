[기존 canonical](../canonical/ChurchOS_Canonical_v2.6/README.md)은 기준 스냅샷이다. 이번 설계로 새 앱이 기존 API·DB와 자동 호환된다고 선언하지 않는다. GitHub main과 ZIP 설계 누적본도 별개이며 현재 배포/원격 변경을 수행하지 않는다.

## 버전 호환 후보

클라이언트는 지원 설정 schema/기능과 서버 계약을 확인하고 모르는 실행 기능을 추정 호출하지 않는다. 서버는 현재 권한·지원 계약을 검증한다. 지원 범위/유예기간/최소 버전/정확한 협상 필드는 OPEN이며 숫자를 만들어 배포하지 않는다.

호환 추가와 의미 변경을 구분한다. 예를 들어 브랜드 메뉴 키 변경, 새 수정본/게시본 구조, 신규 가입 심사, 요청 내구 접수/실패 영수증은 이전 클라이언트의 해석/재시도를 바꿀 수 있다. 지원 클라이언트를 확인하지 않고 기존 필드/동작을 조용히 대체하지 않는다. 독립 제품 API의 인증 대상도 별도 확인한다.

## 출시 준비의 순서 — 설계 후보

1. 승인된 변경 범위·기존 합의·미결·이전 버전 영향과 담당자를 정리한다.
2. 소스·의존성 잠금·스키마/자산·앱 리소스·서버/API·migration·정책 버전을 하나의 릴리스 인계 기록으로 연결한다. 비밀·서명키·토큰은 기록/ZIP/일반 로그에 넣지 않는다.
3. 같은 공통 코드에서 공용/전용 빌드를 구분하고 교회별 application/bundle 식별·서명·로그인 복귀·푸시 대상·데이터 격리를 시험한다. 앱 설치 브랜드만 확인하는 것으로 끝내지 않는다.
4. 정적/회귀→플랫폼 빌드/실기기→실제 인증/제품·DB/철회·복원 검증을 범위별 수행한다. 패키지/문서 해시 PASS를 앱/운영 PASS로 승계하지 않는다.
5. 스토어/배포 채널의 당시 공식 요구·자격·계정·권리·개인정보 안내를 확인하고 제출한다. 접수·심사·승인·출시·단말 설치·실사용을 다른 상태로 기록한다. 일정/승인/비용을 이번 초안에서 보장하지 않는다.
6. 사용자 지시대로 설계/구현 준비 이후에만 파일럿·단계 배포를 계획한다. 현재 파일럿을 시작하지 않는다. 배포 범위·중단 신호·담당/대행·지원 안내·롤백/복구를 실제 증거로 판정한다.

현재 Node24 서버 회귀 준비는 r28에서 의존성 캐시 미확보로 막혔으며 해결됐다고 주장하지 않는다. Flutter CI 정의도 실제 스토어 릴리스 증거가 아니다.

## 업데이트 실패와 구버전

업데이트 안내는 현재 설치 버전과 지원 범위를 검증한 뒤 제공한다. 새 버전이 설치됐는지 확인 전 ‘업데이트 완료’를 표시하지 않는다. 스토어/망/저장공간/설치 실패를 교회 탈퇴/권한 박탈/업무 실패로 바꾸지 않는다. 업데이트 중 이전에 보낸 업무는 결과 확인 대상으로 유지하며 자동 재실행하지 않는다.

보안상 구버전 업무 차단이 필요해도 임의로 보안 검증을 약화한 기존 API를 계속 허용하지 않는다. 반대로 무조건 닫기만 해 계정 복구·탈퇴·필수 상태 확인을 막지 않도록 제한 화면/현재 계약의 지원 경로를 먼저 설계·검증한다. 최소 지원 버전·강제 업데이트 조건·유예·실패 대안은 OPEN이다. 별도 관리자 웹을 사용자 필수 대안으로 만들지 않는다.

## 장애 판정과 복구

오류율/시간/배포 비율 같은 새 수치를 임의 확정하지 않는다. 배포 대상/산출물·실패 유형·영향 교회·권한/원문 유출·상태 전이 오류·복구 담당을 최소 정보로 추적한다. 교회명/개인 원문·토큰·서명키를 일반 진단 로그에 자동 수집하지 않는다.

서버 롤백은 현재 DB 계보와 구/신 앱/API 호환을 확인한 경우에만 후보가 된다. 비호환/데이터 오류이면 안전한 쓰기 보류·수정 배포·명시적 복구를 선택하는 계약이 필요하다. 과거 전체 DB 백업으로 운영을 되돌려 최신 삭제·소속·역할·실행 확정을 부활시키지 않는다. 확인 전 업무 실행/알림·공개 재개 금지.

## 전용 앱 운영과 교회 종료/이관

계정 명의·배포 권한·소스 이용·유지보수/비용·자산 권리·지원·중단/인계는 플랫폼과 교회가 구체 계약해야 한다. 가급적 교회 명의 운영을 검토한다는 기존 방향이 실제 계정 양도 가능성/심사 승인을 보장하지 않는다. 개인 계정/다른 교회 소속·독립 제품 데이터는 교회 앱 종료에 포괄 귀속/삭제하지 않는다.

앱/도메인/로고 변경·교회 대표 변경·전용 서버 이동을 같은 작업으로 처리하지 않는다. 대표·운영권 변화는 기존 사람 확인/분쟁 계약을 따른다. 교회 바인딩·알림/로그인 클라이언트·데이터 수신자는 현재 권한과 목적을 다시 검증한다. 새 사용자나 다른 교회가 과거 캐시/백업/서명 설정을 이어받지 않도록 인계 경계를 명시한다.

## 완료 조건과 현재 미결

배포 완료의 범위는 설정 반영/서버 배포/스토어 출시/단말 업데이트/실제 기능 검증을 각각 증거로 확인해야 한다. 현 문서는 절차 초안이다. 실제 운영 담당/계정·지원 정책·계약 비용·스토어/지역 요구·최소 버전·설정 수명·자산·서명/도메인·기술 스키마와 장애/복구 기준은 OPEN이다.

다음 전체 설계 묶음은 JLPrayer·JLBible·설교/CHGO·Academy/실천의 제공자 연결을 기존 운영 계약과 대조하는 단계다. 이 문서만으로 제공자 API가 준비됐거나 코드 개발을 재개한다고 선언하지 않는다.
