# 송신 전 기기 참조와 서버 확인 ID 연결 계약

2026-10-28 / TECHNICAL_DRAFT / 설계 연결 보완 / 신규 정책 승인 없음 / 앱·API·DB 구현 NOT_RUN

## 이어받는 합의와 해결할 공백

REC-026(동일 의도/다른 내용 거절), REC-027(결과 확인 우선), REC-028(기기 정리/교회 격리), REC-029(본인 발견), REC-030(조회 기한), REC-031(다섯 항목), REC-032(목적별 수명)을 유지한다. v2.6 자원별 쓰기·Idempotency-Key·경로별 영수증을 두 번째 실행 체계로 대체하지 않는다.

서버가 발급하는 확인 ID는 응답 전에는 기기가 모른다. 따라서 송신 전에 저장하는 기기 참조와 서버 확인 ID를 같은 필수 값으로 표현한 기존 초안을 보완한다. 이 문서의 ID/필드/연결 방법은 모두 기술 초안이며 추가 보유기간·공개 항목 합의가 아니다.

## 세 참조의 구분 — 기술 후보

| 참조 | 생성·사용 | 의미와 금지 |
|---|---|---|
| 기기 제출 참조 local_submission_ref | 송신 전 기기가 생성. 보호된 로컬 기록의 연결점 | 접수·성공 증거 아님. 기기별 참조이지 신규 서버 실행 키 아님 |
| 기존 멱등 처리의 범위 | 검증 계정/교회 + canonical route_key + Idempotency-Key | 기존 실행 중복 방지에 사용. 키만으로 전역 요청을 식별하지 않음 |
| 서버 확인 ID confirmation_ref | 후속 영속 접수/결과와 연결해 서버 발급하는 후보 | 다섯 공개 항목의 “요청 확인 ID” 후보. 조회 권한·재실행 권한 아님 |

앱이 새 업무 의도에 추측하기 어려운 멱등 키를 생성하도록 권장하지만, 기존 API의 16~128 인쇄 가능 ASCII 계약을 임의 강화·변경하지 않는다. 키를 다른 경로에서 재사용한 기존 요청은 별개이므로 서버가 전역 한 요청으로 합치지 않는다. confirmation_ref와 공개 request_id의 JSON 이름·형식은 아직 미확정이다.

## 기기 최소 기록 후보와 경계

기기 내부 후보: local_submission_ref, 검증 계정/교회 참조, 계약 버전, 기존 멱등 키에 대한 보호된 참조, 정확한 경로별 범위를 다시 대조할 최소 참조, 최초 기기 기록 시각, nullable confirmation_ref. confirmation_ref는 최초에는 없음이다. 이는 공통 공개 응답에 필드를 추가하는 제안이 아니다.

경로별 범위 참조는 기존 route_key와 정확히 대조 가능해야 한다. 자원 ID가 경로에 포함되면 그 참조도 민감한 업무 메타데이터로 취급한다. 원문·변경 값·이름·토큰·역할 캐시는 저장하지 않는다. 정적 작업 코드만으로 대상 자원을 구분할 수 있다고 가정하지 않는다. 원 경로/대상 참조를 보호 저장할지 별도 불투명 범위 참조로 표현할지 OPEN이며, 안전한 정확 대조가 없으면 기기가 추정 조회·재실행하지 않고 본인 발견/수동 확인으로 전환한다.

이는 기존 기기 후보 표의 식별 부분을 구체화하는 안이다. 후보 필드 전체 수집 승인이나 기기 TTL 확정이 아니다. 로그아웃/다른 계정 전환은 REC-028에 따라 제거하고, 동일 계정 교회 전환은 격리한다. OS 백업·로컬 상한·시계 변경·정리 실패는 별도 설계 게이트다.

## 연결 흐름

1. 현재 계정·선택 교회·소속·쓰기 권한 확인 후 한 의도의 기존 멱등 키를 만들고 최소 기기 참조를 보호 저장한다. 저장 실패 시 평문 대체/자동 송신을 하지 않는 흐름을 권장한다. 이 UX는 초안이다.
2. 기존 자원 경로와 헤더로 한 번 제출한다. 기기 참조 저장과 네트워크는 원자적이지 않으므로 로컬 참조만 생긴 경우도 접수로 표시하지 않는다.
3. 후속 서버 설계는 검증된 계정/교회/경로/키와 실제 접수·영수증·결과를 연결한다. 기존 v2.6 성공 영수증만으로 미확정·거절 접수 전체를 대체하지 않는다.
4. 응답을 받으면 현재 세션·계정·교회·기기 제출 참조를 재검증하고 서버 확인 ID를 연결한다. 다른 계정/교회로 전환 중 도착한 응답은 폐기한다.
5. 응답을 못 받으면 서버 확인 ID가 없는 채 RESULT_UNKNOWN을 유지한다. 이때 새 키 발급·쓰기 재송신을 자동 수행하지 않는다.
6. ID가 없으면 후속 읽기 전용 연결 확인 후보에서 검증된 본인·교회와 정확한 기존 경로/키 범위를 대조하거나, 이미 합의한 본인 발견 화면으로 이동한다. 연결 확인은 새 쓰기가 아니며 원문 제출을 요구하지 않는다. 정확한 경로/키를 확인할 수 없으면 목록의 시각이 비슷하다는 이유로 자동 연결하지 않는다.
7. ID가 있으면 직접 최소 상태 조회로 확인한다. 모든 읽기는 현재 접근과 REC-030 기한을 적용하고 요청 확인 ID·상태·서버 접수·최종 확정(있을 때)·현재 조회 만료만 공개한다.

서버 확인 ID를 성공 영수증 생성 때만 발급하면 성공 전 응답 단절/거절을 포괄하지 못한다. 실제 최초 접수 시점의 내구성, 영수증과의 결합, 최종 결과 원자성, 접수 뒤 실행 전 장애는 아래 상태표와 함께 상세 설계해야 한다. 기존 canonical을 이미 이 구조로 구현했다고 주장하지 않는다.

## 응답 유실·연결 확인 후보 결과

| 상황 | 읽기 결과/앱 동작 | 금지 |
|---|---|---|
| 정확한 본인 요청 하나를 현재 기한 내 대조 | 다섯 항목만 응답, 확인 ID 연결 | 응답에 route_key·키·대상·원문을 추가 공개 |
| 접수 기록은 있으나 결과 미확정 | 실제 최초 접수+168h 내 최소 상태 | 접수를 성공으로 표시 |
| 실제 최종 확정 | 실제 최종 확정+168h 내 최소 상태 | 업무 created_at을 확정 시각으로 자동 대체 |
| 무효 소속/계정·확인 불가 | 기존 비공개/접근 확인 계약 | 요청 존재·대상 유출 |
| 미존재/만료/대조 불가 | 구분되지 않는 일반 확인 안내 | 404를 미실행·만료 증거로 사용 |
| 정확한 범위로도 불일치/복수 후보 | 자동 연결 중단, 한정 수동 확인 | 가장 최근 결과를 임의 선택 |
| 기기 참조가 없음 | 현재 선택 교회의 본인 발견 | 이름/이메일/기기 지문으로 연결 |

연결 확인 입력은 조회를 위한 최소 민감 메타데이터다. URL·프록시·분석 로그에 키/대상 참조를 남기지 않는 전송 방식을 별도 정의하고 무권한 탐색/빈도 제한을 검토한다. 읽기 전용 연결 계약의 입력/HTTP/경로/필드 이름은 OPEN이다. 키를 안다는 이유로 인증·소속·본인 검증을 생략하지 않는다.

## 수명과 복원 연결

기기의 local_submission_ref 수명, 서버 confirmation_ref 매핑 수명, 중복 방지 행 수명, 조회 투영 수명은 별도 목적이다. 24h는 기존 성공 응답 재생 기한이며 168h는 일반 조회 기한이다. 둘 중 하나를 기기/서버 전체 삭제 기한으로 채택하지 않는다.

미확정 일반 조회가 만료된 뒤 실제 최종 확정이 발생하면 새 최종 조회 구간을 실제 사건 시각으로 적용한다. 원래 조회·접수 시각은 덮어쓰지 않는다. 매핑이 삭제/손실됐으면 새 확인 ID를 발급해 같은 쓰기를 다시 실행하지 않는다. 복원은 최신 삭제·권한·실행 결과를 재적용하고 연결 안전성을 확인한 뒤 공개한다.

## 개발 전 연결 검증 시나리오 — 아직 실행하지 않음

- 로컬 기록만 생성, 실제 송신 없음: 접수/성공으로 오인하지 않고 자동 실행 없음.
- 서버 접수 후 응답 유실, 커밋 전/후 각각: 같은 경로/키의 읽기 확인으로만 연결.
- 같은 키가 다른 경로에 사용됨: 별개 확인 결과이며 키만으로 자동 선택하지 않음.
- 재시작/로그아웃/다른 계정/교회 전환: 이전 응답 비공개, 신규 실행 없음.
- 성공 후 대상 row_version 변경: 기존 쓰기 재생 실패와 최소 상태 조회를 구분.
- 접수+168h 만료 후 실제 뒤늦은 확정: 실제 최종 확정+168h만 공개.
- 자료/매핑/백업 복원 실패: 권한/기한/실행 상태 확인 전 공개·재실행 보류.

## 남은 설계 결정

정확한 경로 범위 표현, 서버 ID 발급/내구 접수 시점, 읽기 연결 경로, 영수증/상태 투영의 원자성, 목적별 보유·삭제 상한, 로컬 시계/백업·정리 실패, 대상 Node 24 검증은 미결이다. 이 문서는 이 공백을 명시한 구현 인계 후보이며 실행 허가가 아니다.

## r29 상태·수명 연결

[실제 접수→실행→최종 확정 초안](ACCEPT_EXECUTE_FINALIZE_DRAFT.md)과 [상태별 기록 수명](STATE_RECORD_LIFECYCLE_MAP.md), [22개 수용 시나리오](REQUEST_TRANSITION_ACCEPTANCE.csv)를 함께 읽는다. 후보 구조·새 필드·수명·이행은 DRAFT/OPEN이며 기존 합의 의미를 바꾸지 않는다. 실제 업무 검증은 NOT_RUN이다.
