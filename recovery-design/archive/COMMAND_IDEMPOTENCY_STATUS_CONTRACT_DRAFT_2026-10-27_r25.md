# 요청 식별·중복 방지·결과 조회 API 계약 초안

2026-10-27 / 요청 동일성·내용 변경 거절·기존 결과 우선 확인 원칙 AGREED / 나머지 CONTRACT_DRAFT / 구현·실행 NOT_RUN

확정 근거: 사용자가 직전 세 가지 원칙 확정 질문에 “네”로 동의했다. API 전체를 승인한 것은 아니다.

## 1. 지위와 범위

복원 누적 r9를 이어 작성한다. 소실된 과거 Review r7의 원문 복원이 아니다. ChurchOS 일반 업무 명령의 계약 후보이며 기존 API 경로·canonical·마이그레이션은 수정하지 않는다. 가입 심사·제품별 개인 기록·CHGO 처리 계약으로 확대하지 않는다. 운영 결과 원칙은 합의 사항이고 아래 경로·필드·상태·보유 전략은 신규 제안이다.

## 2. 요청의 의미

요청 식별자는 ‘한 번 수행하려는 동일 업무 의도’를 식별한다. 화면에서 저장을 누를 때 생성해 확정 결과를 확인할 때까지 유지한다. 화면 새로고침·통신 재시도로 새로 만들지 않는다. 다른 내용으로 수정하거나 충돌 해결 후 새 업무를 제출할 때는 결과와 현재 상태를 확인한 뒤 별도 의도로 새 식별자를 만든다.

추측하기 어려운 무작위 식별자 형식을 사용하고 이름·전화번호·토큰·원문을 넣지 않는다. 정확한 길이·포맷은 구현 전 확정한다. 식별자를 안다는 것만으로 조회·실행할 수 없다.

서버의 중복 판정 키 후보는 제품 + 검증된 계정 + 교회 + 요청 식별자다. 명령 종류·대상·기대 버전·의미상 동일하게 정규화한 입력을 최초 접수에 결합한다. 같은 키에 다른 행위·대상·내용·버전을 보내면 거절한다. 단순 JSON 문자열 차이로 동일 의도가 달라지지 않도록 정규화 버전도 고정해야 한다. 본문 자체를 중복 판정 로그에 남기지 않는다. 민감 입력의 일반 해시를 익명 정보로 간주하지 않으며 보호된 검증값의 방식·키 관리·수명은 별도 설계한다.

## 3. 후보 경로와 입력

| 동작 | 후보 경로 | 입력 |
|---|---|---|
| 명령 제출 | POST /api/v1/church/tenants/{tenant_id}/commands | request_id, command_type, target_id, expected_version, payload |
| 본인 최소 상태 조회 | GET /api/v1/church/tenants/{tenant_id}/commands/{request_id}/status | 본문 없음 |

경로는 신규 후보이며 기존 서버와의 충돌·호환성 검토 전이다. tenant_id는 권한 증거가 아니며 검증된 계정의 현재 소속과 대조한다. account_id·역할·승인 여부는 클라이언트 선언으로 받지 않는다. 허용 명령 종류마다 payload 스키마를 별도로 정의하고 임의 필드·임의 DB 작업을 수용하지 않는다. 가입 승인·역할 부여를 이 일반 명령 경로로 우회하지 못하게 한다.

## 4. 최초 요청과 재시도 처리 순서

1. 인증과 해당 교회 접근을 먼저 검증한다. 무효·확인 불가이면 요청 존재를 조회하거나 공개하지 않는다.
2. 접근 가능한 본인 요청의 키와 결합 내용을 조회한다. 다른 계정·교회의 기록은 사용하지 않는다.
3. 기존 같은 요청이 있으면 새로 실행하지 않는다. 내용 불일치는 충돌 처리한다. 현재 업무 권한이 없어도 계정·소속이 유효한 본인에게는 합의된 최소 상태만 제공할 수 있다.
4. 신규 요청이면 현재 명령별 업무 권한·대상 범위·유효 기간·업무 버전을 검증한다. 오래된 권한 캐시나 토큰의 역할만으로 허용하지 않는다.
5. 같은 키의 동시 접수에는 하나의 실행 소유권만 부여한다. 접수 기록만 생겼다고 업무 성공으로 표시하지 않는다. 업무 변경과 확정 결과는 원자적으로 확정하며 이전 해제 경합 합의를 적용한다.
6. 장애로 실행 소유권이 사라진 경우에는 기존 트랜잭션의 커밋·롤백을 판별한 후에만 회복한다. 임대 만료나 시간 초과만으로 다른 실행자를 시작해 중복 실행하지 않는다.

## 5. 최소 결과 상태 후보

| 상태 | 의미 | 앱 동작 |
|---|---|---|
| PROCESSING | 서버가 접수를 확인했지만 최종 결과 미확정 | 같은 요청의 상태 확인 |
| COMMITTED | 업무 변경이 확정됨 | 완료 여부만 안내, 상세 자료는 현재 권한으로 별도 조회 |
| REJECTED | 업무 변경 없이 거절된 결과가 확정됨 | 현재 권한·입력·버전 확인 후 필요 시 새 의도 제출 |
| REVIEW_REQUIRED | 결과를 확정하지 못해 수동 확인 필요 | 미실행·실패로 단정하거나 재실행하지 않음 |

네트워크 단절은 서버 상태가 아니라 앱의 RESULT_UNKNOWN 표시다. 최종 상태는 COMMITTED·REJECTED만으로 제한하는 안이며 운영 검토가 필요하다. 상태 응답에는 request_id·status·최종일 때 confirmed_at·status_expires_at만 후보로 둔다. 응답에서 원문·변경 전후 값·사람 이름·거절 상세 사유·전체 감사 이력을 제공하지 않는다. 상태별 내부 진단 정보는 별도 접근 통제를 적용한다.

본인 최종 최소 상태 조회는 실제 최종 서버 확정부터 168시간 이내에만 허용한다. 조회·재시도는 이를 연장하지 않는다. 계정·소속이 유효하지 않거나 확인 불가이면 기간이 남아도 존재·상태를 제공하지 않는다.

## 6. 응답 분류 후보

| 경우 | HTTP 후보 | 공개 범위 |
|---|---|---|
| 최초 또는 같은 요청의 확정된 최소 상태 | 200 | 허용된 최소 상태 |
| 처리 중 또는 수동 확인 상태 | 202 | 허용된 최소 상태, 완료를 뜻하지 않음 |
| 필수 입력·형식 오류 | 400 | 일반 입력 안내만 |
| 유효한 인증 없음 | 401 | 요청 존재 비공개 |
| 신규 실행 권한 없음 | 403 | 일반 권한 안내, 기존 대상 정보 비공개 |
| 타인·다른 교회·미존재·조회기간 만료 | 404 | 구분되지 않는 일반 안내 |
| 같은 키의 다른 입력 또는 업무 버전 충돌 | 409 | 현재 권한으로 허용되는 일반 안내 |
| 권한·접수 상태를 안전하게 확인 불가 | 503 | 일반 확인 불가, 자동 성공·자동 신규 실행 금지 |

결과 조회 실패를 업무 실패로 해석하지 않는다. 401·403·404·503의 순서와 응답 본문·타이밍을 통한 존재 유출 방지는 구현 전 검토한다. 버전 누락 등 기존 자원 API의 428/412 계약을 일괄 변경하는 제안이 아니다.

## 7. 보유와 오래된 요청

최소 상태 조회 168시간과 중복 방지 기록·업무 원본·감사 기록·백업 수명은 별개다. 현재 계약에 구체 보유 기간을 새로 확정하지 않는다.

특히 오래된 요청 기록을 삭제한 뒤 같은 키가 신규 요청으로 실행되는 공백을 허용할 수 없다. 후보 방식은 서버 발급 실행 기한과 보호된 최소 중복 방지 표식의 결합이다. 실제로 최초 접수되지 않은 지연 요청, 기록 손실·복원, 오프라인 재전송을 포함해 ‘이 요청을 새로 실행해도 안전함’을 증명할 수 없으면 실행을 차단하고 확인 절차로 전환한다. 이 정책의 보유 비용·최소 수집·삭제 계약은 후속 결정 전 운영 적용하지 않는다.

- 동일 키 동시 제출은 업무 변경 1회만 발생한다.
- 같은 키의 다른 내용은 기존 업무를 바꾸지 않는다.
- 커밋 후 응답 유실은 동일 키 재조회로 해결하며 중복 실행하지 않는다.
- 권한 해제 선확정은 아직 확정되지 않은 쓰기를 차단한다.
- 계정·소속 상실 후 본인 요청의 존재도 공개되지 않는다.
- 최종 상태 조회 만료가 키 재사용 허용으로 바뀌지 않는다.
- 요청 기록만 남고 업무 미확정인 장애를 성공으로 표시하지 않는다.
- 복구 뒤 삭제·권한 최신 상태 적용 전 요청 실행·결과 공개가 없다.
